# Runner 설계 계약 해석

`parseContracts()`는 호출자가 특정 commit(내용이 고정된 Git 저장소 버전)에서 읽은 `contracts/` 파일을 받는다.
파일 경로는 저장소 안의 상대 경로만 허용한다.
왜: 다른 폴더의 파일을 계약처럼 보고하거나, 보고한 버전과 실제 파일이 달라지는 일을 막기 위해서다.
이 모듈은 파일 안의 코드나 SQL(데이터베이스에 보내는 명령)을 실행하지 않는다.

`buildDesignSnapshot()`은 해석 결과와 실제 구현에서 추출한 명세를 대조한다.
`reportDesignSnapshot()`은 결과를 기존 Outbox(디스크에 저장하는 보고 대기함)에 넣는다.
왜: 서버 연결이 끊어져도 보고를 잃지 않고 같은 멱등 키로 다시 보낼 수 있어야 하기 때문이다.
호출자가 이미 사용하는 Outbox 전송 주기를 그대로 쓴다.

## 해석 범위

- OpenAPI 3.1: REST API(HTTP 요청으로 자원을 주고받는 방식)의 경로, 요청 파라미터, 요청 본문, 응답과 헤더를 읽는다.
- AsyncAPI 3.0: 채널 주소와 메시지의 JSON Schema(데이터 필드와 타입을 적는 형식)를 읽는다.
  Kafka 메시지도 JSON Schema이면 같은 방식으로 읽는다.
  Q-14 A 결정에 따라 스키마 레지스트리(메시지 형식의 버전을 보관하는 외부 서버)는 연결하지 않는다.
- PostgreSQL SQL: 파일 이름순으로 마이그레이션(저장 구조 변경 파일)을 누적한다.
  테이블·컬럼·기본키·외래키·인덱스를 읽는다.
  `CREATE TABLE`, 지원하는 `ALTER TABLE`, `CREATE INDEX`, `DROP TABLE`, `DROP INDEX`, 컬럼 설명을 반영한다.

Avro·Protobuf, Neo4j·QuestDB·Redis 등 전용 해석기가 없는 형식은 원문을 남긴다.
왜: 확정하지 않은 형식을 임의로 해석하면 실제로 확인하지 않은 내용을 일치로 보고할 수 있기 때문이다.
원문은 `files[].raw`에 둔다.
화면용 `items[].content`는 M6-05 계약의 REST·message·postgres 구조를 따른다.
원문 전용 파일과 통신 종류를 모르는 채널은 Runner의 `items`에 넣지 않는다.
서버가 원문 파일을 대조 안 함으로 표시한다.
왜: 서버가 받지 않는 `file`·`AsyncAPI` 종류로 정상 보고 전체가 거부되는 일을 막기 위해서다.
보고 대기함에 저장할 때와 보내기 직전에 생성에 쓴 OpenAPI 요청 스키마로 검사한다.
중복 주소와 파일·항목 참조도 별도로 검사한다.

## 실제 구현에서 추출하기

호출자는 `openapi`, `asyncapi`, `sql`별 `DesignExtractor` 함수를 제공할 수 있다.
함수는 `{commit, ref, item, signal}`을 받아 `{fields: [{path, type, required}]}` 또는 `null`을 돌려준다.
`signal`은 취소를 알리는 신호다.
`path`는 JSON Pointer(중첩 필드를 가리키는 고정 주소)다.
예를 들어 SQL의 `id` 컬럼은 `/id`다.
OpenAPI의 JSON 요청 필드는 `/requestBody/content/application~1json/id`다.
`~1`은 주소 안의 `/`를 뜻한다.
배열 원소는 `/*`로 표시한다.
실제 추출기에서도 계약 해석기와 같은 주소와 타입 표기를 써야 한다.
SQL 타입 문자열은 `sqlType()`으로 정규화한다.
예를 들어 `int4`는 `integer`, `varchar(10)`은 `character varying(10)`이다.
`serial`과 identity(자동 번호 컬럼)는 실제 DB와 같이 필수로 본다.

실제 명세를 확인할 수 없으면 `null`을 돌려준다.
어댑터가 없거나 예외가 나거나 결과 형식이 잘못되어도 `extracted: null`과 `compat: unchecked`를 보고한다.
왜: 추출 실패를 불일치 0건이나 성공으로 잘못 표시하지 않기 위해서다.
이번 작업에서는 fake(외부 시스템 대신 고정 결과를 주는 구현)로 검증한다.
실제 코드 생성 명령·Drizzle·DB 조회 연결은 실행 격리 결정 뒤 호출자가 연결해야 한다.

요청에서는 필드 삭제가 `compatible`이고 새 필수 필드는 `breaking`이다.
응답·메시지에서는 필드 삭제와 필수 해제가 `breaking`이고 새 필드는 `compatible`이다.
타입 변경은 양쪽 모두 `breaking`이다.
enum(허용 값 목록)·const(고정 값)·format(문자열 형식)은 타입 지문에 넣는다.
이 값이 바뀌면 타입 변경으로 보고한다.
최종 판정은 서버가 `contract`와 `extracted`를 비교해서 내린다.
왜: Runner마다 판정이 달라져도 서버의 승인 규칙이 유지되어야 하기 때문이다.

외부·순환 참조와 지원하지 않는 JSON Schema 키워드는 `unchecked`로 남긴다.
객체로 쓴 스키마에는 `type`이 있어야 한다.
`properties`·`items`·`enum`만 보고 타입을 추측하지 않는다.
왜: 형식이 불명확한 계약을 `any`로 대조하면 검증하지 않은 결과가 일치로 보일 수 있기 때문이다.
참조를 해석한 필드 템플릿과 실패 결과를 재사용한다.
항목당 필드 5,000개·필드 목록 512 KiB·깊이 64를 넘으면 해당 항목을 대조 안 함으로 둔다.
파일은 256 KiB, JSON으로 인코딩한 원문 합계는 512 KiB까지 읽는다.
해석 시간은 전체 1초를 기준으로 제한하고 추출은 항목당 1초·전체 10초를 제한한다.
보고 본문은 서버 계약과 같은 1 MiB까지다.
왜: 작은 계약의 참조가 수백만 필드로 불어나 Runner 전체를 멈추지 못하게 하기 위해서다.
SQL 파일을 하나라도 못 읽으면 SQL 파일 전체를 읽기 실패로 보고한다.
왜: 일부 마이그레이션만 반영한 저장 구조를 최종 구조인 것처럼 대조하지 않기 위해서다.
PostgreSQL 공식 파서로 SQL 문장을 먼저 분류한다.
지원하는 구조 변경은 기존 SQL 모델에 누적한다.
함수·권한·트리거 등은 컬럼 대조와 분리해 원문으로 남긴다.
해석하지 못한 구조 변경은 그 대상 테이블이나 타입을 쓰는 테이블을 대조 안 함으로 둔다.
이 상태는 테이블 이름이 바뀌어도 유지한다.
영향을 받는 타입의 이후 사용도 대조하지 않는다.
DO(실행 시 처리하는 SQL 블록)는 PostgreSQL의 PL/pgSQL(절차형 SQL 언어) 파서로 본문을 읽는다.
조건·반복문의 실행 여부를 추측하지 않는다.
정적 SQL이 바꿀 수 있는 테이블과 타입만 대조 안 함으로 둔다.
왜: 실행되지 않았을 수도 있는 변경을 확정 구조에 바로 반영하면 안 되기 때문이다.
동적 SQL은 실행하지 않는다.
`EXECUTE format(...)`의 첫 인수가 문자열 리터럴인 경우만 제한적으로 분류한다.
`%I`·`%L`·`%s`를 자리값으로 바꾼 뒤 공식 파서로 문장이 정확히 하나인지 확인한다.
허용 목록은 `CREATE TRIGGER`, `CREATE INDEX`, 기존 컬럼의 `UNIQUE`·`FOREIGN KEY` 제약 추가다.
`GRANT`·`REVOKE`, 소유자 변경, `ALTER FUNCTION`의 `SET`·`RESET`, `DROP TRIGGER`도 허용한다.
정적 SQL과 동적 템플릿은 같은 판정 함수로 이 목록을 확인한다.
대상 테이블을 몰라도 이 문장 종류는 비교 대상인 필드 집합·타입·필수 여부를 바꾸지 않으므로 오염하지 않는다.
`PRIMARY KEY`는 컬럼을 암묵적으로 필수로 만들 수 있어 허용하지 않는다.
종류를 모르는 `DROP CONSTRAINT`도 허용하지 않는다.
다른 문장 종류·변수 템플릿·파싱 실패·미지원 PL/pgSQL 실행은 대조 안 함으로 둔다.
카탈로그 조회의 결과를 해석하거나 실제 DB에 연결하지 않는다.
조건·반복 질의·DECLARE 기본값·RETURN·`format` 인수를 포함한 모든 PL/pgSQL 표현식도 SQL 구문 트리로 읽는다.
함수 호출은 코드 한 곳의 고정 허용 목록에 있는 기본 함수만 통과한다.
이름은 한정하지 않거나 `pg_catalog`로 한정해야 한다.
허용 목록 밖의 함수나 해석할 수 없는 표현식은 전체를 대조 안 함으로 둔다.
왜: 조건문이나 초기값의 함수도 테이블 구조를 바꿀 수 있기 때문이다.
마이그레이션에 같은 이름의 함수를 정의하면 그림자 함수(기본 함수와 이름이 겹치는 사용자 함수)로 본다.
이 경우 입력 전체를 대조 안 함으로 두어 앞서 읽은 호출도 신뢰하지 않는다.
다른 파일과 DO 본문 안의 정의에도 같은 규칙을 적용한다.
영향 범위를 모르면 이미 읽은 테이블과 이후 파일에서 읽는 테이블을 모두 대조 안 함으로 둔다.
왜: 해석하지 않은 변경이 이전 구조를 바꿨는지 확인할 수 없기 때문이다.
지원하지 않는 PostgreSQL 문법을 실제 DB에서 임의로 실행해 확인하지 않는다.
`CASCADE` 연쇄 삭제와 의존 인덱스·제약·외래키가 있는 컬럼 삭제도 읽기 실패로 남긴다.
왜: 의존 항목을 정확히 제거하지 않고 이전 정보를 계속 보여주면 잘못된 설계가 되기 때문이다.

## 브랜치와 반영 결과

`ref`와 `jobKind`(서버가 준 작업 종류)는 반드시 지정한다.
`ref`는 `main` 또는 `agent/TASK-0001`처럼 Task 키가 붙은 브랜치다.
`main`은 `design_apply`·`merge_followup` 작업만 보고한다.
`attempt` 작업은 서버 작업의 `payload.branch`를 `branch`로 전달하고 그 브랜치만 보고한다.
브랜치 형식은 generated client에 포함한 서버 계약의 정규식으로 검사한다.
다른 브랜치의 파일은 `draft`로 보고한다.
왜: 진행 중인 변경을 main의 확정 설계와 섞으면 안 되기 때문이다.

`design_apply`의 결과도 실제 결과 commit과 같은 `jobId`·`fence`로 보고한다.
fence는 낡은 Runner 보고를 막는 번호표다.
이 모듈은 계약 파일을 고치거나 커밋하거나 서버의 불일치를 직접 완료 처리하지 않는다.
서버가 main 결과 보고를 확인한 뒤 상태를 바꾼다.

외부 쓰기 차단 오류는 디스크 대기함에 보류 상태로 남긴다.
같은 `ref`의 뒤 보고는 순서대로 기다린다.
다른 `ref`의 보고와 다른 종류의 보고는 계속 보낸다.
예전 대기함의 보고도 본문의 `ref`로 순서를 묶는다.
왜: main의 쓰기 차단 때문에 다른 브랜치와 자원 보고까지 멈추면 안 되기 때문이다.
재시도 간격은 최대 60초이고 준비 상태 경고에서 보류를 확인할 수 있다.
상태 전이 오류는 재시도하지 않고 기존 거부 통지로 작업 번호와 원인을 호출자에게 알린다.
버전 충돌은 서버가 보내 준 항목 hash(내용의 지문)와 비교한다.
내용이 같으면 이미 반영한 것으로 처리한다.
다르면 서버와 불일치로 알리고 중지한다.
왜: 재시도로 서버의 최신 판정을 덮어쓰면 안 되기 때문이다.
hash를 만들 때 필드 목록은 주소순으로 정렬한다.
`content.tables`·`content.usedBy`·`content.decisionKeys`도 문자열순으로 정렬한다.
나머지 배열의 순서는 보존한다.

같은 항목 키가 여러 파일에 있으면 그 항목을 한 번만 남기고 대조 안 함과 중복 이유를 보고한다.
다른 정상 항목은 계속 보고한다.

```sh
pnpm -C agent-runner test -- design
```

M6-05 공용 fixture(정상·위반 사례 묶음)와 hash 벡터 검사는 별도로도 실행한다.
계약이 맞지 않으면 실패하며 skip(검사 생략)은 하지 않는다.
왜: Runner 수정 검증과 두 시스템의 계약 검증을 함께 확인하기 위해서다.

```sh
pnpm -C agent-runner test:design-contract
```

OpenAPI 계약이 바뀌면 client를 재생성하고 이 검사도 다시 실행한다.
