# ② 통합 확인 연결 안내

CI(Continuous Integration, 코드를 자동으로 빌드하고 검사하는 과정)의 ② 경로는 `IntegrationQueue`다.
M7-06이 서버의 병합 대기열 순서로 `run`을 호출한다.
실제 CLI(명령줄 프로그램)와 GitHub 연결은 제공하지 않는다.
Q-08·Q-09의 결정 전에는 기존 GitHub client에 fake(실제 서비스 대신 쓰는 가짜)를 연결한다.

## 실행 순서

1. `open`으로 전용 기록 폴더를 연다.
   기존 Runner의 파일 잠금을 재사용한다.
   왜: 두 Runner가 같은 대기열의 병합을 동시에 시작하면 안 된다.
2. `run`에 PR(변경을 main에 합쳐 달라는 요청) 번호와 브랜치를 전달한다.
   `qaHeadSha`와 `specRevision`도 전달한다.
   `readVerification`은 서버의 현재 QA(Quality Assurance, 수용 기준 검증) 결과를 조회한다.
   왜: 낡은 PASS나 바뀐 명세로 병합하지 않아야 한다.
3. 원격 main A의 정의를 고정한다.
   `observeMainPipeline`은 `{baseSha, pipelineSha}`를 별도 관측 보고로 영속 보관한다.
   이 함수가 실패하면 검사를 시작하지 않는다.
   왜: 서버가 ② 실행의 정의 SHA(내용을 식별하는 해시)를 main A의 관측과 대조해야 한다.
   M7-04의 최종 관측 API 연결은 M7-06에서 기존 outbox(재전송할 보고를 저장하는 대기열)를 쓴다.
4. QA한 H에 main A만 자동 병합해 H′를 만든다.
   부모 순서는 정확히 H,A다.
   tree(커밋 시점의 파일 전체 내용)를 Git의 자동 병합 결과와 다시 비교한다.
   추가 변경이나 충돌을 허용하지 않는다.
   H가 이미 A를 포함하면 H를 그대로 쓴다.
   왜: 자동 동기화 외의 변경까지 이전 QA로 승인하면 안 된다.
5. H′를 PR 브랜치에 일반 push한다.
   H′의 새 사본에서 기존 `runTaskCheck`로 ①을 다시 실행한다.
   ①은 고정한 A의 정의를 받는다.
   ②도 별도의 새 사본에 같은 정의의 `install`로 설치한다.
   그 뒤 `stages.int`의 명령을 정의 순서대로 실행한다.
   왜: Agent가 남긴 파일이나 실행 도구를 검사 근거로 쓰면 안 된다.
6. 검사 앞뒤에 추적 파일을 고정 SHA와 대조한다.
   실패 뒤의 단계는 `skip`으로 남는다.
   출력과 소요 시간을 보존한다.
   비밀값 가리기는 기존 함수를 쓴다.
   공유 `HeavySemaphore`의 번호표를 반납하기 전에 사본을 정리한다.
   왜: 실제 검사한 코드와 보고한 코드가 같아야 한다.
7. QA·명세·main·PR head를 다시 조회한다.
   ② 성공은 `agentwbs/int`로 H′에만 게시한다.
   병합 직전에도 같은 값인지 다시 확인한다.
   왜: 검사하는 동안 바뀐 코드는 다시 검사해야 한다.
8. 병합 의도를 먼저 디스크에 저장한다.
   기존 `mergePullRequest`에 `baseSha=A`, `headSha=H′`를 넘긴다.
   이 client는 예상 head와 strict 보호(main의 최신 커밋을 포함해야 하는 보호 규칙)를 사용한다.
   실제 병합 부모 A,H′와 H′의 tree도 확인한다.
   왜: 마지막 조회 직후의 경합도 GitHub에서 막아야 한다.

실행 함수 `execute`는 프로세스 그룹의 자손까지 모두 종료한 뒤 반환해야 한다.
마이그레이션은 빈 시험 DB에서 시작해야 한다.
서비스 기동과 앱의 health check(정상 응답 확인), 브라우저 시험도 프로젝트의 main 정의가 정한다.
이 모듈은 명령의 의미를 이름만으로 대신 검증하지 않는다.
왜: G §4.13은 별도 CI 엔진을 만들지 않고 프로젝트 정의를 순서대로 실행하도록 한다.

테스트 단계 이름은 `test`, `tests`, `unit`, `integration`, `e2e`, `contract`다.
이 단계의 일반 실패만 한 번 재시도한다.
재시도에서 통과하면 `flakyCandidates`에 이름을 남긴다.
실행 오류·사본 변조·중단은 재시도하지 않는다.
다른 단계 이름으로 테스트를 실행하는 프로젝트는 연결 전에 단계 종류를 명시하는 계약이 필요하다.
왜: 마이그레이션이나 서비스 기동을 테스트로 잘못 알아보고 반복 실행하면 안 된다.

## 결과와 보고

- `merged`: 부모·tree 대조까지 끝났다.
  `actualMergeSha`, `actualTreeSha`, `mergeParents`를 서버에 보고한다.
  자동 동기화했다면 M7-04 형식의 `headSync`도 함께 보고한다.
- `recheck`: main·head·QA가 바뀌었거나 strict 보호가 거부했다.
  새 CI 실행으로 다시 검사한다.
  head가 QA의 H와 다르면 먼저 새 head를 QA해야 한다.
  왜: 이전 H′에 다시 main을 합친 커밋은 부모가 원래 H,A인 단일 자동 병합이 아니다.
- `baseline_failed`: ①의 기준 설치·수집 실패다.
  `failScope: baseline`을 보존한다.
  Task 자동 재작업 횟수를 쓰면 안 된다.
- `rework`: Task 코드 검사 실패나 병합 충돌이다.
  M7-04가 서버의 `gate → rework` 전이를 처리한다.
- `unknown`: 병합 결과가 미확정이다.
  `reconcile`로 쓰기 없이 다시 조회한다.
  같은 병합을 다시 호출하면 안 된다.
- `verify_failed`: 실제 병합 SHA와 경고를 보존한다.
  서버의 `MERGE_MISMATCH` 처리로 넘긴다.
  Task를 완료로 만들거나 main을 자동으로 되돌리지 않는다.
- `blocked`: 앞선 병합 기록이 남아 있다.
  그 기록을 먼저 보고하거나 대조해야 한다.

결과를 기존 outbox에 영속 보관한 뒤 `acknowledge`를 호출한다.
그 전에는 다음 PR을 시작하지 않는다.
`unknown`과 `verify_failed`는 이 함수로 해제할 수 없다.
왜: 네트워크 시간 초과는 GitHub가 나중에 병합하지 않는다는 뜻이 아니다.
대조 실패의 해제는 사람이 실제 병합과 서버 기록을 확인하는 별도 복구 절차가 필요하다.
이 모듈은 그 결정을 자동으로 하지 않는다.

재시작하면 같은 기록 폴더로 `open`하고 `reconcile`을 먼저 호출한다.
이미 확정한 결과는 저장한 그대로 재생한다.
미확정 기록만 GitHub에 다시 조회한다.
병합 직후 프로세스가 종료되어도 저장한 A,H′를 기준으로 대조한다.
기록이 손상됐으면 원본을 보존하고 중지한다.
종료할 때는 `close`로 파일 잠금을 푼다.
검사 도중 남은 사본은 M7-01의 Runner 시작 정리 경로를 재사용한다.

## 묶음 확인

대기열이 길면 `checkBatch`로 여러 PR을 예비 검사한다.
같은 main A에서 묶음 커밋을 만든다.
실패한 묶음은 반으로 나누고 각각 다시 검사한다.
하나만 남아도 실패한 PR은 `suspects`에 담는다.
각각은 통과하고 함께 있을 때만 실패하면 상호작용 문제다.
이 경우 상위 묶음의 실패 기록을 원인 탐색에 쓴다.

묶음 확인은 브랜치를 push하지 않는다.
commit status(커밋에 붙이는 검사 결과)도 게시하지 않는다.
PR 병합도 호출하지 않는다.
왜: 각 PR은 자기 H′에서 ①·②를 통과한 뒤 하나씩 병합해야 한다.

## 검증

`pnpm -C agent-runner test -- ci-int`를 실행한다.
로컬 Git과 기존 fake GitHub HTTP 서버를 쓴다.
실 GitHub 보호 실증과 실제 ①→QA→②→완료 연결은 이 시험에 포함하지 않는다.
각각 M4-06·Q-09와 M7-06의 작업이다.

## 용어

| 이름 | 뜻 |
| --- | --- |
| `headSync` | QA한 H에 main A만 합쳤다는 부모·tree 근거다. |
| `mergeParents` | 실제 PR 병합 커밋의 부모다. 순서는 A,H′다. |
| `failScope` | 실패가 기준 코드(`baseline`) 쪽인지 Task 코드(`task`) 쪽인지 구분한다. |
| `unknown` | 병합 여부를 아직 확정할 수 없는 결과다. |
| `acknowledge` | 결과 보고를 보관한 뒤 다음 PR을 시작할 수 있게 기록을 정리하는 함수다. |
