# ③ 야간 점검 안내

③ 야간 점검은 매일 정한 시각에 main 브랜치 전체를 다시 확인하는 단계다(G L476).
여기서는 Runner(개발 PC에서 Agent와 검사를 실제로 실행하는 프로그램)가 하는 일을 적는다.
M7-06에서 실제 실행기·API에 연결한다. 지금은 job 처리 흐름이나 서버 판정을 바꾸지 않는다.

## ③④가 지키는 네 가지 원칙

조정자가 리뷰(2026-11-27) 뒤 정한 원칙이다. 본문의 「원칙 A」 등은 아래를 가리킨다.

- **원칙 A — 단계 출력은 믿지 않는다.**
  - Runner는 단계가 만든 경로·링크를 따라가 쓰지 않는다. Runner 소유 폴더에만 쓴다.
  - 화면 비교 기준 이미지와 응답 시간 기준은 main 고정 정의에서만 읽는다.
  - 기준이 있는 측정이 빠지거나 이름이 바뀌면 실패다.
- **원칙 B — 재시도는 판정을 느슨하게 하지 않는다.**
  - 재시도에서 새로 실패한 시험이 있으면 실패다.
  - 응답 시간은 모든 시도 중 하나라도 기준을 넘으면 기준 초과다.
- **원칙 C — 사실대로 보고한다.**
  - 배포 실패 때 이전 서비스 상태는 실제로 확인한 결과만 보고한다.
  - 각 단계 뒤 사본이 커밋과 달라졌으면 실패다.
- **원칙 D — 이름·키가 부딪히지 않는다.**
  - 야간 키는 날짜 기준이다. 시작 응답을 잃어도 같은 키·같은 본문으로 복구한다.
  - Runner가 붙이는 단계 이름에는 `runner:` 접두어를 붙인다.

## 언제 시작하나

- 정책의 `ci.nightAt`(기본 `02:00`) 시각이 지나면 시작한다.
- 날짜는 Asia/Seoul(한국 시간) 기준이다.
  - 왜: 서버의 날짜 형식(shared 계약의 「Asia/Seoul 기준 하루」)과 같은 날을 가리켜야 한다.
- `dueNight(home, now, nightAt)`가 시작할 날짜를 준다. 아직 아니면 `null`이다.
- Runner가 꺼져 있다가 09시에 켜져도 그날 한 번은 한다.
  - 왜: 꺼져 있었다는 이유로 그날 점검이 빠지면 main이 깨진 것을 하루 늦게 안다.
- 마지막으로 시작한 날짜는 `<AWBS_HOME>/ci/night/state.json`에 남긴다.
- 이미 시작한 날짜보다 이르거나 같은 날짜면 다시 하지 않는다.
  - 왜: 이 PC는 시계가 가끔 뒤로 간다. 시계가 뒤로 가도 같은 날을 두 번 돌리면 안 된다.
- 서버에 보낼 때 멱등 키(같은 요청을 두 번 보내도 한 번만 처리되게 하는 이름표)는 `night:<날짜>`다(contracts §3.2-5).
  - 예: `night:2026-11-27`
  - 시작을 보내기 전에 시작 본문(고정한 main 포함)을 `state.json`의 `pending`에 저장한다.
  - 시작 응답을 잃거나 Runner가 죽으면, 같은 날짜는 main이 움직였어도 저장한 본문을 그대로 다시 보낸다.
    - 왜: 서버는 같은 키에 다른 본문이 오면 `IDEMPOTENCY_CONFLICT`로 거부한다. 같은 본문이어야 같은 실행을 돌려받는다(원칙 D).
  - 실행이 끝나면 `pending`을 지운다. 다음 날은 그날의 main을 새로 고정한다.

## 무엇을 실행하나

1. main을 고정한다. 기준 커밋(`baseSha`)과 정의 파일 SHA(`pipelineSha`)를 함께 남긴다.
2. job(서버가 Runner에게 시키는 일 하나) 없이 시작한다. 야간 점검은 job이 없는 유일한 실행이다.
   - 그래서 갱신 보고의 `fence`(낡은 Runner의 보고를 막는 번호표)는 항상 `null`이다(contracts §3.2-4).
3. 고정한 커밋을 새 사본에 꺼낸다. Agent 작업 폴더는 쓰지 않는다.
4. 정의의 `task` 첫 단계(`install`)로 설치한 뒤 `night` 단계를 순서대로 실행한다.
   - Runner가 붙이는 설치 단계는 `runner:install`이라는 이름으로 보고한다.
   - 왜: 정의의 단계 이름은 영소문자·숫자·`-`만 쓰므로 `:`이 든 이름과 겹치지 않는다. 겹치면 서버가 보고를 거부한다(원칙 D).
5. 각 단계가 끝날 때마다 사본이 고정한 커밋과 같은지 다시 확인한다. 단계가 커밋 파일을 바꿨으면 그 단계는 실패다.
   - 왜: 다른 파일로 한 검사를 그 커밋의 근거로 남기면 안 된다(원칙 C).
6. 실행이 끝나면 사본을 지운다.

## 단계 결과 보고서 계약

이 절은 단계 명령과 Runner 사이의 계약이다(조정자 결정 4, 2026-11-27 승인).
이름과 형식을 바꾸려면 계약을 바꾸는 것이므로 조정자 승인이 필요하다.
계획 문서(docs/plan)에는 아직 없다. 반영 목록에 올라가 있다.

### 환경 변수

Runner는 ③④의 각 단계 명령에 아래 환경 변수를 준다.

- ③에만: `AWBS_SCREEN_WIDTH`, `AWBS_SCREEN_HEIGHT` — 앱 화면을 찍을 크기(기준 이미지와 같은 1440×900)

- `AWBS_REPORT`: 단계가 결과를 JSON으로 쓸 파일의 절대 경로. 시도마다 새 경로다.
- `AWBS_REPORT_NONCE`: 이번 시도에만 쓰는 일회용 값(nonce). 보고서의 `nonce`에 그대로 적어야 한다.
- `AWBS_EVIDENCE_DIR`: 스크린샷 같은 근거 파일을 둘 폴더의 절대 경로
- ④에만 주는 변수는 deploy/README.md에 있다.

두 경로는 모두 저장소 밖의 근거 폴더(`<AWBS_HOME>/runs/<실행 ID>/`) 안이다.
왜: 검사 사본 안에 파일을 쓰면 「커밋하지 않은 변경」으로 보여 사본 대조가 깨진다.

### 보고서 형식

- 보고서는 없어도 된다. 없으면 종료 코드만으로 판정한다.
- 보고서를 쓴다면 `nonce`에 이번 시도의 `AWBS_REPORT_NONCE`를 그대로 적는다. 없거나 다르면 형식 오류이고 그 단계는 실패다(재리뷰 원칙 3).
  - Runner는 시도마다 새 무작위 경로를 주고, 그 경로의 보고서만 nonce를 확인해 읽는다.
  - 옛 보고서는 지우지 않는다. 이번 시도의 경로는 새 무작위 이름이라 지울 것이 없다.
    - 왜: 이름 앞부분으로 고르면 `a-1`과 `a`처럼 이름이 겹치는 다른 단계의 근거를 지울 수 있다(3차 리뷰). 옛 파일은 실행 폴더 보존 정책(30일)으로 정리한다.
  - 왜 새 경로와 nonce인가: 중단된 야간 점검은 같은 실행 ID로 재개한다. 예전 보고서를 읽으면 이번 측정이 없는데도 통과할 수 있다.
- 최상위 항목은 `nonce`와 아래 넷만 쓸 수 있다. 다른 항목이 있으면 형식 오류이고 그 단계는 실패다.
- 크기는 4 MiB 이하여야 한다.

```json
{
  "nonce": "AWBS_REPORT_NONCE 값",
  "tests": [{ "key": "wbs-tree.spec.ts › 접힘 상태 유지", "status": "fail" }],
  "screens": [{ "name": "wbs", "actual": "shots/wbs.png", "expected": "shots/wbs.proto.png" }],
  "timings": [{ "name": "GET /api/tasks", "samplesMs": [120, 140, 400] }],
  "screenshots": ["shots/login.png"]
}
```

- `tests[]`: 테스트 이름(`key`)과 결과(`status`: `pass` 또는 `fail`). 한 시도 안에서 이름이 겹치면 안 된다.
- `screens[]`: 화면 이름(`name`)과 앱 스크린샷 파일(`actual`)만 쓴다.
  - 비교 기준 이미지(`expected`)를 넣으면 형식 오류다. 기준은 main 정의에만 있다(아래 「화면 비교」).
- `timings[]`: API 이름(`name`)과 측정값 목록(`samplesMs`, 밀리초)만 쓴다.
  - 기준(`budgetMs`)을 넣으면 형식 오류다. 기준은 main 정의에만 있다(아래 「주요 API 응답 시간」).
- `screenshots[]`: ④ 브라우저 접속 스크린샷 파일.
- 파일 경로는 모두 `AWBS_EVIDENCE_DIR` 기준 상대 경로다.
- 항목마다 위에 적은 필드만 쓸 수 있다. 다른 필드가 있으면 형식 오류다.
- 단계 폴더 밖을 가리키면(`..`·중간 폴더 symlink 포함) 그 파일을 읽지 않는다.
- 보고서 파일이나 근거 파일 자체가 symlink면 따라가지 않는다(O_NOFOLLOW).
  - 왜: 단계가 다른 파일(비밀값 등)을 근거인 척 올리지 못하게 한다(원칙 A).

### 단계 출력은 믿지 않는다 (원칙 A)

- 근거 폴더는 둘로 나뉜다.
  - `runs/<실행 ID>/step/`: 단계에게 주는 폴더(`AWBS_EVIDENCE_DIR`, `AWBS_REPORT`가 여기 있다).
  - `runs/<실행 ID>/runner/`: Runner만 쓰는 폴더(로그 원문, `run.json`).
- Runner는 `runner/`에 새 파일만 만든다(O_CREAT·O_EXCL). 링크를 따라가지 않는다(O_NOFOLLOW).
  - 같은 이름이 이미 있으면 덮어쓰지 않고 `e2e-1~2.log`처럼 다른 이름으로 만든다.
  - 쓰기 전마다 `runs/<실행 ID>/`와 `runner/`가 링크가 아닌 실제 폴더인지 확인한다.
  - 왜: 단계가 미리 심은 링크를 Runner가 따라가 쓰면 다른 작업의 근거를 덮어쓴다.
- 비교 기준(화면 기준 이미지·응답 시간 기준)은 main에 고정된 정의에서만 읽는다. 실행 출력이 바꿀 수 없다.
- 기준이 있는 측정이 빠지거나 이름이 바뀌면 그 단계는 실패다.
- 한계: 지금은 Runner와 단계가 같은 사용자 권한으로 돈다.
  - 그래서 확인과 쓰기 사이에 폴더를 바꿔치기하는 경쟁(TOCTOU: 확인한 시점과 사용하는 시점 사이의 틈)까지는 이 코드만으로 막지 못한다.
  - 이 틈은 Q-08에서 단계를 전용 계정으로 실행해 막는다(조정자 결정 10). 전용 계정은 Runner 폴더에 쓸 권한이 없다.

## 판정 규칙

### 전체 E2E와 불안정 테스트

- E2E(End-to-End, 사용자가 쓰는 것처럼 화면부터 서버까지 한 번에 확인하는 시험)는 `tests` 결과로 판정한다.
- 실패한 단계는 정책의 `ci.retry`(기본 1)번 더 실행한다(G L482).
  - 설치 단계는 재시도하지 않는다. 재시도는 실패 테스트를 위한 것이다.
- 재시도는 판정을 느슨하게 하지 않는다(원칙 B).
  - 시도마다 실제로 보고된 테스트는 그 시도의 결과로 바꾼다.
  - 앞에서 통과했어도 재시도에서 실패하면 실패다. 재시도에서 처음 나온 실패 테스트도 실패다.
  - 재시도에 다시 나오지 않은 테스트만 앞 결과를 그대로 둔다. 사라진 실패를 통과로 보면 실패를 숨길 수 있다.
- 앞 시도에서 실패했는데 마지막 결과가 통과인 테스트는 「불안정 후보」다.
  - 불안정 후보는 통과를 막지 않는다.
- 격리된 테스트가 실패하면 결과는 남기되 통과를 막지 않는다.
  - 격리 목록은 정책(`GET /api/runner/policy`)의 `ci.quarantined[]`에서 받는다(조정자 결정 1, M7-04 14b60db).
    - 값은 `flaky_tests.test_key`다. 단계 보고서 `tests[].key`와 같은 이름이다.
    - 필수 필드다. `policyQuarantine(policy.ci)`가 판정 집합으로 바꾸고, 없거나 형식이 틀리면 거부한다.
  - 격리를 해제하면 다음 실행부터 다시 판정에 들어간다.
- 종료 코드가 실패인데 실패 테스트가 하나도 없으면 실패다. 격리로 덮지 않는다.
  - 왜: 테스트가 아닌 다른 이유(설정 오류 등)로 깨진 것까지 격리가 숨기면 안 된다.
- 종료 코드가 0이어도 격리하지 않은 실패 테스트가 보고서에 있으면 실패다.

### 불안정 테스트 보고

- 불안정 후보나 격리 실패가 된 테스트는 「추적」을 시작해 `flakyTests`로 보낸다.
- 추적 중인 테스트는 이후 정상 통과한 날에도 보낸다.
  - 왜: 회복해서 낮아진 비율이 서버 화면에 반영되어야 격리·해제를 바르게 판단한다.
  - `rate`: 최근 20번 야간 점검 중 그 테스트가 한 번이라도 실패한 비율이다. 화면의 「2 / 20 실패」와 같은 뜻이다.
  - `lastFailedAt`: 실제로 마지막에 실패한 야간 점검이 끝난 시각이다. 통과한 날은 바꾸지 않는다.
- 불안정 후보가 아닌 진짜 실패(재시도에서도 실패)는 추적하지 않는다.
- 담당 Task는 보내지 않는다.
  - 왜: 야간 점검은 Task가 없는 실행이다. 서버는 이미 정해진 담당 Task를 지우지 않고 그대로 둔다(M7-04).
- 최근 결과 기록은 `state.json`에 함께 남는다.

### 화면 비교

- 기준은 main 정의의 night 단계 선택 필드 `screens`에 적는다(원칙 A, 조정자 결정 13과 보완).
  - 화면 하나마다 아래 필드를 적는다.
    - `page`(필수): `prototype/uiux/` 아래 HTML 파일
    - `route`(선택): 화면을 여는 `#조각`
    - `steps`(선택): 화면까지 가는 제한된 조작. 1~20개.
    - `ready`(필수): 화면 준비가 끝났음을 알리는 CSS 선택자. 이것이 보일 때까지 기다린 뒤 찍는다.
  - `steps`에 쓸 수 있는 조작은 세 가지뿐이다.
    - `click: 선택자` — 그 요소를 누른다.
    - `waitFor: 선택자` — 그 요소가 보일 때까지 기다린다.
    - `setViewport: { width, height }` — 화면 크기를 바꾼다(가로 320~3840, 세로 240~2160).
  - 임의 JavaScript 실행은 받지 않는다. 다른 조작이나 필드가 있으면 정의 전체를 거부한다.
    - 왜: 기준을 만드는 절차가 코드 실행이 되면, 정의만 보고 무엇을 찍는지 알 수 없다.
  - 원본 프로토타입(`Main.dc.html`)에는 `#조각` 라우팅이 없다. 그래서 보통 `steps`로 화면까지 찾아간다.

```yaml
  night:
    - name: visual
      argv: [node, capture.mjs]
      screens:
        home:
          page: prototype/uiux/Main.dc.html
          ready: main
        ci:
          page: prototype/uiux/Main.dc.html
          steps:
            - click: "nav [data-nav=ci]"
            - waitFor: .ci-tabs
          ready: .ci-tabs
```

- 조작이 실패하거나 `ready`가 10초 안에 보이지 않으면, 그 화면은 `missing`(비교 불가)이고 실패다.
- 기준 이미지는 Runner가 직접 만든다(조정자 결정 8). 커밋한 PNG는 요구하지 않는다.
  - Runner 소유 렌더러가 고정한 main 커밋의 HTML을 렌더해 PNG로 찍는다.
    - 렌더러는 단계(정의의 명령)가 아니라 Runner가 실행한다. 그래서 Agent가 만든 코드가 기준을 만들 수 없다.
  - 렌더 설정은 `BASELINE_RENDER`로 고정한다.
    - 뷰포트 1440×900, 배율 1
    - 글꼴 `Noto Sans KR`(CSS로 모든 요소에 강제)
    - 언어 `ko-KR`, 시간대 `Asia/Seoul`, 애니메이션·커서 끔
    - 왜: 같은 main이면 언제 렌더해도 같은 기준이 나와야 한다.
  - 렌더러 브라우저는 네트워크가 없는 상태로 띄운다(3차 리뷰, 조정자 지시).
    - 왜: 페이지 안 가로채기로 하나씩 막으면 끝이 없다. 예를 들어 blob Worker 안의 WebSocket은 Playwright의 가로채기를 거치지 않았다. 소켓 자체가 바깥에 닿지 않아야 한다.
    - 1순위 `namespace`: 사용자 네트워크 네임스페이스(`unshare --user --map-current-user --net`, root 불필요) 안에서 Chromium을 띄운다.
      - 그 안에는 꺼진 loopback 하나뿐이라 이 PC의 다른 서비스를 포함해 어디에도 접속할 수 없다.
      - Runner가 작업 폴더에 작은 실행 래퍼(`chromium-netns.sh`)를 만들어 Playwright의 `executablePath`로 넘긴다. Playwright는 파이프로 브라우저와 이야기하므로 네트워크가 없어도 조작할 수 있다.
      - `detectNetworkIsolation()`이 실제로 네임스페이스를 만들어 보고 쓸 수 있는지 정한다. 이 개발 PC(WSL2, util-linux 2.39.3)에서는 된다.
    - 2순위 `proxy`(네임스페이스를 못 쓸 때): 실행 인자로 모든 소켓을 막는다.
    - 두 방식 모두 아래 차단 인자(`NETWORK_DENY_ARGS`)를 붙인다.
      - `--proxy-server=socks5://127.0.0.1:9`: 모든 요청을 죽은 주소(discard 포트)의 프록시로 보낸다.
      - `--proxy-bypass-list=<-loopback>`: loopback도 프록시를 거치게 한다(기본 우회를 끈다).
      - `--host-resolver-rules=MAP * ~NOTFOUND`: localhost를 포함한 모든 이름 해석을 실패시킨다(EXCLUDE 없음).
      - `--force-webrtc-ip-handling-policy=disable_non_proxied_udp`: WebRTC가 프록시를 거치지 않는 UDP를 쓰지 못한다.
      - 백그라운드 통신 끄기(`--disable-background-networking`, `--disable-component-update`, `--dns-prefetch-disable`, `--no-pings`)
    - 프로토타입은 고정한 main의 `prototype/uiux/` 파일을 Runner 소유 작업 폴더(`<AWBS_HOME>/ci/render/<무작위>/`)에 꺼내 `file://`로만 연다. 끝나면 지운다.
    - 2차 방어: 컨텍스트 가로채기(그 폴더의 `file://`만 통과, 나머지 모두 차단), WebSocket 닫기, 서비스 워커·다운로드 차단, 새 창 바로 닫기.
    - 실제 Chromium 시험(`ci-night-chromium`)으로 확인한다.
      - 페이지·Worker·SharedWorker의 WebSocket, WebRTC(STUN·TURN), fetch keepalive, EventSource, sendBeacon, 새 창, `window.open`, 외부 CSS·이미지·글꼴이 두 방식 모두 접속 0건이다.
      - 대조 시험: 같은 프로토타입을 보호 없이 띄우면 실제로 접속이 기록된다. 시험 장치가 누출을 잡는다는 증거다.
      - 겹마다 따로 시험한다. 네임스페이스 래퍼만, 차단 인자만, 그 안의 프록시 쌍만, 이름 해석 차단만으로도 각각 접속 0건이다.
        - 왜: 여러 겹이 함께 있으면 한 겹이 빠져도 다른 겹이 가려 시험이 알아채지 못한다.
      - blob SharedWorker는 `file://` 문서(불투명 출처)에서 시작되지 않는다. 렌더러도 `file://`로 열므로 같은 이유로 막힌다.
      - 리뷰어 방식(관측용 프록시를 브라우저에 끼워 넣음)으로도 네임스페이스 안의 Worker WebSocket은 닿지 않는다.
      - Runner에 Playwright가 없어 지금은 이 PC의 agent-wbs 웹 앱 설치본을 쓰고, 없으면 건너뛴다.
  - 만든 기준 이미지는 `<AWBS_HOME>/ci/baselines/<main SHA>/`에 보관한다. 같은 main이면 다시 렌더하지 않는다.
    - 보관본은 링크를 따라가지 않고 읽는다. 손상됐으면 다시 렌더한다.
  - 렌더가 실패하거나 렌더러가 연결되지 않았으면 그 화면은 `missing`(비교 불가)이고 실패다.
  - 고정 글꼴이 없으면 브라우저가 다른 글꼴로 그린다. 그래서 렌더러가 브라우저 안에서 글꼴 설치를 재고, 없으면 렌더를 멈춘다(비교 불가, 결정 12).
    - 글자 폭으로 잰다. `document.fonts.check`는 없는 글꼴에도 true를 돌려주므로 쓰지 않는다.
    - Runner 준비 점검의 `font` 항목도 `fc-list`로 같은 글꼴을 확인한다. 없으면 warn이고, 실행은 멈추지 않는다.
  - 실제 브라우저 렌더러(`createPlaywrightRenderer`)는 M7-06에서 Playwright의 chromium을 넘겨 연결한다.
    - Runner에 Playwright 의존성을 더하는 일(lockfile 변경)은 그때 한다.
- 단계는 앱 화면도 같은 크기로 찍어야 한다. Runner가 `AWBS_SCREEN_WIDTH=1440`, `AWBS_SCREEN_HEIGHT=900`을 준다.
  - 크기가 다르면 화면 전체가 차이(`diff`, ratio 1)로 기록된다.
- 단계는 화면 이름과 앱 스크린샷만 보고한다(`screens[]`의 `name`·`actual`).
- Runner가 두 PNG를 픽셀 단위로 비교한다.
  - 왜: 단계가 「같다」고 말한 것이 아니라 Runner가 직접 비교한 결과를 근거로 남긴다(G L466).
- 결과는 화면마다 아래 넷 중 하나다.
  - `same`: 같음
  - `diff`: 차이 있음(기록만)
  - `missing`: 기준이 있는데 스크린샷이 없거나 읽을 수 없음(실패)
  - `unchecked`: 정의에 기준이 없는 화면(기록만, note에 「기준 없는 화면 N」)
- 차이가 있어도 실패로 보지 않고 note에 개수를 남긴다.
  - 예: 「화면 비교 9개 중 2개 차이」
  - 근거: 프로토타입 CI-0120은 차이 2개가 있어도 통과다(P L3539).
- 기준이 있는 화면이 보고서에서 빠지거나 이름이 바뀌면 `missing`이고 그 단계는 실패다.
  - 왜: 비교하지 못한 화면을 「차이 없음」으로 보면 안 된다.
- 읽을 수 있는 형식은 8비트 RGB·RGBA, 비interlace PNG다. Playwright 스크린샷 형식이다.

### 주요 API 응답 시간

- 단계 보고서의 `timings`에 API마다 측정값(`samplesMs`)을 보낸다.
- 기준은 main에 고정된 `.agentwbs/pipeline.yaml`의 night 단계 선택 필드 `budgetsMs`에서 읽는다(조정자 결정 3).
  - 왜: 기준을 실행 출력에서 받으면 Agent가 만든 코드가 자기 기준을 느슨하게 바꿀 수 있다. main 정의는 팀장 승인 없이 바꿀 수 없다.

```yaml
  night:
    - name: perf
      argv: [node, measure.mjs]
      budgetsMs:
        GET /api/tasks: 300
        GET /api/wbs: 500
```

- `budgetsMs`는 API 이름 → 기준(ms) 표다.
  - 값은 1 이상 600,000 이하 정수다. 빈 표, 빈 이름은 거부한다.
  - night 단계에만 쓸 수 있다. 다른 단계에 쓰면 정의 전체를 거부한다.
- Runner가 p95(측정값의 95%가 이 값 이하인 값)를 nearest-rank 방식으로 계산한다.
  - nearest-rank는 보간하지 않고 실제로 잰 값 중 하나를 고르는 방식이다.
  - 예: 측정값 1~20ms 20개의 p95는 19ms다.
- 테스트 재시도로 단계를 다시 실행해도 응답 시간은 모든 시도를 합쳐 판정한다(원칙 B).
  - API마다 가장 느린 p95를 남긴다. 어느 시도든 기준을 넘으면 기준 초과이고 그 단계는 실패다.
  - 왜: 재시도는 불안정 시험을 가려내려는 것이다. 느린 것을 다시 재서 우연히 빠르게 나온 값으로 덮지 않는다.
- 기준이 있는 API가 마지막 시도에서 빠지거나 이름이 바뀌면 그 단계는 실패다(원칙 A).
  - 보고서가 없거나, `timings`가 비어 있어도 마찬가지다.
- 기준이 없는 API는 응답 시간을 기록만 하고 통과를 막지 않는다.
  - note 예: 「응답 시간 2개 기록 · 기준 없음 1 · 초과 0」

### 원인 추적

- 실패하면 마지막으로 통과한 야간 점검의 커밋 이후 main에 들어온 커밋을 원인 후보로 남긴다.
  - main의 first-parent(병합 커밋의 첫 번째 부모를 따라간 줄기) 커밋만 센다. PR 하나가 병합 커밋 하나다.
- 원인 후보는 결과 보고의 `causeCandidates: [{ commit }]`로 보낸다(조정자 결정 5, M7-04 14b60db). note에도 짧은 SHA로 적는다.
  - Runner는 커밋만 보낸다. commit을 Task와 잇는 것은 서버가 병합 기록으로 한다.
  - 후보가 없으면 보내지 않는다. 서버는 생략을 「이전 값 보존」으로, `[]`를 「비움」으로 본다. 새 실행이라 보존할 이전 값이 없다.

## 근거와 보존

- 로그 원문과 보고서, 스크린샷은 `<AWBS_HOME>/runs/<실행 ID>/`에 둔다(G L488).
  - 로그는 비밀값을 가린 뒤 `runner/`에 저장한다.
- 서버에는 위치(`runs/<실행 ID>/runner/<파일>`, `runs/<실행 ID>/step/<파일>`)와 요약만 보낸다. DB에는 위치와 요약만 남는다.
- 실행이 끝나면 `runner/run.json`에 끝난 시각을 남긴다.
- `pruneEvidence`가 기본 30일이 지난 실행 폴더를 지운다.
  - 끝난 시각으로 판단한다. `run.json`은 링크를 따라가지 않고 읽는다.
  - `run.json`이 없는 폴더는 진행 중일 수 있어 기본으로 남긴다.
    - 왜: 파일 내용을 고쳐도 부모 폴더의 수정 시각은 바뀌지 않는다. 오래 걸리는 실행의 근거를 지울 수 있다.
    - 진행 중인 실행이 없다고 확인한 호출(예: Runner 시작 때, M7-06)만 `unfinished: 'remove'`로 기간이 지난 미완료 폴더를 지운다.
  - 경계에서 5초 여유를 둔다. 왜: 이 PC는 시계가 몇 초씩 뒤로 간다.
  - 실행 ID 형식이 아닌 폴더, symlink, 끝난 시각이 손상된 폴더는 지우지 않는다.
  - 야간 점검이 끝날 때마다 한 번 정리한다.
- 빌드 결과물은 근거 폴더에 두지 않는다. 필요하면 커밋 해시로 다시 빌드한다(G L485).

## 서버에 보내는 순서

1. `POST /api/runner/ci/runs` — `stage: night`, `trigger: 야간 일정`, `headSha`=`baseSha`=고정한 main
2. `PATCH /api/runner/ci/runs/:id` — `{ fence: null, status: run }`
3. `PATCH /api/runner/ci/runs/:id` — 결과: `status`, `steps`, `e2e`, `flakyTests`, `note`, `logExcerpt`, `artifacts`, `finishedAt`

`apiCiReport`는 시작은 client로 바로 부르고, 갱신은 outbox(보낼 보고를 디스크에 쌓아 두었다가 순서대로 보내는 대기열)로 보낸다.
시작을 바로 부르는 이유는 응답의 실행 ID가 있어야 근거 폴더를 만들 수 있기 때문이다.

실패 알림(「빌드 실패」, 실패 단계 포함)은 서버가 보낸다. ③ 통과는 알리지 않는다(G L516).
