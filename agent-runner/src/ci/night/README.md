# ③ 야간 점검 안내

③ 야간 점검은 매일 정한 시각에 main 브랜치 전체를 다시 확인하는 단계다(G L476).
여기서는 Runner(개발 PC에서 Agent와 검사를 실제로 실행하는 프로그램)가 하는 일을 적는다.
M7-06에서 실제 실행기·API에 연결한다. 지금은 job 처리 흐름이나 서버 판정을 바꾸지 않는다.

## 언제 시작하나

- 정책의 `ci.nightAt`(기본 `02:00`) 시각이 지나면 시작한다.
- 날짜는 Asia/Seoul(한국 시간) 기준이다.
  - 왜: 서버의 날짜 규칙(contracts `LocalDate`)과 같은 날을 가리켜야 한다.
- `dueNight(home, now, nightAt)`가 시작할 날짜를 준다. 아직 아니면 `null`이다.
- Runner가 꺼져 있다가 09시에 켜져도 그날 한 번은 한다.
  - 왜: 꺼져 있었다는 이유로 그날 점검이 빠지면 main이 깨진 것을 하루 늦게 안다.
- 마지막으로 시작한 날짜는 `<AWBS_HOME>/ci/night/state.json`에 남긴다.
- 이미 시작한 날짜보다 이르거나 같은 날짜면 다시 하지 않는다.
  - 왜: 이 PC는 시계가 가끔 뒤로 간다. 시계가 뒤로 가도 같은 날을 두 번 돌리면 안 된다.
- 서버에 보낼 때 멱등 키(같은 요청을 두 번 보내도 한 번만 처리되게 하는 이름표)는 `night:<날짜>`다(contracts §3.2-5).
  - 예: `night:2026-11-27`
  - 시작을 보낸 뒤 Runner가 죽어도, 다시 켜서 같은 키로 보내면 서버가 같은 실행을 돌려준다.

## 무엇을 실행하나

1. main을 고정한다. 기준 커밋(`baseSha`)과 정의 파일 SHA(`pipelineSha`)를 함께 남긴다.
2. job(서버가 Runner에게 시키는 일 하나) 없이 시작한다. 야간 점검은 job이 없는 유일한 실행이다.
   - 그래서 갱신 보고의 `fence`(낡은 Runner의 보고를 막는 번호표)는 항상 `null`이다(contracts §3.2-4).
3. 고정한 커밋을 새 사본에 꺼낸다. Agent 작업 폴더는 쓰지 않는다.
4. 정의의 `task` 첫 단계(`install`)로 설치한 뒤 `night` 단계를 순서대로 실행한다.
5. 실행이 끝나면 사본을 지운다.

## 단계가 남기는 보고서

각 단계 명령에는 환경 변수 두 개를 준다.

- `AWBS_REPORT`: 단계가 결과를 JSON으로 쓸 파일 경로
- `AWBS_EVIDENCE_DIR`: 스크린샷 같은 근거 파일을 둘 폴더

보고서는 없어도 된다. 없으면 종료 코드만으로 판정한다.
보고서에 쓸 수 있는 항목은 아래 넷이다. 다른 항목이 있으면 형식 오류로 실패 처리한다.

```json
{
  "tests": [{ "key": "wbs-tree.spec.ts › 접힘 상태 유지", "status": "fail" }],
  "screens": [{ "name": "wbs", "actual": "shots/wbs.png", "expected": "shots/wbs.proto.png" }],
  "timings": [{ "name": "GET /api/tasks", "samplesMs": [120, 140, 400], "budgetMs": 300 }],
  "screenshots": ["shots/login.png"]
}
```

- 파일 경로는 모두 `AWBS_EVIDENCE_DIR` 기준 상대 경로다.
- 근거 폴더 밖을 가리키면(symlink 포함) 그 파일을 읽지 않는다.
  - 왜: 단계가 다른 파일(비밀값 등)을 근거인 척 올리지 못하게 한다.

## 판정 규칙

### 전체 E2E와 불안정 테스트

- E2E(End-to-End, 사용자가 쓰는 것처럼 화면부터 서버까지 한 번에 확인하는 시험)는 `tests` 결과로 판정한다.
- 실패한 단계는 정책의 `ci.retry`(기본 1)번 더 실행한다(G L482).
  - 설치 단계는 재시도하지 않는다. 재시도는 실패 테스트를 위한 것이다.
- 앞 시도에서 실패했는데 마지막 시도에서 통과한 테스트는 「불안정 후보」다.
  - 불안정 후보는 통과를 막지 않는다.
- 재시도에 다시 나오지 않은 실패 테스트는 실패로 둔다.
  - 왜: 사라진 테스트를 통과로 보면 실패를 숨길 수 있다.
- 격리된 테스트가 실패하면 결과는 남기되 통과를 막지 않는다.
  - 격리를 해제하면 다음 실행부터 다시 판정에 들어간다.
- 종료 코드가 실패인데 실패 테스트가 하나도 없으면 실패다. 격리로 덮지 않는다.
  - 왜: 테스트가 아닌 다른 이유(설정 오류 등)로 깨진 것까지 격리가 숨기면 안 된다.
- 종료 코드가 0이어도 격리하지 않은 실패 테스트가 보고서에 있으면 실패다.

### 불안정 테스트 보고

- 불안정 후보와 격리 실패는 `flakyTests`로 보낸다.
  - `rate`: 최근 20번 야간 점검 중 그 테스트가 한 번이라도 실패한 비율이다. 화면의 「2 / 20 실패」와 같은 뜻이다.
  - `lastFailedAt`: 이번 실행이 끝난 시각이다.
- 담당 Task는 보내지 않는다.
  - 왜: 야간 점검은 Task가 없는 실행이다. 서버는 이미 정해진 담당 Task를 지우지 않고 그대로 둔다(M7-04).
- 최근 결과 기록은 `state.json`에 함께 남는다.

### 화면 비교

- 앱 화면 스크린샷과 `prototype/uiux/`를 띄운 화면 스크린샷을 짝지어(`screens`) 보낸다.
- Runner가 두 PNG를 픽셀 단위로 비교한다.
  - 왜: 단계가 「같다」고 말한 것이 아니라 Runner가 직접 비교한 결과를 근거로 남긴다(G L466).
- 결과는 화면마다 `same`(같음), `diff`(차이 있음), `missing`(비교 못 함) 중 하나다.
- 차이가 있어도 실패로 보지 않고 note에 개수를 남긴다.
  - 예: 「화면 비교 9개 중 2개 차이」
  - 근거: 프로토타입 CI-0120은 차이 2개가 있어도 통과다(P L3539).
- 파일이 없거나 PNG가 아니면 `missing`이고 그 단계는 실패다.
  - 왜: 비교하지 못한 화면을 「차이 없음」으로 보면 안 된다.
- 읽을 수 있는 형식은 8비트 RGB·RGBA, 비interlace PNG다. Playwright 스크린샷 형식이다.

### 주요 API 응답 시간

- `timings`에 API마다 측정값(`samplesMs`)과 기준(`budgetMs`)을 보낸다.
- Runner가 p95(측정값의 95%가 이 값 이하인 값)를 nearest-rank 방식으로 계산한다.
  - nearest-rank는 보간하지 않고 실제로 잰 값 중 하나를 고르는 방식이다.
  - 예: 측정값 1~20ms 20개의 p95는 19ms다.
- p95가 기준보다 크면 그 단계는 실패다. 응답 시간 초과는 재시도하지 않는다.
  - 왜: 느린 것을 다시 재서 우연히 빠르게 나온 값으로 덮지 않는다.

### 원인 추적

- 실패하면 마지막으로 통과한 야간 점검의 커밋 이후 main에 들어온 커밋을 원인 후보로 남긴다.
  - main의 first-parent(병합 커밋의 첫 번째 부모를 따라간 줄기) 커밋만 센다. PR 하나가 병합 커밋 하나다.
- 원인 후보는 note에 짧은 SHA로 적는다. 이를 Task와 잇는 것은 서버 몫이다.

## 근거와 보존

- 로그 원문과 보고서, 스크린샷은 `<AWBS_HOME>/runs/<실행 ID>/`에 둔다(G L488).
  - 로그는 비밀값을 가린 뒤 저장한다.
- 서버에는 위치(`runs/<실행 ID>/<파일>`)와 요약만 보낸다. DB에는 위치와 요약만 남는다.
- 실행이 끝나면 `run.json`에 끝난 시각을 남긴다.
- `pruneEvidence`가 기본 30일이 지난 실행 폴더를 지운다.
  - 끝난 시각으로 판단하고, `run.json`이 없으면(중간에 죽은 실행) 폴더 수정 시각을 쓴다.
  - 경계에서 5초 여유를 둔다. 왜: 이 PC는 시계가 몇 초씩 뒤로 간다.
  - 실행 ID 형식이 아닌 폴더, symlink, 끝난 시각이 손상된 폴더는 지우지 않는다.
  - 야간 점검이 끝날 때마다 한 번 정리한다.
- 빌드 결과물은 근거 폴더에 두지 않는다. 필요하면 커밋 해시로 다시 빌드한다(G L485).

## 서버에 보내는 순서

1. `POST /api/runner/ci/runs` — `stage: night`, `trigger: 야간 일정`, `headSha`=`baseSha`=고정한 main
2. `PATCH /api/runner/ci/runs/:id` — `{ fence: null, status: run }`
3. `PATCH /api/runner/ci/runs/:id` — 결과: `status`, `steps`, `e2e`, `flakyTests`, `note`, `logExcerpt`, `artifacts`, `finishedAt`

`apiCiReport`는 시작은 client로 바로 부르고, 갱신은 outbox(보낼 보고를 디스크에 쌓아 두었다가 순서대로 보내는 대기열)로 보낸다.
시작을 바로 부르는 이유는 응답의 실행 ID가 있어야 근거 폴더를 만들 수 있기 때문이다.

실패 알림(「빌드 실패」, 실패 단계 포함)은 서버가 보낸다. ③ 통과는 알리지 않는다(G L516).
