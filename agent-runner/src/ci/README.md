# ① Task 검사 연결 안내

CI(Continuous Integration, 코드를 자동으로 빌드하고 검사하는 과정)의 ① 경로는 `runTaskCheck`다.
M7-06에서 기존 자리표시 대신 호출한다.
서버의 Gate(완료 전에 통과해야 하는 조건 묶음)는 저장된 실제 검사 결과를 대조한다.

## 실제 통합 작업 연결

`CiJobs`는 `integrate`와 `ci_retry` 작업을 서버에서 받아 처리한다.
Runner 앱은 실행 준비와 가용 자원을 확인한 뒤 이 실행기를 호출한다.
`ci` 의존성에는 기존 Git 저장소와 검사 명령 실행기, 테스트 목록 수집기를 전달한다.
실행기는 각 명령의 프로세스를 등록하고 종료 증거와 슬롯 반환을 보고해야 한다.
검사 함수가 이미 heavy(무거운 검사 동시 실행을 제한하는 번호표)를 보유한다.
따라서 M5-05의 `Execution.command`를 연결할 때는 `{ heavyHeld:true }`를 전달한다.
왜: 같은 번호표를 중복으로 기다리면 검사가 멈출 수 있다.
Q-08의 실행 환경 결정 전에는 이 경계를 fake 실행기로 검증한다.

작업과 보고 순서는 `ci-job.json`에 보관한다.
병합 전후 GitHub 관측은 기존 병합 journal(재시작 뒤 대조할 기록)을 사용한다.
서버 보고는 기존 outbox를 함께 사용한다.
왜: 응답이 끊겨도 같은 멱등 키로 보고를 복구하고 병합 명령을 중복 실행하지 않기 위해서다.
`GATE_UNMET_AFTER_MERGE` 응답은 서버가 실제 병합을 저장했다는 뜻이다.
Runner는 병합을 다시 시도하지 않고 서버의 Gate 재평가를 기다린다.

## 정의 형식

YAML(사람이 읽기 쉬운 설정 파일 형식)의 `version`은 `1`이다.
`stages`에는 `task`, `int`, `night`, `deploy` 네 목록을 넣는다.
각 목록의 단계에는 `name`과 `argv`만 넣는다.
argv는 실행 파일과 인자를 따로 담은 문자열 배열이다.
왜: shell(명령 문자열을 해석하는 프로그램)로 문자열을 조합하면 인자가 새 명령으로 바뀔 수 있다.

①의 `name`은 아래 여섯 개를 이 순서로 모두 적는다.
보호 경로 검사는 Runner가 그보다 먼저 실행한다.
왜: 정의에서 필수 검사를 빼거나 보호 경로 검사를 우회하지 못하게 한다.

```yaml
version: 1
stages:
  task:
    - name: install
      argv: [pnpm, install, --frozen-lockfile]
    - name: typecheck
      argv: [pnpm, typecheck]
    - name: lint
      argv: [pnpm, lint]
    - name: unit
      argv: [pnpm, test]
    - name: build
      argv: [pnpm, build]
    - name: contract
      argv: [pnpm, test:contract]
  int:
    - name: integration
      argv: [node, fake-integration.mjs]
  night:
    - name: nightly
      argv: [node, fake-nightly.mjs]
  deploy:
    - name: health
      argv: [node, fake-health.mjs]
```

위 코드는 형식 예시다.
②③④의 명령은 fake(실제 실행 대신 쓰는 가짜) 이름이다.
운영 기본값으로 설치하지 않는다.
②③④ 목록은 비어 있으면 안 되며 이름이 목록 안에서 겹치면 안 된다.
구체적인 명령과 대상은 각 후속 마일스톤에서 정한다.

알 수 없는 필드, 다른 버전, 빈 명령, 중복 YAML 키, 별칭, 알 수 없는 태그, 여러 문서는 거부한다.
정의 크기가 256 KiB(262,144 바이트)를 넘으면 거부한다.
왜: 잘못 적은 설정을 일부만 받아 실행하지 않도록 한다.
별칭은 다른 값을 이름으로 재사용하는 YAML 문법이다.
이 형식에는 필요하지 않아 허용하지 않는다.

## 실행과 근거

`GitRepository.mainPipeline()`이 등록된 원격의 main을 가져온다.
필요한 `refs/heads/main`만 가져온다.
왜: 다른 작업자의 브랜치 이력 재작성이 ①을 막아서는 안 된다.
그 커밋의 `.agentwbs/pipeline.yaml`을 Git 객체에서 읽는다.
SHA(파일이나 커밋 내용을 구별하는 해시 값)는 두 가지를 구분해 반환한다.
`baseSha`는 고정한 main 커밋이다.
`pipelineSha`는 그 커밋에 있는 정의 파일의 blob(파일 내용 객체) SHA다.
왜: 실행 중 main이 바뀌어도 어떤 정의로 검사했는지 다시 확인할 수 있어야 한다.

검사 전 Agent의 결과 커밋을 Runner 저장소에 가져와 `headSha`로 고정한다.
보호 경로와 빌드 결과물 검사는 기존 `GitRepository.checkTask`를 쓴다.
두 커밋의 merge-base(브랜치가 갈라진 공통 조상)부터 비교한다.
Agent 폴더에 미커밋 변경이 있으면 `failStep: worktree`인 실패 결과를 반환한다.
Agent index(다음 커밋에 넣을 파일 목록)의 숨김 설정은 믿지 않는다.
Runner가 만든 임시 index로 직접 대조한다.

실제 검사는 Agent 작업 폴더에서 실행하지 않는다.
Runner가 소유한 Git 객체에서 검사할 SHA만 새 폴더에 복사한다.
변경 전 기준인 merge-base와 변경 후 `headSha`를 각각 따로 복사한다.
이 폴더에는 Agent의 무시 파일, `node_modules`, Git 설정이 들어가지 않는다.
커밋에 `node_modules`, symlink(다른 파일을 가리키는 링크), submodule(다른 저장소의 연결)이 있으면 거부한다.
왜: Agent가 남긴 가짜 실행 도구나 바깥 파일로 테스트 결과를 조작하지 못하게 한다.
각 사본은 main에서 고정한 `install` 명령으로 먼저 설치한다.
기준 SHA와 `headSha`가 같으면 사본과 설치를 한 번만 사용한다.
이 경우 대상의 `install` 단계는 `skip`이다.
SHA가 다르면 각 사본의 lockfile로 따로 설치한다.
왜: 다른 커밋의 의존성을 섞으면 전후 수집 결과를 믿을 수 없다.
이 명령은 프로젝트의 lockfile(설치할 의존성 버전을 고정한 파일)을 지켜야 한다.
pnpm은 예시의 `--frozen-lockfile`을 사용한다.
검사 도중에도 각 명령 앞뒤에서 사본의 추적 파일을 원래 SHA와 대조한다.
설치·빌드로 생긴 무시 대상 파일은 이 새 사본 안에서만 사용한다.
검사가 성공하거나 실패하면 사본과 생성 기록을 지운다.
Agent 작업 폴더는 지우거나 고치지 않는다.
왜: 결과물과 실행 도구가 검사한 커밋에서 시작했다는 것을 보장하면서 Agent의 작업을 보존해야 한다.

정상적인 symlink도 현재 ①에서 거부한다.
저장소 안을 가리키는 상대 링크도 예외로 두지 않는다.
왜: 링크를 따라가면 고정한 커밋 밖의 파일이나 실행 도중 바뀐 목표 파일을 읽을 수 있다.
현재는 링크 연결 전체와 실행 중 목표 변경까지 확인하는 격리 검증을 제공하지 않는다.
Q-08에서 이 경계를 확인하기 전에는 일반 파일만 검사 사본에 넣는다.
기준 커밋에 정상 링크가 있어도 검사는 진행할 수 없다.
이 경우 Agent에게 재작업을 요청하지 않고 아래의 기준 실패로 기록한다.
링크 허용 정책은 이 변경에서 추가하지 않았다.

공유 `HeavySemaphore`의 번호표를 받은 뒤 명령을 실행한다.
①도 Agent와 같은 무거운 작업 상한을 지켜야 하기 때문이다.
`unit`과 `contract`의 테스트 실패는 한 번만 재시도한다.
재시도에서만 통과하면 `flakyCandidates`에 불안정 후보 이름을 남긴다.
실행 오류와 중단은 테스트 실패로 재시도하지 않는다.
실패한 단계 다음의 명령은 실행하지 않는다.
결과에는 단계별 종료 코드, 출력, 소요 시간과 `failStep`을 남긴다.
실패 결과에는 선택 필드 `failScope`도 넣는다.
`baseline-install`과 `test-collection-before`의 실패는 `baseline`이다.
나머지 검사 실패는 `task`다.
성공 결과에는 이 필드가 없다.
`status`와 기존 필드·함수 인자는 그대로 유지한다.
왜: 기준 커밋에서 이미 생긴 문제는 해당 Task의 Agent가 고칠 수 없기 때문이다.
M7-02·M7-04·M7-06 연결부는 `failScope: baseline`을 기준 실패 경보로 처리해야 한다.
Task 실패 횟수를 올리거나 같은 시도의 Agent 재작업으로 보내면 안 된다.
이 결과는 통과가 아니므로 Gate의 통과 근거로도 쓰지 않는다.
명령 뒤 사본 대조가 실패해도 이미 받은 stdout(표준 출력)과 stderr(오류 출력)를 보존한다.
출력과 변경 근거는 기존 비밀값 가리기 함수를 적용한다.
호출자는 `redact`에 자신이 알고 있는 비밀값을 추가할 수 있다.

Q-08의 격리 방식이 정해지기 전에는 `execute`와 `collectTests`에 fake만 전달한다.
기본 실행기는 제공하지 않는다.
실제 실행기를 연결하는 쪽은 자격 증명 격리, 프로세스 그룹 등록, 슬롯 획득, 중단과 자손 종료 확인을 맡는다.
두 함수는 프로세스가 모두 끝난 뒤 반환해야 한다.
왜: ①도 Agent와 같은 자격 증명 경계를 지켜야 하고 살아 있는 자손의 번호표를 반납하면 안 된다.

Runner 시작에서는 홈 잠금을 얻은 뒤 남은 검사 사본을 한 번 정리한다.
생성 기록의 `ci-<uuid>` 이름과 `agent/ci-<uuid>` 브랜치가 맞는 사본만 대상으로 삼는다.
uuid는 사본 이름에 붙인 무작위 고유 번호다.
기존 `removeWorktree`로 폴더·생성 기록과 여전히 시작 커밋을 가리키는 브랜치를 정리한다.
기록이 없는 폴더나 다른 Task의 브랜치는 보존한다.
왜: 강제 종료로 남은 검사 사본을 회수하면서 사용자 작업을 잘못 지우지 않아야 한다.
일반 `GitRepository.open`과 시작 후 반복 호출에서는 이 정리를 하지 않는다.
정리가 실패하면 새 작업을 시작하지 않고 오류를 보고한다.
실제 실행기를 연결할 때는 재시작 후 살아 있는 자손 프로세스의 종료 확인도 먼저 연결해야 한다.
현재 Q-08 이전 경로는 fake만 실행한다.

## 테스트 삭제와 QA

QA(Quality Assurance, 수용 기준을 검증하는 Agent)의 확인 묶음으로 `result.testReview`를 넘긴다.
이 묶음은 `baseSha`와 `headSha`, 변경 전후 blob SHA, 변경 경로, diff(변경 전후 비교문)를 담는다.
diff는 경로를 글자 그대로 지정한다.
왜: `[id].test.ts`의 대괄호를 패턴으로 해석하면 다른 파일의 변경이 섞일 수 있다.
비밀값 가리기를 거친 diff는 원문과 일부 다를 수 있다.
원문을 확인할 때는 기록한 blob SHA를 사용한다.
테스트 삭제는 자동 실패로 만들지 않는다.
건너뛰기 추가나 단언 제거는 기존 파일의 수정 근거로 남는다.
이름 변경도 이전 파일의 삭제 근거로 남는다.
왜: G L480과 coordinator의 확인에 따라 삭제·약화의 타당성은 검증 Agent가 명시적으로 판단해야 한다.

테스트 파일 이름은 프로젝트마다 다르다.
따라서 파일의 추가·삭제·수정은 모두 확인 후보에 포함한다.
일반 소스 수정도 들어갈 수 있다.
왜: 이름 규칙만 보고 찾으면 독자적인 이름의 테스트나 바이너리 근거가 빠질 수 있다.
새 설정 파일 하나로 기존 테스트를 제외할 수 있으므로 추가 파일도 빠뜨리면 안 된다.

`collectTests`는 반드시 제공해야 하는 테스트 수집 함수다.
main에서 고정한 `unit`과 `contract` 명령의 argv와 설치된 사본 경로를 받는다.
실제 테스트 실행기가 그 사본에서 수집한 테스트 식별자 목록을 반환해야 한다.
식별자는 사본 루트의 상대 파일 경로와 테스트 이름으로 만든다.
왜: 매번 다른 임시 절대 경로를 넣으면 같은 테스트도 다른 것으로 보인다.
이 함수는 각 프로젝트 테스트 실행기에 맞게 연결한다.
Git 파일 이름이나 테스트 개수로 목록을 대신 만들면 안 된다.
빈 문자열·중복 식별자·수집 실패는 해당 수집 단계의 실패로 처리한다.

수집은 변경 전·후 사본의 lockfile 설치가 끝난 뒤 각각 수행한다.
`testReview.collection`에 `baselineSha`, `before`, `after`, `removed`, `added`를 담는다.
`baselineSha`는 merge-base 커밋이다.
각 식별자 앞에는 `unit:` 또는 `contract:`를 붙여 구분한다.
테스트가 사라졌으면 기존 파일 변경이 없어도 `testReview.required`를 켠다.
왜: 설정 파일을 추가해 테스트를 제외하는 경우도 QA가 명시적으로 확인해야 한다.
단언 제거처럼 식별자가 그대로인 약화는 파일 diff와 함께 검증한다.

`testReview.required`가 참이면 기계 검사 `pass`만으로 Gate 근거로 삼으면 안 된다.
M7-06 연결부는 이 묶음을 QA 작업에 전달해야 한다.
같은 SHA의 목록을 검증 Agent가 명시적으로 확인한 기록도 서버에 남겨야 한다.
확인 기록이 없거나 검사 대상 SHA가 바뀌면 Gate에서 받아들이면 안 된다.
이 모듈은 QA 확인 여부를 대신 판정하거나 서버 기록을 만들어 내지 않는다.
API(프로그램 사이 통신 규칙) 보고와 영속 보관은 M7-06에서 기존 client·outbox(재전송할 보고를 보관하는 대기열)로 연결한다.
왜: M7-01은 실제 ① 경로를 준비하고 자리표시 제거는 M7-06이 맡는다.

## 검증

`pnpm -C agent-runner test -- ci-task`로 검사한다.
외부 서비스 대신 로컬 Git 저장소와 fake 명령을 쓴다.
근거 보관 폴더 아래에 `TMPDIR`을 지정하면 임시 시험 저장소도 그 폴더에 만든 뒤 삭제한다.
