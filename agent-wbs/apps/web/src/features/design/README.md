# M6-07 — 설계 화면 6탭 · Task 연결

이 문서는 M6-07에서 만든 「설계」 메뉴 화면(UI-04)의 사용 설명이다.
원본 `prototype/uiux/Main.dc.html`의 P L1483–1610(화면)과 P L4813–4936(동작)을 옮겼다.
서버는 M6-05 설계 원장(`apps/api/src/design`)이고, 계약은 `packages/shared/src/api/routes/project.ts`의 설계 API다.

- 처음이라면 [apps/web/README.md](../../../README.md) → [src/shared/README.md](../../shared/README.md) → 이 문서 순서로 읽는다.
- 낯선 말은 맨 아래 [용어집](#용어집)에 있다.

## 1. 한눈에 보기

| 주소 | 보이는 것 |
|---|---|
| `/design` | 구성도 · 계약 파일 탭 |
| `/design?tab=dec` | 기술 결정 탭 |
| `/design?tab=iface&kind=REST` | 인터페이스 목록(방식 필터) |
| `/design?tab=iface&sel=PATCH+%2Fapi%2Ftasks%2F%3AtaskKey` | 왼쪽 레일 + 그 인터페이스 상세 |
| `/design?tab=data&store=postgres&sel=postgres%3Atasks` | 왼쪽 레일 + 그 테이블 상세 |
| `/design?tab=own` | 소유권 · 흐름 탭 |
| `/design?tab=chg` | 변경 · 불일치 탭과 설계 버전 |

- 탭·필터·검색어(`q`)·선택(`sel`)을 모두 주소에 둔다.
  - 왜: 새로고침·뒤로 가기·Task 상세의 링크로 같은 화면이 열려야 한다.
- 주소는 `shared/links.ts`의 `LINK.design(tab, key)`로만 만든다.
  - 예: `LINK.design('data', 'postgres:tasks')` → `/design?tab=data&store=postgres&sel=postgres%3Atasks`.
- `sel`은 설계 항목의 **고정 키(item key)**다(G L1056).
  - REST는 `METHOD path`(예: `PATCH /api/tasks/:taskKey`), 테이블은 `저장소:이름`(예: `postgres:tasks`)이다.
  - 왜: 서버의 Task 연결·불일치·충돌 묶음이 모두 이 키를 쓴다. 화면도 같은 키를 써야 서로 가리킬 수 있다.

## 3. 데이터 — 어떤 API를 부르나

모든 요청과 응답 모양은 계약 타입(`@awbs/shared/api`)에서 뽑아 쓴다. 모두 main 기준(`ref` 없음)이다.

| 요청 | 쓰는 곳 | 변경 이벤트 topic |
|---|---|---|
| `GET /api/projects/:projectId/design` | 요약 줄(버전)·구성도·연결·계약 파일·설계 버전 | design |
| `GET …/design/decisions` | 기술 결정 탭, 구성도의 결정 상태 | design |
| `GET …/design/interfaces`, `GET …/design/data` | 탭 건수·목록 | design·task |
| `GET …/design/interfaces/:key`, `GET …/design/data/:key` | 항목 상세 | design |
| `GET …/design/ownership` | 소유권 · 흐름 탭 | design |
| `GET …/design/drifts` | 불일치 건수·탭·항목 표시 | design |
| `GET /api/projects/:projectId/tasks` | 항목 상태(담당 Task 상태로 계산) | task |
| `POST /api/design/decisions/:id/approve·reject·change` | 승인·반려·변경 제안 | — |
| `POST …/design/drifts/:id/resolve` | 계약에 반영·코드 수정 요청 | — |

- 항목 상태(계획·구현 중 · 브랜치·구현됨·검증됨·폐기)는 **담당 Task 상태로 계산**한다(G L452, 원본 `Sel.dsStat`).
  - 왜: 서버 목록의 `status`는 계약 파일 읽기 상태(ok·draft·error)라 뜻이 다르다. 읽기 실패면 상태 옆에 「읽기 실패」를 덧붙인다.

## 4. 규칙과 이유

### 4.1 「대조 안 함」은 불일치 0건이 아니다

- 서버는 코드에서 명세를 추출하지 못한 항목을 `compat: 'unchecked'` 불일치로 남긴다. 파일 단위면 키가 `file:<경로>`다.
- 화면은 이것을 **「대조 안 함」**(노란 배지)으로 보인다. 「호환」(초록)이나 「해결됨」으로 보이지 않는다.
  - 왜: 대조하지 못한 것을 「불일치 없음」처럼 보이면 팀장이 확인된 것으로 착각한다(G L1058).
- 요약 줄은 「불일치 N」과 「대조 안 함 M」을 따로 센다. 탭 배지는 둘을 합친 열린 건수다.
  - 예: 대조 안 함만 1건이면 요약 줄 끝이 「· 대조 안 함 1」, 탭은 「변경 · 불일치 1」이다.
- 「대조 안 함」에는 「계약에 반영」 버튼이 없다. 서버가 거부하기 때문이다(409 INVALID_TRANSITION). 담당 Task가 있으면 「코드 수정 요청」은 할 수 있다.
- 계약 파일 표에서도 추출하지 못한 파일 옆에 「대조 안 함」을 붙인다.

### 4.2 계약에 반영 — 결과 커밋 전에는 해결이 아니다

- 「계약에 반영」은 서버가 Runner 작업(design_apply job)만 만들고 202 `{ jobId }`를 돌려준다.
- 화면은 그 불일치를 **「계약 반영 대기」**로 보이고 「해결됨」으로 바꾸지 않는다.
  - 왜: Runner가 결과 커밋을 보고하고 대조가 일치해야 실제로 반영된 것이다(contracts §2.3, UAT-DESIGN-04 a).
  - 원본(P dsDrift L4831)은 누르자마자 해결로 바꿨다. 조정자가 계획(결과 커밋 뒤 해결)을 따르도록 승인했다.
- 서버가 job 상태(`resolution.jobStatus`, M6-05 fix1)를 준다. 화면은 상태별로 보인다.
  - queued: 「계약 반영 대기」, running: 「계약 반영 중」 — 버튼이 없다. 왜: 같은 계약 수정이 겹쳐 실행되면 안 된다.
  - done인데 아직 열림: 「결과 대조 대기」 — 결과 커밋의 대조가 일치해야 해결된다. 「계약 반영 다시 요청」과 「코드 수정 요청」을 열어 둔다.
  - failed: 「계약 반영 실패」(빨강) — 「계약 반영 다시 요청」과 「코드 수정 요청」.
  - 상태가 없는 옛 기록은 「계약 반영 대기」로 보이고 다시 요청은 서버가 판단한다.
- 해결되면 「처리: 계약에 반영 — 결과 커밋 abcdef1」처럼 결과 커밋을 보인다.

### 4.3 호환을 깨는 차이는 승인된 결정 ID가 필요하다

- 호환 깨짐(breaking: 필드 삭제·타입 변경·필수화)의 「계약에 반영」은 바로 보내지 않고 창을 연다.
- 창에서 **이 불일치에 연결된 승인 결정**만 고를 수 있다. 같은 itemKey와 같은 driftId를 가리키고 승인됨(approved)인 결정이다(coord-decisions 2). 고른 결정의 id가 `decisionId`로 간다.
  - 왜: 다른 항목이나 같은 항목의 옛 불일치에 대한 승인을 재사용하면 팀장이 승인하지 않은 변경이 반영된다. 서버도 거부한다.
- 연결된 승인 결정이 없으면 「이 불일치(DR-01)에 연결된 승인 결정이 없습니다」 안내와 「기술 결정 보기」만 있다.
  - 연결된 승인 대기 결정이 있으면 그 TD 번호를 보이고 승인하라고 안내한다.
  - 없으면 만드는 길 두 가지를 안내한다. Agent가 이 불일치에 연결한 결정을 제안하거나, 팀장이 기술 결정 탭의 「변경 제안」 창에서 「연결할 불일치」를 골라 올린 뒤 승인한다(연결은 승인할 때 결정에 붙는다).
- 기술 결정 행에는 연결이 있으면 「연결 PATCH /api/tasks/:taskKey · DR-01」을 보인다.
- 다른 방법은 「코드 수정 요청」이다. 서버가 담당 Task에 실제 메시지(수정 요청)를 만들고 바로 해결로 기록한다.

### 4.4 기술 결정 — 승인 전에는 기존 결정이 기준

- 승인 대기(pending)와 변경 제안(change)에만 「승인」「반려」가 있다.
- 「변경 제안」 버튼은 확정·승인된 Agent 제안과 팀장 지정 조건부 선호에만 있다(원본 canChg).
  - 팀장 지정 필수·금지, Agent 재량 기록은 바꿀 수 없다. 서버도 409로 거부한다.
- 변경 제안을 올려도 결정의 선택(choice)은 그대로다. 행에 「변경 제안 기존 → 새 선택 — 이유」를 덧붙인다.
  - 승인하면 새 선택이 되고 설계 버전이 오른다. 반려하면 원래 상태(확정·승인됨)로 돌아간다.
- 변경 제안 창의 입력은 세션이 끊겨도 보관했다가 복원을 제안한다(useSessionDraft). 입력 중에 탭·메뉴를 옮기면 먼저 묻는다(useEditGuard).

### 4.5 저장은 공통 규칙(useSave)을 따른다

- 승인·반려·변경 제안·불일치 처리는 모두 `useSave`를 쓴다.
  - 누른 순간의 `updatedAt`을 찍어 보내고, 멱등 키(Idempotency-Key)를 붙인다.
  - 응답을 잃으면(500·네트워크·10초·503) 같은 내용·같은 키로 「다시 시도」한다. 왜: 서버가 이미 처리했을 수 있다.
  - 409 VERSION_CONFLICT면 충돌 창이 뜨고, 「최신 내용 불러오기」는 서버에서 결정·불일치·요약을 새로 읽는다.
  - 그 밖의 409(INVALID_TRANSITION 등)는 오류 막대로 알리고 최신을 다시 읽는다.

### 4.6 계약 파일 읽기 실패

- 서버가 파일 읽기 실패를 보고하면 빨간 배너에 경로·원인·마지막 성공 버전(커밋 앞 7자리)을 보인다.
- 「다시 읽기」는 서버의 최신 해석 결과를 다시 읽는다. 서버가 아직 실패면 배너는 남는다.
  - 왜: 실제 재해석은 Runner가 한다. 서버가 성공을 기록한 뒤에만 해제한다(UAT-DESIGN-01 a). 원본의 「다시 읽기 (Mock: 수정됨)」처럼 화면이 지우지 않는다.

### 4.7 빈 상태

- 기술 결정과 계약 파일이 모두 없으면 탭 없이 「아직 확정된 기술 결정이 없습니다.」 안내만 보인다.
- 목록이 비었을 때 두 경우를 구분한다(UAT-EMPTY-09).
  - 정의가 없음: 「아직 인터페이스 계약이 없습니다. 계약 설계 Task가 …」처럼 생기는 조건을 안내한다.
  - 조건에 맞는 것이 없음: 「조건에 맞는 인터페이스가 없습니다.」와 「필터 초기화」. 초기화는 검색어와 방식·저장소 필터를 모두 지운다.

### 4.8 브랜치 조회(ref)

- 「계약 파일」 카드 머리의 「기준」에서 main(확정 설계)이나 진행 중 Task의 브랜치(`agent/TASK-0005`) 초안을 고른다. 주소는 `?ref=agent%2FTASK-0005`다.
- ref는 main 또는 `agent/TASK-0000`(권한 세대 접미사 `-hN` 포함)만 받는다(M6-05 `DESIGN_REF_PATTERN`). 형식이 틀린 값(예: `refs/heads/main`)은 서버에 보내지 않고 main을 보이며 경고한다.
  - 왜: 브랜치의 진행 중 자료가 확정 설계와 섞이면 안 된다. 서버 보고 규칙과 같은 이름 규칙을 쓴다.
- 브랜치를 보는 동안 모든 설계 조회(요약·목록·상세·소유권·불일치)에 같은 ref를 붙이고, 탭을 옮겨도 ref를 유지한다. 위에 파란 안내와 「main 보기」가 있다.
- 브랜치 불일치에는 처리 버튼이 없다. main 병합 뒤 대조 결과에서 처리한다(서버도 브랜치 resolve를 막는다).
- 고를 수 있는 브랜치는 진행 중 Task의 기본 이름(`agent/<Task>`)이다. 세대 접미사가 붙은 브랜치는 브랜치 목록 API가 없어 주소로만 연다(보고함).

## 5. 원본·계획과 다른 점(보고한 것)

- 설명·불일치 표시 번호(DR-01)·메시지의 기술 결정(TD-07)·반영 job 상태는 M6-05 fix1이 계약에 더해 이제 보인다.
- 목록 순서는 원본처럼 담당 Task 순이다(인터페이스 탭에서는 REST와 메시지 인터페이스가 Task 순으로 섞인다. 원본은 REST 다음 메시지). 같은 Task 안은 항목 key 순이고(원본은 Task 설계에 적은 순서), 담당 Task가 없는 항목은 맨 뒤다(조정자 결정).
  - 왜: 서버는 key 순으로 주지만 팀장은 Task 단위로 설계를 본다. 이전·다음 이동도 이 순서다.
- 원본의 Mock 버튼(「Mock: 읽기 실패」, 「변경 제안 (Mock)」)과 「Prototype Mock — …」 문구는 없다. 변경 제안은 실제 API로 올린다.
- 원본의 저장소별 안내 문구(QuestDB TD-03 등)는 Mock 데이터에 묶여 있어 일반 문구로 바꿨다.
- 계약 반영 직후 「해결됨」 대신 「계약 반영 대기」(§4.2).

## 용어집

| 용어 | 뜻 |
|---|---|
| 계약 파일 | 저장소 main의 `contracts/` 아래 API·스키마 정의 파일. 설계의 기준(정본) |
| 설계 원장 | 서버가 계약 파일을 읽어 커밋 기준으로 저장해 둔 것. 화면은 이것을 보여 준다 |
| 고정 키(item key) | 설계 항목 이름표. REST는 `METHOD path`, 테이블은 `저장소:이름` |
| 불일치(drift) | 계약 파일과 실제 코드에서 추출한 명세가 다른 것 |
| 호환 / 호환 깨짐 | 기존 사용자를 깨지 않는 변경 / 필드 삭제·타입 변경·필수화처럼 깨는 변경 |
| 대조 안 함(unchecked) | 코드에서 명세를 추출하지 못해 비교하지 않은 상태. 불일치 0건이 아니다 |
| job | 서버가 Runner에게 맡기는 작업 한 건. 계약 반영은 design_apply job이다 |
| 결과 커밋 | Runner가 계약 반영 작업을 끝내고 만든 커밋. 이것이 보고돼야 해결된다 |
| 멱등 키(Idempotency-Key) | 같은 요청을 다시 보내도 한 번만 처리되게 붙이는 번호표 |
| 레일 | 상세를 볼 때 왼쪽에 좁게 남는 목록 |
