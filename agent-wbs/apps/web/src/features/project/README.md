# features/project — 프로젝트 메뉴(M3-04)

프로젝트 메뉴(`/project`) 화면 묶음이다.
가이드 G§4.2의 세 흐름(① 등록·초기 분석, ② 입력 자료 변경, ③ 초기화)과 기술 결정 확정을 다룬다.
공통 부품 사용법은 [../../shared/README.md](../../shared/README.md)에 있다. 낯선 말은 맨 아래 [용어집](#용어집)에 있다.

  - 왜 `state` 값으로 고르지 않나: 계약의 열거값이 TypeScript에서 `string | number`라 타입이 좁혀지지 않는다(shared/README §8).

## 2. 지킨 규칙과 이유

- **저장(변경 요청)은 모두 `useSave`를 쓴다.**
  - 등록·저장소 확인·기술 결정 확정·승인·재분석·다시 시도·분석·분석 안 함·recheck·초기화가 모두 해당한다.
  - 왜: 멱등 키(같은 요청을 두 번 보내도 한 번만 처리되게 하는 번호)와 「다시 시도 = 같은 키·같은 내용」 규칙을 한곳에서 지키기 위해서다.
  - `onSuccess`는 보낸 내용(payload)과 지금 입력을 비교해, 같을 때만 입력을 지운다. 재시도 사이에 고친 입력은 남긴다.
- **편집 대상은 배열 위치가 아니라 안정 키로 정한다.**
  - 기술 제약 행은 행마다 만든 `key`(UUID)로 고치고 지운다. 기술 결정 승인·반려는 결정 `id`로 기억한다.
  - 왜: 가운데 행을 지우면 위치가 밀려 다른 행을 고치게 된다(앞선 리뷰에서 반복된 결함).
- **입력이 있는 곳은 편집 보호(`useEditGuard`)와 세션 초안(`useSessionDraft`)을 함께 쓴다.**
  - 등록 입력, 기술 결정 선택, 재분석 지시, 입력 변경 분석 지시가 해당한다.
- **진행은 서버(Runner 보고)만 보여 준다.** 화면이 시간 경과로 단계를 넘기지 않는다(UAT-PROJECT-04).
  - 원본의 「Mock: …」 버튼, 「일시정지 (Mock)」, 「지금 확인」은 만들지 않았다.
- **본 적 없는 새 초안을 자동으로 승인하지 않는다.**
  - 승인·재분석은 화면이 본 초안 `revision`을 보낸다. 그사이 새 초안이 오면 서버가 409 충돌을 준다.
  - 충돌 창에서 「다시 적용」을 눌러도 새 초안을 다시 읽기만 한다. 팀장이 확인하고 다시 누른다(UAT-PROJECT-07).
- **승인이 끝나면 첫 Task 상세(`/wbs/<가장 앞 Task 키>`)로 간다(UAT-PROJECT-06 b).**
  - 승인 응답에 Task 키가 없어서 `listTasks`로 한 번 더 읽는다.
- **기술 결정 확정은 미결이 있으면 보내지 않는다.** 서버도 409 `DECISIONS_PENDING`으로 거부한다.
- **초기화 창 안에도 실패 안내와 「다시 시도」를 보인다.**
  - 왜: 앱 틀의 오류 막대는 모달 overlay(화면을 덮는 반투명 판) 아래에 있어, 창이 열린 동안 누를 수 없다.
- **입력 이력 재작성 경고**(`alerts` key `input_history_rewritten`)가 열려 있으면 「복구 확인 · 입력 확인 다시 시도」를 보인다.
  - 요청은 `POST /api/project/inputs/recheck` `{updatedAt}`이다(조정자 결정 2026-11-26).
  - 요청만으로 경고를 지우지 않는다. Runner가 다시 관측해 서버가 해소해야 사라진다.
- **원본과 다르게 바로잡은 문구**
  - 초기화 「삭제하지 않음」: 원본 「원본 입력 파일(프로토타입 zip · 설계 문서)」 → 「입력 자료(prototype/ (uiux · docs) — GitHub에 그대로)」(MM-23, UAT-RESET-01).
  - 입력 파일 영역: 원본은 옛 규칙 `^docs/`로 나눠 설계 문서를 「프로토타입」으로 잘못 분류했다. 제품은 `prototype/docs/` 아래면 「설계 문서」다(MM-04).
  - 구조 표 숫자: 원본 고정 숫자(HTML 3 · JS 4 …) 대신 Runner 보고값을 쓴다(MM-27).
  - 기술 결정 단계 칩: 원본과 같이 「진행 중」. 「팀장 확인 대기」는 「팀장 승인」 단계와 기술 결정 카드 제목에만 쓴다.

## 4. 알려진 문제(보고함)

- **프로젝트 정보 편집 API가 계약에 없다.** 그래서 UAT-PROJECT-10(이름·설명·시작일·목표일 수정)은 화면에 편집 버튼을 두지 않았다.
- **「지금 확인」·감지 확인 시각이 계약에 없다.** UAT-PROJECT-09 b의 「감지 확인 시각 갱신」을 화면에 보일 값이 없다.
- **입력 버전 표의 「커밋 메시지」가 응답에 없다.** 그 자리에 그 버전의 팀장 지시를 보인다.
- **`getGithubSettings` 타입이 깨져 있다.** 설정 요청 id를 템플릿 문자열로 만들어 TypeScript에서 `string`이 된다. 그래서 `github.ts`가 계약 필드를 옮겨 적은 임시 타입을 쓴다.
  - 서버(apps/api)에는 아직 `/api/settings/github`가 없다. 실제 서버에서는 「GitHub 연결 상태를 확인하지 못했습니다」가 보인다.
- **출처 Task 링크는 `/wbs?srcV=<버전>`으로 간다.** 그 필터를 적용하는 일은 WBS 화면(M3-02)의 몫이다.
- **차이 분석의 CP 연결**(`inputJob.proposalId`)은 서버가 아직 null을 준다. 값이 오면 「Change Proposal 보기」(`/change?cp=<id>`)가 보인다.

## 5. 시각 비교

- 조건: 1920×1080, 배율 1, ko-KR, Asia/Seoul, 시계 2026-11-05 20:00 KST, 애니메이션 끔, 마우스는 화면 구석.
- 차이 계산: pixelmatch, 색 차이 기준 0.1, 글자 가장자리 번짐(안티에일리어싱) 픽셀은 세지 않는다(apps/web/README §5와 같다).
- 결과: `~/.orca/bots/agentwbs/archive/2026-11-26/M3-04/visual/`에 `[원본 | 구현 | 차이]` 이미지와 `summary.md`.
- 합격 기준
  - 같아야 하는 영역(제목 줄, 등록 카드 위쪽, 오른쪽 안내 카드, 9단계 카드, 초기화 창 위쪽)은 2~4% 이하. 넘으면 시험이 실패한다.
  - 초기화 창 위쪽은 4%까지 둔다. 왜: 아래 내용 길이 차이로 창이 몇 px 위로 올라가 경계선 위치가 조금 다르다.
- 예외(기록만): 데이터 글자가 다른 전체 화면, Mock 버튼이 빠진 자리, 브라우저 언어에 따라 다른 date 칸 자리표시.

## 용어집

| 용어 | 뜻 |
|---|---|
| 멱등 키(Idempotency-Key) | 같은 요청을 두 번 보내도 서버가 한 번만 처리하게 붙이는 번호 |
| revision | 초기 WBS 초안의 판 번호. 재분석할 때마다 올라간다 |
| epoch(초기화 번호) | 초기화할 때마다 1 오르는 번호. 낡은 보고·요청을 거부하는 데 쓴다 |
| inputHead(입력 사슬 끝) | Runner가 마지막으로 보고한 main 끝 커밋. 「이 버전으로 분석」은 이 커밋으로 고정한다 |
| recheck | 입력 이력 재작성 뒤, 복구했으니 다시 확인해 달라는 요청 |
| overlay | 모달 뒤에서 화면 전체를 덮는 반투명 판. 그 아래 버튼은 누를 수 없다 |
| 세션 초안 | 로그인이 끊겼을 때 입력을 탭 안에 잠시 보관했다가 다시 로그인하면 복원하는 기능 |
