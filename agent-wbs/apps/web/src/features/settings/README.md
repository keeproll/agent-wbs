# features/settings — 설정 화면(M3-08)

팀장이 Runner·Agent·일정 정책을 정하고 데이터 정합성을 점검하는 화면이다.
원본은 `prototype/uiux/Main.dc.html`의 설정(UI-12, P L2251–2676)이다.
낯선 말은 맨 아래 [용어집](#용어집)에 있다.

## 1. 주소와 탭

| 주소 | 탭 | 만든 곳 |
|---|---|---|
| `/settings`, `/settings/runner` | Runner · 실행 환경(기본) | `RunnerTab.tsx` |
| `/settings/agent` | Agent | `AgentTab.tsx` |
| `/settings/plan` | 일정 · Task | `PlanTab.tsx` |
| `/settings/report` | 보고서 · 메일 | M6-03이 만든다(지금은 안내 한 줄) |
| `/settings/notify` | 알림 | M6-04가 만든다(지금은 안내 한 줄) |
| `/settings/system` | 점검 | `SystemTab.tsx` |

- 탭은 주소가 있는 링크다.
  - 왜: 새로고침·뒤로 가기·링크 공유 때 같은 탭이 열려야 한다(UAT-SHELL-01, MM-29).
- 모르는 탭 주소(예: `/settings/abc`)는 `/settings/runner`로 바꾼다.
- 다른 화면에서 설정으로 보낼 때는 탭 주소를 그대로 쓴다. 예: 메일 실패 알림 → `/settings/report`.
- 라우터 연결: `src/app/router.tsx`에서 `/settings`와 `/settings/:tab`을 `SettingsPage`로 바꿨다(M3-08 E2E에 필요해서). 병합 때 coordinator가 확인한다.

## 3. 편집 규칙 — `useSettingForm`

설정 카드는 모두 같은 규칙으로 저장한다.

1. 선택 버튼을 누르면 **초안**만 바뀐다. 카드 아래에 「저장하지 않은 변경이 있습니다 · 변경 취소 · 저장」 줄이 나타난다.
   - 왜: 원본은 누르는 즉시 저장했다(P L6655). 그러면 저장 실패·충돌·세션 만료 때 지킬 입력이 없고, 이동 전에 물어볼 수도 없다.
   - 바뀐 것이 없으면 저장 줄은 보이지 않는다. 그래서 평소 화면 모양은 원본과 같다.
2. 초안 규칙은 하나다: **내가 편집한 칸은 서버 변경 이벤트·자동 갱신·저장 응답이 덮어쓰지 않는다.**
   - 칸마다 「편집됨」을 기억한다(예: `lowPct`, `floors.dbHigh`). 값을 원래대로 되돌려도 편집됨으로 남는다.
   - 화면 값은 서버 최신 값 위에 편집됨 칸만 내 값으로 덮은 것이다. 편집하지 않은 칸은 다른 탭·Runner 변경을 그대로 따라간다.
   - 왜: 저장 응답보다 자기 저장의 변경 이벤트가 먼저 오는 등 순서가 섞여도 사용자가 고른 값이 사라지지 않게 한다(재리뷰 48a7f7a).
3. 저장은 공통 `useSave`로 보내고, **기준(버전)** 을 함께 보낸다.
   - 서버 값이 새로 읽혔는데 내가 편집한 칸을 건드리지 않았으면 기준 버전만 최신으로 옮긴다. 그래서 다른 탭이 다른 칸을 바꿔도 충돌 없이 내 칸만 저장된다.
   - 서버가 내가 편집한 칸을 바꿨으면(다른 탭) 기준을 옮기지 않는다. 저장하면 서버가 `409 VERSION_CONFLICT`를 주고 충돌 창이 뜬다(조용히 덮어쓰지 않음).
   - 저장을 기다리는 동안 더 고친 칸(되돌림 포함)은 저장이 성공해도 남고, 기준만 성공 결과로 옮긴다. 다음 저장은 새 버전으로 그 값을 보낸다.
   - 화면에서 고치지 않는 칸(예: heartbeat 주기)은 기준 값에서 채운다(`send`의 세 번째 인수 `data`).
   - 충돌 창의 「최신 불러오기」는 서버에서 새로 읽고 초안을 버린다.
   - 충돌 창의 「최신 위에 다시 적용」은 공통 `useSave`의 `reapplyRequest`(M3-04 0dcb8db)로 보낸다. 최신 값 위에 편집됨 칸만 얹는다. 응답을 잃으면 같은 내용·같은 키로만 다시 보낸다.
   - 순서를 섞은 시험: `e2e/settings-core-events.spec.ts`.
4. 초안은 공통 `useSessionDraft`에 `settings:<카드 키>` 이름으로 등록한다.
   - 로그인이 끊기면 보관하고, 다시 로그인하면 같은 탭에서 「복원 / 버리기」를 묻는다.
   - 편집 시작 값도 함께 보관한다. 복원한 초안을 저장해도 그 버전으로 보내 충돌을 알아챈다.
   - 아직 「추가」를 누르지 않은 작업 불가일 날짜·사유도 따로 보관하고(`settings:blackouts-input`), 이동 전에 묻는다(지적 5).
   - GitHub 새 토큰은 비밀값이라 보관하지 않는다. 토큰 저장의 다시 적용도 `reapplyRequest`로 보낸다.
5. 저장하지 않은 카드가 하나라도 있으면 다른 탭·메뉴로 가기 전에 묻는다(공통 `useEditGuard`).
   - 편집 보호는 화면에 하나만 둔다. 카드들은 `DirtyContext`로 「나 바뀌었음」을 알린다.
   - 왜: React Router의 이동 막기(useBlocker)는 한 번에 하나만 쓸 수 있다.
6. 편집 대상은 **안정 키**로 정한다. 배열 위치를 쓰지 않는다.
   - 카드: `exec-policy`, `models`, `split`처럼 카드 이름.
   - 목록 항목: 모델은 `Agent:모델ID`, 하위 Agent는 정의 ID, 작업 불가일은 날짜.
   - 왜: 서버 목록 순서가 바뀌어도 엉뚱한 항목을 고치지 않는다.

새 카드를 만들 때 예시:

```tsx
const q = useSettingQuery('getExecPolicy', '실행 정책');          // 조회 + 갱신 실패 알림
const form = useSettingForm({
  id: 'exec-policy', label: '실행 정책', ...q,
  toForm: (d) => ({ lowPct: d.lowPct }),                          // 화면에서 고칠 값만
  send: (f, updatedAt) => client.call('putExecPolicy', { body: { updatedAt, ...나머지, ...f } }),
});
// form.form(보일 값) · form.edit(바꾸기) · form.footer(저장 줄+충돌 창) · form.restoreOffer(복원 안내)
```

## 4. 기본값과 원본 값

- 낮춤 기준(사용량 부족 기준) 기본 20%, 가정 가동률 60%, 재조정 임계값 1일(owner 2026-11-26).
  - 값은 서버 system seed가 넣는다. 화면은 서버 값을 그대로 보이고, 선택지에 없는 값이 와도 버튼을 하나 더 만들어 보인다(`withValue`).
- 모델 순서는 설정값이다(owner 2026-11-26 아이템 8). 「▲ / ▼」로 바꾸고, 바꿨을 때만 `rankOrder`를 보낸다.
  - 표는 순서 목록(`rankOrder`)을 기준으로 그린다. Runner가 아직 보고하지 않은 모델도 「보고 전」으로 보이고 순서를 바꿀 수 있다(새 설치, 지적 4).
  - 보고 전 모델은 허용 버튼이 없다. 순서만 바꾸고 허용 모델을 임의로 늘리지 않는다.
- 일정에 영향을 주는 저장 뒤 일정 다시 읽기가 실패하면 저장 성공 안내와 별도로 오류 막대 「최신 일정을 불러오지 못했습니다」와 「다시 시도」를 보인다(지적 6).
  - 순서 목록은 **아래 등급부터** 적는다(contracts §2.1). 화면은 위 등급부터 보인다.
- 진행률 가중치는 원본 STAGE_PCT(P L3397, owner Q-03) 그대로다.

## 6. 서버에 없어서 못 보인 것(보고함)

아래는 화면 자리는 정했지만 서버 API가 없어 보이지 않는다. 서버가 생기면 붙인다.

- `GET/PUT /api/settings/split`·`schedule`·`blackouts`·`concurrency`·`obs-budget`·`github`, `POST /api/settings/github/check`(13개): 계약에는 있으나 서버(apps/api)에 경로가 없어 404다(실제 API E2E로 확인). 서버 후속 3차가 맡는다.
  - 그래서 실제 서버에서는 이 카드들이 「불러오지 못했습니다 · 다시 시도」를 보인다.
- 「기준을 벗어난 Task」 목록과 일정 탭 배지: Task별 분할 점검 결과를 주는 API가 없다.
- 팀장 고정 Task 목록: Task 목록 응답에 등급 고정 여부가 없다. Task 상세(`getTask`)의 `grades.*.locked`에는 있으므로, 상세를 모아 쓰거나 집계 계약을 더하는 문제다.
- 모델별 「사용 중 Task n건」, 하위 Agent별 지정 Task·마지막 사용·재작업률, 참고 자료 목록: 응답에 없다.
- 반복 재작업 알림의 「확인」(알림 닫기): 알림을 처리하는 API가 없다. 「실행 보기」만 둔다.
- 준비 상태 「다시 점검」: Runner에 다시 점검을 요청하는 API가 없다.

## 용어집

| 용어 | 뜻 |
|---|---|
| 초안(draft) | 화면에서 바꿨지만 아직 서버에 저장하지 않은 값 |
| updatedAt(버전) | 서버가 마지막으로 저장한 시각. 저장 때 함께 보내 「내가 본 값 위에 저장하는지」 확인한다 |
| 충돌 창 | 내가 본 뒤 다른 곳에서 먼저 저장했을 때 뜨는 창(409 VERSION_CONFLICT) |
| 편집 보호 | 저장하지 않은 변경이 있을 때 이동 전에 묻는 기능 |
| heartbeat | Runner가 「살아 있다」고 주기적으로 보내는 신호 |
| readiness(준비 상태) | Runner가 스스로 점검한 실행 환경 결과(CLI 설치·로그인·디스크 등) |
| 관측 등급 | 하위 Agent 수를 얼마나 믿을 수 있게 셀 수 있는지(검증됨·일부 관측·미검증) |
| 보수 계산 | 확실하지 않을 때 실제보다 많이 쓴다고 보고 자리를 잡아 두는 계산 |
| seed | 처음 DB를 만들 때 넣는 기본값 |
| 안정 키 | 순서가 바뀌어도 그 항목을 가리키는 이름(ID·날짜) |
| pixelmatch | 두 그림의 픽셀을 비교해 다른 픽셀 수를 세는 도구 |
