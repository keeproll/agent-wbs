# M7-05 — 빌드·통합 화면

이 문서는 M7-05에서 만든 빌드·통합 화면(UI-08)의 사용 설명이다.
원본 `prototype/uiux/Main.dc.html`의 P L1405–1482(화면)와 P L4765–4801(계산)을 옮겼다.
서버 API는 M7-04(keeproll/m7-04)의 shared 계약을 그대로 쓴다.

- 처음이라면 [apps/web/README.md](../../../README.md) → [src/shared/README.md](../../shared/README.md) → 이 문서 순서로 읽는다.
- 낯선 말은 맨 아래 [용어집](#용어집)에 있다.

## 1. 한눈에 보기

| 주소 | 보이는 것 |
|---|---|
| `/ci` | 실행 기록 목록 |
| `/ci?stage=int` | 단계 필터를 건 목록(`task`·`int`·`night`·`deploy`) |
| `/ci/<실행 id>` | 왼쪽 레일(목록) + 오른쪽 실행 상세 |
| `/ci?tab=queue` | 병합 대기열 |
| `/ci?tab=deploy` | 배포 확인 |
| `/ci?tab=pipe` | 파이프라인 정의와 실행 설정 |
| `/ci?tab=flaky` | 불안정 테스트 |

- 탭·선택·필터를 모두 주소에 둔다.
  - 왜: 새로고침·뒤로 가기·알림 링크로 같은 화면이 열려야 한다(MM-29).
- 상세 주소 `/ci/<실행 id>`는 서버 알림·통지 ref의 `path`(`/ci/<id>`)와 같은 모양이다.
  - 왜: Telegram·메일·대시보드 알림 링크가 주소를 바꾸지 않고 바로 상세를 연다(UAT-RESP-02, UAT-TG-09).
- 키보드(UAT-TASK-11과 같은 규칙):
  - 목록에서 ↑/↓로 행을 옮기고 Enter로 연다.
  - 상세에서 ↑/K는 이전, ↓/J는 다음, Esc는 「펼치기」(목록으로)다.
  - 글자를 입력하는 중이거나 창(모달)이 열려 있으면 동작하지 않는다.

## 3. 데이터 — 어떤 API를 언제 부르나

모든 요청과 응답 모양은 계약 타입(`@awbs/shared/api`)에서 뽑아 쓴다.

- 변경 이벤트 topic(바뀐 자료의 종류)은 자료마다 다르다.
  - CI 자료(실행·대기열·불안정 테스트·정의·설정)는 `ci`다. 설정은 `settings`, 정의는 `project`도 받는다.
  - 대기열의 Task 제목은 `task`, 상세의 시도 번호는 `attempt`다.
  - 왜: 각 자료가 실제로 바뀔 때만 다시 읽어 표시를 갱신하기 위해서다. 하나로 줄이면 Task 제목이나 시도 번호 갱신을 놓친다.

| 화면 | 요청 |
|---|---|
| 머리글·실행 기록 | `GET /api/projects/:projectId/ci/runs`(모든 쪽) |
| 실행 상세 | `GET /api/projects/:projectId/ci/runs/:id`, `GET /api/tasks/:taskKey/attempts`(시도 번호) |
| 병합 대기열 | `GET /api/projects/:projectId/ci/queue`, `GET /api/projects/:projectId/tasks`(제목) |
| 배포 확인 | `GET /api/projects/:projectId/ci/settings`(접속 URL) |
| 파이프라인 정의 | `GET /api/projects/:projectId/ci/pipeline`, `…/ci/settings` |
| 불안정 테스트 | `GET /api/projects/:projectId/ci/flaky` |
| Task 실행 탭 | `GET …/ci/runs?taskKey=<Task>`(모든 쪽) |

- 실행 목록은 「모든 쪽」을 읽는다(`useAllPages`).
  - 왜: 단계별 건수·미해결 실패 수·탭 배지는 모든 행을 알아야 서버와 일치한다.
- 목록 순서는 서버 순서 그대로다. 화면이 다시 정렬하지 않는다.
  - 서버는 시작 시각이 늦은 것을 먼저 준다. 시작 시각이 같으면 단조 순번(run_no)이 큰 것을 먼저 준다(M7-04 조정자 결정 8).
  - 즉 순번은 시각이 같을 때만 순서를 정한다. 시각이 다르면 시각이 우선이다.
  - 시험 자료도 이 순서로 준다. 원본 화면의 행 순서(추가한 순서의 역순)는 시각 비교에서만 쓴다.

## 4. 표시 규칙

### 4.1 결과 이름

- 통과·실패·실행 중·대기·건너뜀은 원본 이름과 색 그대로다(P CI_ST L3524).
- **기준선 실패**(`failScope=baseline`)는 「실패」가 아니라 노란 「기준선 실패」로 보인다.
  - 왜: main 기준 커밋 자체가 실패한 것이라 Task 탓이 아니다. Task 실패로 보이면 죄 없는 Task에 재작업을 시킨다(M7-04 조정자 결정).
  - 상세에는 「main 기준 커밋에서도 실패했습니다」 안내가 붙는다.

### 4.2 단계 표

- 실패한 실행에서 실패 단계 뒤의 대기·실행 중 단계는 「건너뜀」으로 보인다(UAT-CI-01 d).
  - 왜: 실제로 돌지 않은 단계를 「대기」로 두면 아직 돌 것처럼 보인다.
- Runner가 실패 단계를 단계 목록에 보내지 않고 `failStep`만 보냈으면 맨 뒤에 실패 줄을 더한다.
  - 왜: 어느 단계에서 멈췄는지를 잃지 않는다.
- 단계 시간은 원본처럼 초 하나(예: 136초), 전체 소요는 「분 초」(예: 14분 02초)로 쓴다.
- 전체 소요는 시작~끝(`finishedAt`)이다. 끝난 시각이 없으면 보고된 단계 시간의 합, 단계도 없으면 「—」.

### 4.2-1 실행 설명과 GitHub 칸

- 실행 설명(`note`)은 Runner가 실행 시점에 아는 설명이다. 있으면 상세의 대상 표 아래에 원본처럼 한 줄로 보인다.
  - 나중에 생긴 QA 결과 같은 설명은 실행 시점에 알 수 없어 오지 않는다(M7-04 fix2).
- GitHub 칸은 Runner가 GitHub에 실제로 보고하고 응답을 확인한 상태(`githubStatus`)만 「보고」로 보인다.
  - 예: 「GitHub PR #9 검사 상태 보고: agentwbs/task — failure · 2026-11-03 17:44」. 링크(url)가 있으면 누를 수 있다.
  - 값이 없으면 「검사 상태 보고 확인 전」이다. CI 결과(통과·실패)로 GitHub 상태를 짐작해 만들지 않는다.
  - 왜: GitHub 응답이 끊기면 실제 전송 여부를 모를 수 있다. 짐작한 「보고됨」은 거짓일 수 있다.

### 4.3 main 상태 배지

원본은 Mock 값을 그대로 썼다. 제품은 실행 기록과 **서버 판정값**으로 정한다.

> 원칙: **화면은 판정하지 않는다.** 기준선 해소·병합 여부·자동 재통합·다시 실행 가능 여부는 서버가 실행 응답에 넣어 준 값(M7-04 fix4)을 그대로 보인다.
> 왜: 화면이 같은 규칙을 따로 계산하면 서버와 다른 결론을 낼 수 있다. 예: 잘못된 정의의 PASS를 해소로 보거나, 화면이 모르는 대조 대기(reconcile)를 놓친다(재리뷰 review2 P2-2·3·4).

- 가장 최근의 「main을 본 실행」을 쓴다.
  - 야간 점검(통과·실패)
  - 통합 확인 통과 가운데 서버의 대기열 상태(`mergeStatus`)가 `merged`인 것 → 정상
    - 실제 병합 SHA(`actualMergeSha`)가 있는데 `merged`가 아니면 「main 확인 필요 · 병합 불일치 · <실제 병합 SHA>」다.
    - 왜: 실행의 병합 SHA는 「검사한 병합본」일 뿐이다. 실제 병합은 서버 대기열 상태로만 안다.
  - 서버가 아직 해소하지 않았다고 한(`baselineResolved: false`) 기준선 실패 → 「main 깨짐 · 기준선 검사 실패」
    - 서버는 main이 이동했거나, 올바른 정의로 실행한 더 나중의 ① PASS가 있으면 `true`로 준다. 순서는 서버 순번(run_no)으로 본다.
- 통합 확인 실패는 main을 깨지 않는다.
  - 왜: 실패한 PR은 병합되지 않는다(G L475).
- E2E 수는 Runner가 구조화해 보고한 값(`e2e { passed, total }`)이 있을 때만 「E2E 12 / 12」로 보인다.
  - 왜: 종료 코드만으로는 통과 수를 알 수 없다. 숫자를 꾸미지 않는다(M7-04 fix2 계약 1).
- 시각은 그 실행이 끝난 시각(`finishedAt`)이다. 끝난 시각이 없으면 시작 시각을 쓴다.
- 예: 야간 점검이 02:00에 시작해 14분 02초 걸렸으면 「main 정상 · c4e81f0 · E2E 12 / 12 · 2026-11-03 02:14」.

### 4.4 미해결 실패 수(실행 기록 탭 배지)

- **기준선 실패**는 서버 값 `baselineResolved`가 `false`일 때만 센다. 화면이 같은 대상의 통과로 다시 판단하지 않는다.
  - 왜: 서버는 정의가 맞는지·main이 이동했는지까지 보고 해소를 판정한다. 화면이 다시 세면 머리글의 「main 깨짐」과 건수가 서로 어긋난다.
  - 값이 없으면(`null`) 미해결로 꾸미지 않는다.
- **그 밖의 실패**는 같은 대상(같은 단계 + 같은 Task + 같은 PR)에 더 최근 통과가 없을 때만 센다.
  - 예: CI-0124(TASK-0004 실패) 뒤에 CI-0125(TASK-0004 통과)가 있으면 해결로 본다.

### 4.5 병합 대기열

- 서버의 대기열 순서(position)를 뒤집어 최근 것이 위에 오게 한다(원본 P L4792와 같음).
- 상태 이름: 검증 대기 · 대기 · 통합 확인 중 · 병합됨 · 통합 실패 — 병합 보류 · 대기열에서 빠짐.
- **병합 불일치(MERGE_MISMATCH)**: 실제 병합 SHA가 기록됐는데 병합됨이 아니면 빨간 경고 막대와 「병합 불일치 — 완료 보류」를 보인다.
  - 왜: 서버는 이때 Task를 done으로 넘기지 않고 보류한다(M7-04 조정자 결정 4). 팀장이 알아야 한다.
- 시각 칸: 병합됨은 실제 병합 시각(`mergedAt`), 그 밖은 대기열에 들어온 시각(`queuedAt`)이다. 원본도 같은 칸에 두 시각을 썼다.
  - 병합됐는데 실제 병합 시각을 아직 확인하지 못했으면 「병합 시각 미확인」이다. 서버가 받은 시각으로 대신하지 않는다.
- 연결된 실행이 있으면 시각 칸을 눌러 그 실행 상세를 연다. 실패 원인·재작업을 실행 상세에서 추적한다(UAT-CI-03).
- **기준선 실패로 끝난 통합**은 노란색이다. Task 탓이 아니다.
  - 뒤에 붙는 말은 연결된 실행의 서버 값 `autoReintegrate` 그대로다.
    - `pending` → 「기준선 실패 — 자동 재통합 대기·진행」
      - main 변경을 기다리는 경우와 이미 대기·진행 중인 작업을 모두 뜻한다. 그래서 「main이 바뀌면」 같은 시작 조건을 붙이지 않고, 상세에 서버 사유를 붙인다.
    - `blocked` → 「기준선 실패 — 자동 재통합 보류」(상세에 서버 사유 `autoReintegrateReason`)
    - `none` → 「기준선 실패」
  - 기준선 실패가 있으면 대기열 안내에 「기준선 실패는 예외입니다 …」 한 줄을 더한다. 원본 안내의 「실패하면 재작업 요청」과 어긋나지 않게 하기 위해서다.
    - 이 공통 안내는 자동 진행을 약속하지 않는다. 서버가 보류(`blocked`)한 행이 있을 수 있어서, 상태와 사유는 각 행과 실행 상세에서 확인하게 한다.

### 4.6 실행 상세의 서버 판정 칸

- **병합**(통합 확인 실행만): `mergeStatus`·`actualMergeSha`·`mergeCompleted` 그대로다.
  - 예: 「병합됨 → main @ c4e81f0 · 완료」, 「병합됨 → main @ … · Task 완료 처리 전」, 「병합 불일치 — 실제 병합 dead000 · 완료 보류 (검사한 병합본 c4e81f0)」, 「대기열 기록 없음 — 병합 여부 미확인」.
- **원인 후보**: `causeCandidates`의 커밋과, 서버가 병합 기록으로 연결한 Task 링크다. 연결이 없으면 「연결된 Task 없음」이다.
  - 왜: 원인 Task를 화면이 짐작하면 다른 Task에 잘못 연결할 수 있다. 서버가 확정한 연결만 링크로 보인다.
- **기준선 실패 안내**: `baselineResolved: true`면 「서버가 이 기준선 실패를 해소로 판정했습니다」를 붙인다. 자동 재통합 안내는 `autoReintegrate`·사유 그대로다.
- **다시 실행**: 실패한 실행에만 버튼이 있다. `retryAllowed`가 거짓이면 버튼을 막고 「다시 실행할 수 없습니다 — <retryBlockedReason>」을 보인다.
  - 예: 병합 불일치 보류·대조 대기 중이면 서버가 막는다. Gate를 벗어난 Task의 기준선 실패처럼 서버가 허용하면 누를 수 있다.

## 5. 바꾸는 요청 — 화면은 결과를 꾸며 만들지 않는다

| 버튼 | 요청 | 결과 |
|---|---|---|
| 다시 실행(실패한 실행만) | `POST …/ci/runs/:id/retry` | 202 `{ jobId }`. Runner가 실제로 다시 실행해 새 기록을 보고한다 |
| 배포 확인 실행 | `POST …/ci/deploy-check` | 202 `{ jobId }`. 같은 방식 |
| 격리 해제 / 다시 격리 | `PATCH …/ci/flaky/:id` `{ updatedAt, quarantined }` | 바뀐 불안정 테스트 |

- 원본은 다시 실행을 누르면 늘 「통과」 기록을 만들었다. 제품은 만들지 않는다(MM-07).
- Gate에서 기다리는 Task의 기준선 실패를 다시 실행하면, 서버는 ① 재검사 대신 새 통합 확인(`integrate`)을 만든다(M7-04 결정 11). 화면 요청은 같다.
  - 왜: 꾸민 통과는 실제 실패를 숨긴다.
- 공통 흐름 `useSave`를 쓴다.
  - 처리 중 버튼 잠금, 500·끊김은 같은 멱등 키로 다시 시도, `EXTERNAL_WRITE_BLOCKED` 같은 409는 오류 막대다.
- 격리 요청은 「토글」이 아니라 「quarantined를 이 값으로」라는 절대값이다.
  - 왜: 다시 시도·다시 적용으로 같은 요청이 두 번 가도 결과가 같다.
  - 버전 충돌(409 `VERSION_CONFLICT`)은 충돌 창을 띄운다. 「다시 적용」은 최신 목록을 읽어 그 `updatedAt`으로 같은 값을 보낸다(`reapplyRequest`).
- 이 화면에는 글자 입력 칸이 없다. 그래서 편집 보호(`useEditGuard`)와 세션 초안(`useSessionDraft`)은 쓸 곳이 없다.

## 6. 휴대폰(390px)

## 용어집

| 용어 | 뜻 |
|---|---|
| CI 실행 | Runner가 빌드·테스트·기동을 직접 돌린 기록 하나. 예: CI-0124 |
| ① Task 검사 | Agent 작업이 끝난 Task 브랜치를 검사하는 단계 |
| ② 통합 확인 | main + PR 병합본을 검사하는 단계. 통과해야 병합된다 |
| ③ 야간 점검 | 매일 main 전체를 검사하는 단계 |
| ④ 배포 확인 | 운영 빌드·기동·브라우저 접속을 확인하는 단계 |
| 기준선 실패(baseline) | main 기준 커밋에서도 같은 검사가 실패한 것. Task 탓이 아니다(`failScope=baseline`) |
| 재통합 | 통합 확인을 다시 하는 것. 기준선 실패 뒤 서버가 조건을 확인해 자동으로 만들거나 보류한다(상태는 `autoReintegrate`) |
| 병합 대기열 | 검증 PASS인 PR이 통합 확인을 한 번에 하나씩 기다리는 줄 |
| 병합 불일치(MERGE_MISMATCH) | 실제 병합 결과가 검증 근거와 달라 서버가 완료를 보류한 상태 |
| 불안정 테스트(flaky) | 가끔만 실패하는 테스트. 격리하면 실패해도 통과를 막지 않는다 |
| 격리 | 불안정 테스트의 실패를 기록만 하고 판정에서 빼는 것 |
| job | 서버가 Runner에게 맡긴 일 하나. 다시 실행·배포 확인은 job을 만든다 |
| 멱등 키(Idempotency-Key) | 같은 요청을 두 번 보내도 한 번만 처리되게 하는 요청 번호 |
| 레일 | 상세를 볼 때 왼쪽에 좁게 남는 목록 |
| 펼치기 | 상세를 닫고 넓은 목록으로 돌아가기 |
| pixelmatch | 두 그림의 픽셀을 비교해 다른 픽셀 수를 세는 도구 |
