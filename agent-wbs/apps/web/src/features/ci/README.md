# M7-05 — 빌드·통합 화면

이 문서는 M7-05에서 만든 빌드·통합 화면(UI-08)의 사용 설명이다.
원본 `prototype/uiux/Main.dc.html`의 P L1405–1482(화면)와 P L4765–4801(계산)을 옮겼다.
서버 API는 M7-04(keeproll/m7-04)의 shared 계약을 그대로 쓴다.

- 처음이라면 [apps/web/README.md](../../../README.md) → [src/shared/README.md](../../shared/README.md) → 이 문서 순서로 읽는다.
- 낯선 말은 맨 아래 [용어집](#용어집)에 있다.

## 1. 한눈에 보기

| 주소 | 보이는 것 |
|---|---|
| `/ci` | 실행 기록 목록 |
| `/ci?stage=int` | 단계 필터를 건 목록(`task`·`int`·`night`·`deploy`) |
| `/ci/<실행 id>` | 왼쪽 레일(목록) + 오른쪽 실행 상세 |
| `/ci?tab=queue` | 병합 대기열 |
| `/ci?tab=deploy` | 배포 확인 |
| `/ci?tab=pipe` | 파이프라인 정의와 실행 설정 |
| `/ci?tab=flaky` | 불안정 테스트 |

- 탭·선택·필터를 모두 주소에 둔다.
  - 왜: 새로고침·뒤로 가기·알림 링크로 같은 화면이 열려야 한다(MM-29).
- 상세 주소 `/ci/<실행 id>`는 서버 알림·통지 ref의 `path`(`/ci/<id>`)와 같은 모양이다.
  - 왜: Telegram·메일·대시보드 알림 링크가 주소를 바꾸지 않고 바로 상세를 연다(UAT-RESP-02, UAT-TG-09).
- 키보드(UAT-TASK-11과 같은 규칙):
  - 목록에서 ↑/↓로 행을 옮기고 Enter로 연다.
  - 상세에서 ↑/K는 이전, ↓/J는 다음, Esc는 「펼치기」(목록으로)다.
  - 글자를 입력하는 중이거나 창(모달)이 열려 있으면 동작하지 않는다.

## 3. 데이터 — 어떤 API를 언제 부르나

모든 요청과 응답 모양은 계약 타입(`@awbs/shared/api`)에서 뽑아 쓴다. 변경 이벤트 topic은 모두 `ci`다.

| 화면 | 요청 |
|---|---|
| 머리글·실행 기록 | `GET /api/projects/:projectId/ci/runs`(모든 쪽) |
| 실행 상세 | `GET /api/projects/:projectId/ci/runs/:id`, `GET /api/tasks/:taskKey/attempts`(시도 번호) |
| 병합 대기열 | `GET /api/projects/:projectId/ci/queue`, `GET /api/projects/:projectId/tasks`(제목) |
| 배포 확인 | `GET /api/projects/:projectId/ci/settings`(접속 URL) |
| 파이프라인 정의 | `GET /api/projects/:projectId/ci/pipeline`, `…/ci/settings` |
| 불안정 테스트 | `GET /api/projects/:projectId/ci/flaky` |
| Task 실행 탭 | `GET …/ci/runs?taskKey=<Task>`(모든 쪽) |

- 실행 목록은 「모든 쪽」을 읽는다(`useAllPages`).
  - 왜: 단계별 건수·미해결 실패 수·탭 배지는 모든 행을 알아야 서버와 일치한다.
- 목록 순서는 서버 순서(시작 시각 + 단조 순번, 최근 먼저) 그대로다. 화면이 다시 정렬하지 않는다.
  - 왜: M7-04 조정자 결정 8. 벽시계가 같거나 뒤틀려도 순번이 순서를 정한다.

## 4. 표시 규칙

### 4.1 결과 이름

- 통과·실패·실행 중·대기·건너뜀은 원본 이름과 색 그대로다(P CI_ST L3524).
- **기준선 실패**(`failScope=baseline`)는 「실패」가 아니라 노란 「기준선 실패」로 보인다.
  - 왜: main 기준 커밋 자체가 실패한 것이라 Task 탓이 아니다. Task 실패로 보이면 죄 없는 Task에 재작업을 시킨다(M7-04 조정자 결정).
  - 상세에는 「main 기준 커밋에서도 실패했습니다」 안내가 붙는다.

### 4.2 단계 표

- 실패한 실행에서 실패 단계 뒤의 대기·실행 중 단계는 「건너뜀」으로 보인다(UAT-CI-01 d).
  - 왜: 실제로 돌지 않은 단계를 「대기」로 두면 아직 돌 것처럼 보인다.
- Runner가 실패 단계를 단계 목록에 보내지 않고 `failStep`만 보냈으면 맨 뒤에 실패 줄을 더한다.
  - 왜: 어느 단계에서 멈췄는지를 잃지 않는다.
- 단계 시간은 원본처럼 초 하나(예: 136초), 전체 소요는 「분 초」(예: 14분 02초)로 쓴다.
- 전체 소요는 보고된 단계 시간의 합이다. 단계가 없으면 「—」.

### 4.3 main 상태 배지

원본은 Mock 값을 그대로 썼다. 제품은 실행 기록에서 정한다.

- 가장 최근의 「main을 본 실행」을 쓴다.
  - 야간 점검(통과·실패)
  - 병합된 통합 확인(통과 + 병합 SHA)
  - 기준선 실패 → 「main 깨짐 · 기준선 검사 실패」
- 통합 확인 실패는 main을 깨지 않는다.
  - 왜: 실패한 PR은 병합되지 않는다(G L475).

### 4.4 미해결 실패 수(실행 기록 탭 배지)

- 같은 대상(같은 단계 + 같은 Task + 같은 PR)에 더 최근 통과가 없는 실패만 센다.
- 예: CI-0124(TASK-0004 실패) 뒤에 CI-0125(TASK-0004 통과)가 있으면 해결로 본다.

### 4.5 병합 대기열

- 서버의 대기열 순서(position)를 뒤집어 최근 것이 위에 오게 한다(원본 P L4792와 같음).
- 상태 이름: 검증 대기 · 대기 · 통합 확인 중 · 병합됨 · 통합 실패 — 병합 보류 · 대기열에서 빠짐.
- **병합 불일치(MERGE_MISMATCH)**: 실제 병합 SHA가 기록됐는데 병합됨이 아니면 빨간 경고 막대와 「병합 불일치 — 완료 보류」를 보인다.
  - 왜: 서버는 이때 Task를 done으로 넘기지 않고 보류한다(M7-04 조정자 결정 4). 팀장이 알아야 한다.
- 시각 칸은 연결된 통합 확인 실행의 시작 시각이고, 누르면 그 실행 상세가 열린다.
  - 왜: 계약의 대기열 행에는 시각이 없다. 실패 원인·재작업을 실행 상세에서 추적한다(UAT-CI-03).

## 5. 바꾸는 요청 — 화면은 결과를 꾸며 만들지 않는다

| 버튼 | 요청 | 결과 |
|---|---|---|
| 다시 실행(실패한 실행만) | `POST …/ci/runs/:id/retry` | 202 `{ jobId }`. Runner가 실제로 다시 실행해 새 기록을 보고한다 |
| 배포 확인 실행 | `POST …/ci/deploy-check` | 202 `{ jobId }`. 같은 방식 |
| 격리 해제 / 다시 격리 | `PATCH …/ci/flaky/:id` `{ updatedAt, quarantined }` | 바뀐 불안정 테스트 |

- 원본은 다시 실행을 누르면 늘 「통과」 기록을 만들었다. 제품은 만들지 않는다(MM-07).
  - 왜: 꾸민 통과는 실제 실패를 숨긴다.
- 공통 흐름 `useSave`를 쓴다.
  - 처리 중 버튼 잠금, 500·끊김은 같은 멱등 키로 다시 시도, `EXTERNAL_WRITE_BLOCKED` 같은 409는 오류 막대다.
- 격리 요청은 「토글」이 아니라 「quarantined를 이 값으로」라는 절대값이다.
  - 왜: 다시 시도·다시 적용으로 같은 요청이 두 번 가도 결과가 같다.
  - 버전 충돌(409 `VERSION_CONFLICT`)은 충돌 창을 띄운다. 「다시 적용」은 최신 목록을 읽어 그 `updatedAt`으로 같은 값을 보낸다(`reapplyRequest`).
- 이 화면에는 글자 입력 칸이 없다. 그래서 편집 보호(`useEditGuard`)와 세션 초안(`useSessionDraft`)은 쓸 곳이 없다.

## 6. 휴대폰(390px)

- 알림 링크(`/ci/<id>`)로 열면 로그인 뒤 그 상세로 돌아온다.
- 760px 이하에서는 상세가 레일(목록)보다 먼저 나온다(`ci.css`).
  - 왜: 알림을 받고 연 사람은 상세부터 읽어야 한다. 변경 제안 화면과 같은 규칙이다.
- 단계 표의 이름 칸은 줄바꿈해 화면 폭을 넘지 않는다.
- 1280px 미만 표는 영역 안에서 가로로 밀어 모든 열을 읽는다(`TableScroll`, D-28).

## 9. 계약에 없어 보이지 못하는 값(보고 대상)

아래 값은 원본 화면에 있지만 M7-04 계약에 필드가 없다. 화면은 값을 꾸미지 않고 빼거나 다른 실제 값으로 대신했다.

- main E2E 통과 수(「E2E 12 / 12」)
- 실행 기록의 설명 한 줄(note)
- 병합 대기열 행의 시각
- 불안정 테스트의 마지막 실패 시각
- CI 설정의 서비스 기동 구성
- GitHub 검사 상태가 실제로 보고됐는지 여부(화면은 PR·단계·결과로 「보고하는 이름과 상태」를 보인다)

## 용어집

| 용어 | 뜻 |
|---|---|
| CI 실행 | Runner가 빌드·테스트·기동을 직접 돌린 기록 하나. 예: CI-0124 |
| ① Task 검사 | Agent 작업이 끝난 Task 브랜치를 검사하는 단계 |
| ② 통합 확인 | main + PR 병합본을 검사하는 단계. 통과해야 병합된다 |
| ③ 야간 점검 | 매일 main 전체를 검사하는 단계 |
| ④ 배포 확인 | 운영 빌드·기동·브라우저 접속을 확인하는 단계 |
| 기준선 실패(baseline) | main 기준 커밋에서도 같은 검사가 실패한 것. Task 탓이 아니다(`failScope=baseline`) |
| 병합 대기열 | 검증 PASS인 PR이 통합 확인을 한 번에 하나씩 기다리는 줄 |
| 병합 불일치(MERGE_MISMATCH) | 실제 병합 결과가 검증 근거와 달라 서버가 완료를 보류한 상태 |
| 불안정 테스트(flaky) | 가끔만 실패하는 테스트. 격리하면 실패해도 통과를 막지 않는다 |
| 격리 | 불안정 테스트의 실패를 기록만 하고 판정에서 빼는 것 |
| job | 서버가 Runner에게 맡긴 일 하나. 다시 실행·배포 확인은 job을 만든다 |
| 멱등 키(Idempotency-Key) | 같은 요청을 두 번 보내도 한 번만 처리되게 하는 요청 번호 |
| 레일 | 상세를 볼 때 왼쪽에 좁게 남는 목록 |
| 펼치기 | 상세를 닫고 넓은 목록으로 돌아가기 |
| pixelmatch | 두 그림의 픽셀을 비교해 다른 픽셀 수를 세는 도구 |
