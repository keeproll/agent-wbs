# features/task — Task 상세(M3-03)

Task 하나의 요약과 9개 탭을 보여 주고 편집하는 화면이다.
원본은 `prototype/uiux/Main.dc.html`의 P L924–1355(UI-03E, UI-03F, UI-03-01~09)다.

- 처음이라면 이 문서 → [../../shared/README.md](../../shared/README.md)(공통 부품) 순서로 읽는다.
- 낯선 말은 맨 아래 [용어집](#용어집)에 있다.

## 1. 명령

저장소 루트에서 실행한다. `W`는 `pnpm -C agent-wbs`의 줄임이다.

| 명령 | 하는 일 |
|---|---|
| `W e2e -- task-detail` | **M3-03 완료 조건.** 가짜 서버로 요약·9탭·편집·승인·390px·화면 폭·시각 비교를 시험한다 |
| `W --filter @awbs/web e2e:api:task` | 실제 API와 전용 DB(demo seed)로 Task 상세를 시험한다(§5) |
| `W test -- task-editor` | 편집기 검사(중복 테이블·없는 FK 등) 단위 시험 |

- 다른 작업이 개발 서버 포트(5183)를 쓰고 있으면 `AWBS_E2E_PORT=5313`처럼 빈 포트를 준다.

## 2. 다른 화면에서 쓰는 법 — `<TaskDetail>`

WBS 화면(M3-02)은 레일 옆에 이 컴포넌트를 놓는다.
레일·필터·주소 바꾸기는 부모가 하고, 이 컴포넌트는 상세만 그린다.
왜: 같은 상세를 WBS 화면과 다른 화면(알림 링크 등)이 함께 쓰기 위해서다.

```tsx
import { TaskDetail, isTabKey, type TabKey } from '../task/TaskDetail.tsx';

<TaskDetail
  key={taskKey}                 // Task를 옮기면 새로 만든다(편집 상태가 다른 Task로 넘어가지 않게)
  taskKey="TASK-0007"
  projectId={project.id}
  tab={tab}                     // 'overview' | 'spec' | 'deps' | 'tech' | 'checklist' | 'exec' | 'verif' | 'hist' | 'msg'
  onTab={(next) => setSearch({ tab: next })}
  nav={{
    posLabel: '7 / 12',         // 레일 순서. 필터에 맞지 않으면 '목록 밖 (필터에 맞지 않음)'
    onPrev, onNext,             // 없으면 버튼이 꺼진다
    backTo: 'TASK-0006',        // 참조 링크로 왔을 때만. 「← TASK-0006로 돌아가기」
    onBack,
  }}
  onOpenTask={(key, ref) => …}  // 선행·후속·차단 링크. ref=true면 지금 Task를 복귀 스택에 쌓는다
/>
```

props 계약:

| prop | 뜻 |
|---|---|
| `taskKey` | 열 Task ID(예: `TASK-0007`). WBS 번호가 아니다 |
| `projectId` | WBS 목록(`listTasks`)을 읽을 프로젝트. 선행 Task 제목·상태와 의존성 후보에 쓴다 |
| `tab`, `onTab` | 지금 탭과 탭 바꾸기. 주소 `?tab=`에 두면 새로고침·공유해도 같은 탭이 열린다 |
| `nav` | 위쪽 위치·이전/다음·돌아가기. 부모가 레일 순서로 계산한다(G§4.3) |
| `onOpenTask` | 다른 Task로 이동. 편집 중이면 공통 편집 보호가 먼저 묻는다 |

- 주소 `/wbs/:taskKey`는 WBS 화면(M3-02 `WbsPage`)이 맡는다. 자기 레일 옆에 `<TaskDetail>`을 놓는다(M3 통합).
  - 연결은 `features/wbs/detail-slot.tsx` 한 파일이 한다(props 이름 바꿔 끼우기). M3-03의 임시 화면 `TaskDetailPage.tsx`는 지웠다.
- 키보드: ↑/K 이전, ↓/J 다음, Esc 펼치기(G§4.3)는 WBS 화면이 한다. 입력 칸 안에서는 동작하지 않는다.

## 4. 규칙과 이유

### 4.1 화면 모양 — 원본 그대로

- 원본과 **같은 마크업·클래스**(`.dt-head`, `.summary`, `.gtb`, `.sgrp` 등)를 쓴다. 새 CSS는 `task.css`에만 둔다.
  - 왜: `prototype.css`는 원본을 한 글자도 바꾸지 않고 옮긴 파일이라, 같은 클래스를 쓰면 모양이 자동으로 같아진다.
- 문구는 `labels.ts`와 각 탭에 원본 문구를 그대로 쓴다. 원본 줄 번호(P L…)를 주석에 남겼다.

### 4.2 서버 값만 보인다 — 값을 지어내지 않는다

- 계약(`TaskDetail`)에 없는 값은 보이지 않는다(UAT-EMPTY-01).
  - 예: 원본 Mock에만 있고 계약에 없는 값.
  - 시도의 지정 · 실제 하위 Agent 태그는 계약 `Attempt.subagents`에 생겨(UAT-TASK-10) 원본 P L1310처럼 보인다. 값이 없으면 태그를 그리지 않는다(`shared/subagents.ts`).
  - M3 통합: 예상 토큰·추정 주체/신뢰도/근거·실제 실행·실제 시작/완료·고정 시작일은 이제 계약(`TaskDetail`의 `estimate`·`actStart`·`actEnd`·`actualHours`·`fixStart`)에 있어 원본 P L1048–1059처럼 보인다.
  - 왜: 없는 값을 화면에서 계산하거나 「—」로 채우면 팀장이 사실로 오해한다.
- 선행 충족 여부는 서버의 `blocked`를 따르고, 차단 사유(FS 완료 필요 / SS 시작 필요)만 화면이 목록 상태로 적는다.

### 4.3 편집 — 한 번에 한 곳

- 편집 버튼을 누르면 그 영역만 편집 상태가 된다(`edit-slot.tsx`). 다른 편집 버튼은 꺼진다.
  - 왜: 여러 곳을 동시에 열면 저장 순서에 따라 버전 충돌이 나고, 무엇이 저장됐는지 헷갈린다(원본 `canEdit`).
- 입력이 바뀌면 `setDirty(true)`. 이때 탭·Task·메뉴 이동은 공통 확인창을 띄운다(UAT-STATE-09).
- 저장은 모두 `useTaskSave`를 쓴다. 공통 `useSave` 규칙을 그대로 받는다.
  - 저장 내용(payload)은 **누른 순간** 찍는다. 재시도는 같은 내용·같은 키·같은 버전으로 보낸다.
  - 편집기는 **편집을 시작한 순간의 값과 버전(updatedAt)을 고정**하고 그 버전으로 보낸다(`useTaskSave`의 `version`).
    - 왜: 화면은 3초마다 변경을 받아 Task를 새로 읽는다. 새로 읽은 버전으로 보내면 그 사이 다른 사람이 저장한 내용을 충돌 없이 덮어쓴다(독립 리뷰 R1).
    - 묶음으로만 저장되는 값(개요·명세)은 「서버 최신 값 + 내가 바꾼 칸」으로 보낸다. 내가 건드리지 않은 칸을 옛 값으로 되돌리지 않는다.
    - 기술 설계는 섹션 복사본 대신 「무엇을 바꿨는지」(`DesignOp`: 블록·엔티티 추가/수정/삭제, 섹션 제거)를 보낸다. 보낼 때마다 서버 최신 섹션 위에 그것만 적용하므로 「다시 적용」도 다른 사람이 고친 테이블을 되돌리지 않는다(재리뷰 P1).
  - 편집 대상은 **배열 위치가 아니라 편집을 시작할 때 고정한 안정 키**로만 정한다(재리뷰2 P1).
    - 기술 설계 엔티티: 테이블명·「방식 경로」를 `EditorDraft.target`에 고정한다. 저장·「다시 적용」·편집기 검사(중복 테이블·FK·중복 Endpoint)가 모두 이 이름을 쓴다.
    - 체크리스트 `itemKey`, 선행 관계 `dependency.id`, 명세 섹션 키, 등급 역할(dev·qa), 분할 규칙 키도 같은 원칙이다. AC·산출물 표는 목록 전체를 한 번에 저장한다(행 ID가 계약에 없음).
  - 성공 콜백은 **실제로 성공한 요청 내용**으로 불린다. 보내지 못하고 막힌 새 초안은 「다시 적용」·성공 처리에 쓰지 않는다(재리뷰 P2).
  - 성공해도 **저장한 내용과 지금 입력이 같을 때만** 편집을 닫는다. 재시도 사이에 더 고친 입력을 지키기 위해서다.
  - 409 충돌 창의 「다시 적용」은 최신 Task를 읽고 같은 내용을 새 버전으로 다시 보낸다.
    - M3 통합: 공통 `useSave`의 `reapplyRequest`로 옮겼다. 응답을 잃으면 같은 내용·같은 키로만 다시 보낸다(shared/README §3).
  - 409 충돌 창의 「최신 불러오기」는 서버에서 Task를 실제로 읽은 뒤에만 편집을 닫는다. 읽기가 실패하면 창 안에 이유를 보인다(M3-02 7cddacd 공통 규칙).
  - 응답에 Task가 없으면(의존성 추가·삭제, 분할 요청) Task를 다시 읽는다.
- 체크리스트 새 항목 입력도 편집 자리에 올린다. 이동은 확인을 묻고, 추가가 성공해도 그 사이 더 입력한 내용은 지우지 않는다(R5).
- 로그인이 끊기면(401) 편집 중이던 초안을 탭 안에 보관하고, 다시 로그인하면 「복원 / 버리기」를 묻는다(공통 `useSessionDraft`).
  - Task마다 편집 자리가 하나라 초안 이름도 `task:<TaskID>:edit` 하나다. 편집기는 `slot.report(초안)`으로 알리고 `slot.restored`로 되살린다.

### 4.3-1 읽기 실패와 잘못된 데이터

- 실행·검증·이력·메시지 목록을 못 읽으면 「불러오는 중」에 머물지 않고 원인 카드와 「다시 시도」를 보인다(R6). Evidence 실패는 「없음」과 구분한다.
- 저장된 설계 content가 예상 모양이 아니면 읽을 수 있는 부분만 그리고 「읽을 수 없는 항목 n건」을 알린다(`normalizeDesign`, R4).
- 그래도 탭을 그리다 예외가 나면 그 탭에만 「이 탭을 표시하지 못했습니다」를 보인다(`TabBoundary`). 메뉴·머리·다른 탭은 계속 쓴다.

### 4.4 저장 전 검사 — 기술 설계

- 화면이 저장 전에 검사한다(`editor-model.ts` `validateDraft`, 원본 P L5549–5591).
  - 중복 테이블, 없는 FK(없는 대상을 가리키는 외래키), nullable PK('값 없음'을 허용한 기본키), 없는 인덱스 컬럼.
  - 중복 Endpoint(같은 HTTP 방식+주소), 3자리가 아닌 HTTP 상태, 규칙에 맞지 않는 환경 변수 이름.
- 오류가 있으면 「저장」이 꺼지고, 오류 목록과 칸 표시(`aria-invalid`)가 보인다. 초안은 그대로 남는다.
- 왜 화면이 하나: 서버가 설계 내용을 검사하지 않고 그대로 저장하기 때문이다(보고함). 다른 Task의 테이블을 알기 위해 DB 관련 Task 상세를 함께 읽는다.
- 설계 섹션 제거는 빈 내용 `{}`을 저장해서 한다. 화면은 `{}`를 「섹션 없음」으로 본다(설계 섹션 삭제 API가 없음, 보고함).

### 4.5 착수 승인(원본에 없는 화면)

- `planning`: 「착수 승인 요청」. 명세 필수 항목이 비면 서버가 400으로 거부하고, 오류 막대에 고칠 항목이 보인다.
- `approval`: 「승인」(→ `ready`)·「반려」(→ `planning`, 사유 선택 입력).
- 승인만으로 실행하거나 완료하지 않는다. 실행은 [작업 실행]에서 따로 요청한다(UAT-APPROVE-01).
- 실제 서버는 분할 기준 판단(규칙 5·7·9) 기록이 없으면 승인을 `409 SPLIT_JUDGEMENT_REQUIRED`로 막는다(D-33). 화면은 이 거부를 오류 막대로 보이고 상태를 그대로 둔다.

### 4.6 화면 폭(D-28)

- 1280·1920: 9탭 모두 페이지 가로 스크롤이 없다.
- 1280 미만: 표는 원본 `.gtb`(가로 스크롤 상자) 안에서만 밀린다.
- 1100px 이하: 원본처럼 상세가 전체 화면으로 열린다.
- 560px 이하(휴대폰)는 요약을 한 줄 1칸으로 바꾸고, 머리가 화면을 다 차지하지 않게 **상세 전체를 세로로 스크롤**한다(`task.css`, R2). 원본은 머리를 고정해 본문이 수십 px만 남는다.
- 390px 알림 링크: 로그인 → 원래 주소로 돌아와 상세를 읽는다. 휴대폰 편집·승인은 필수로 요구하지 않는다(UAT-RESP-02-TASK).

- **합격 기준**: 같아야 하는 영역은 차이 1% 이하. 넘으면 시험이 실패한다.
  - 대상: 상세 머리, Gate 펼침, 작업 명세, 의존성, 기술 설계, 체크리스트, 검증·Evidence, 이력, 메시지.
- **예외(기록만 하고 실패시키지 않음)**: 계약에 값이 없어 칸이 빠진 영역이다.
  - 개요(UI-03-01): M3 통합에서 추정·실제 칸을 넣었다. 남은 차이는 시험 자료 값이다(기록만).
  - 실행(UI-03-06) 패널 전체: 지정/실제 하위 Agent 태그는 생겼다. 남은 차이는 CI 참조가 원본 버튼 대신 링크 모양(M7-05)이라 줄 위치가 1~2px 다른 것(기록만).
    - 대신 태그 영역(`UI-03-06-tags-ATT-0004-1`·`-2`)은 요소 위치로 맞춰 따로 비교하고, 차이 1%를 넘으면 실패한다(측정 0.00%).

## 7. 서버 작업을 기다리는 자리(독립 리뷰 R3·R8)

- 등급 변경·고정: 서버에 PUT·DELETE 등급 라우트가 있다. 서버가 404를 줄 때만(옛 서버) 「서버 기능이 준비되면 사용할 수 있습니다」를 보인다.
- 작업량·예상 토큰·고정 시작일(M3 통합): 개요 편집에서 고치고 `updateTask`의 `estimate`(낙관·예상·비관·토큰 네 값 한 묶음)·`fixStart`로 저장한다.
  - 검사 규칙(0<시간≤400, 낙관≤예상≤비관, 토큰 정수, 날짜 형식)은 `editor-model.ts estimateErrors`다. 바꾼 칸만 검사한다.
  - 저장하면 서버가 일정을 다시 계산한다. 화면은 응답 Task로 다시 그린다.
- 기술 설계 서버 검사: 서버가 400으로 거부하게 되면 공통 오류 막대가 고칠 항목을 보인다. 화면 검사는 그대로 둔다.
