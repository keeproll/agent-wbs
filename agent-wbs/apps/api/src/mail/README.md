# apps/api/src/mail — 보고서 메일(M6-03)

보고서를 HTML 메일로 보내는 서버 부분이다.
SMTP 설정, 받는 사람, 메일 본문 만들기, 발송 큐, 발송 worker가 여기 있다.
낯선 말은 맨 아래 [용어](#용어)에 모았다.

- 근거: 가이드 G§4.11 L398-408(메일 발송), §8.5(API 표), §9.6-6 L1049-1052(구현 규칙), contracts §2.3·§4.4, data-model §3.7.
- 실제 메일 서버에는 연결하지 않았다. 시험은 로컬 가짜 SMTP 서버(`e2e/fakes/smtp.ts`)로 한다.
  - Q-13은 결정 A다: owner의 SMTP 계정으로 보내고, 외부 수신자에게는 링크 없이 PDF만 보낸다(§5-1).
  - 실제 계정 연결은 M8-06 전에 owner가 설정 화면에서 한다(open-questions Q-13). 그래서 시험은 여전히 가짜 SMTP만 쓴다.

## 1. 파일 지도

| 파일 | 하는 일 |
|---|---|
| `routes.ts` | API 경로 등록(계약 `settings.ts`의 메일 operation 13개) |
| `settings.ts` | SMTP 설정 조회·저장·연결 확인, 받는 사람 추가·변경·삭제 |
| `secret.ts` | SMTP 비밀번호 암호화 보관과 꺼내기 |
| `render.ts` | 메일 제목·HTML·text/plain 만들기(미리보기와 발송이 함께 씀) |
| `queue.ts` | 발송 큐에 넣기(정기·테스트·수동·다시 보내기), 발송 기록 목록, 대시보드 알림 |
| `deliver.ts` | 발송 worker(찜하기 → SMTP → 기록), 재시작 정리 |
| `smtp.ts` | SMTP 한 번 보내기·연결 확인, 결과 분류(수락 / 확실한 실패 / 수락 여부 불명) |

## 2. 한 통이 나가는 길

1. 정기 보고서가 생기면 같은 트랜잭션에서 구독자를 큐(`mail_outbox`)에 넣는다(`reports/service.ts` → `enqueueReportMail`).
   - 큐에 넣기만 하고 SMTP는 부르지 않는다.
   - 왜: 메일 서버 오류가 보고서 생성을 실패시키면 안 된다(G L1050).
   - 기간 지정 보고서는 자동으로 보내지 않는다. 「메일로 보내기」(수동 발송)로만 보낸다(G L401).
2. worker가 보낼 차례인 줄 **한 통**을 `sending`으로 바꾸고 **먼저 커밋한다**(찜하기).
   - `for update skip locked`로 찜하므로 worker가 둘이어도 한 줄은 한 번만 나간다.
   - 한 통씩 찜한다. 왜: 여러 통을 한꺼번에 찜하면, 한 통의 결과 저장이 실패했을 때 아직 보내지 않은 메일까지 `sending`에 묶인다(리뷰 지적 1).
   - 찜하기 직전에 지금의 받는 사람 목록으로 다시 확인한다. 받는 사람을 지웠으면 보내지 않고 `failed`(「받는 사람이 삭제되어 보내지 않음」)로 적는다.
3. 트랜잭션 밖에서 SMTP를 부른다.
4. 결과를 그 줄과 `mail_log`(추가 전용 기록)에 적는다.
   - 결과 저장이 DB 오류로 실패하면 메일은 다시 보내지 않고 **기록만** 몇 번 다시 시도한다.
   - 끝내 적지 못하면 그 줄만 `unknown`(「발송 결과를 저장하지 못함 — 수락 여부 불명」)으로 적고 다음 메일로 넘어간다. 예외로 주기를 끝내지 않는다.
   - 그것도 못 했으면 다음 주기 시작의 정리가 맡는다: 「SMTP 응답 대기의 10배 + 2분」보다 오래 `sending`인 줄은 `unknown`으로 바꾼다(프로세스 재시작을 기다리지 않는다).

예: 팀장이 일간·주간을 모두 구독하면, 월요일 07:00에는 일간 1통·주간 1통이 큐에 들어간다.

## 3. 결과별 처리

| SMTP 결과 | 상태 | 그다음 |
|---|---|---|
| 서버가 수락(250) | `accepted` | 끝 |
| 수락되지 않은 것이 확실(연결 실패, 로그인 거부 535, 명시적 거부 4xx·5xx, SMTP 미설정) | 첫 실패면 `retry_wait`, 자동 재시도 뒤에도 실패면 `failed` | 15분 뒤 같은 줄을 **한 번만** 다시 보낸다 |
| 받는 사람이 삭제됨(찜하기 직전 확인) | `failed` | 보내지 않는다. 다시 보낼 대상에서도 빠진다 |
| 본문을 보낸 뒤 응답을 못 받음(timeout·연결 끊김) | `unknown` | 자동으로 다시 보내지 않는다 |
| 보내는 중 worker가 죽음 | (`sending`으로 남음) → 다음 시작 때 `unknown` | 자동으로 다시 보내지 않는다 |

- 왜 unknown은 다시 보내지 않나: 서버가 이미 받았을 수 있다. 가이드는 메일이 두 번 나가면 안 된다고 했다(G§9.6-6, contracts §4.4).
  - 팀장은 발송 기록의 「수락 여부 불명」 안내를 보고 직접 「다시 보내기」를 누른다.
- 어떻게 「본문을 보냈는지」 아나: nodemailer 오류는 연결 실패와 응답 유실을 둘 다 `command: 'CONN'`으로 알린다(직접 확인함).
  - 그래서 메일 원문을 넘기는 스트림이 처음 읽힌 순간(서버가 DATA에 354로 답한 뒤)을 기록해 둘을 가른다(`smtp.ts`).
- 15분은 **실패를 기록하는 순간의 DB 시각**부터 센다. 보낼 차례인지도 DB 시각으로 판정한다(시험은 `now`로 시각을 정한다).
  - 왜: 느린 서버를 기다린 시간만큼 재시도가 앞당겨지면 안 된다(리뷰 지적 6).
  - 왜 DB 시각인가: 이 PC의 시계는 약 32초마다 2.3초 뒤로 간다. 기록과 판정을 같은 시계로 하면 시계가 뒤로 가도 재시도가 늦어질 뿐 앞당겨지지 않는다.
- failed·unknown이 남아 있으면 대시보드 알림(`alerts`, 키 `mail:failed`)을 연다. 모두 해소되면 닫는다.
  - 「해소」는 같은 보고서·같은 사람에게 그 뒤에 다시 보낸 발송이 있다는 뜻이다.

### 3-1. 결과 전이표(늦은 응답 · 정리와 겹칠 때)

결과가 도착하면 `transition.ts`의 표 하나로 상태를 정한다. 모든 칸은 `test/mail-transition.test.ts`가 시험한다.

- 찜할 때마다 새 **시도 ID**(`mail_outbox.attempt`)를 매긴다. 결과는 그 시도가 아직 현재일 때만 상태를 바꾼다.
  - 낡은 시도의 결과는 상태를 바꾸지 않고, 받은 응답만 이력(`mail_log`)에 「늦은 응답(상태 변경 없음 …)」으로 남긴다.
- `unknown`에서 바뀌는 늦은 결과는 **수락(250)뿐**이다(→ `accepted`).
  - 늦은 거부(451 등)는 이력에만 남기고 자동 재시도를 다시 켜지 않는다.
  - 왜: `unknown`이 된 뒤 사람이 「다시 보내기」로 새 발송을 만들 수 있다. 늦은 거부로 원본을 재시도에 올리면 프로그램이 한 통을 더 보낸다(Codex 재리뷰 재현).
- `retry_wait`로 가는 칸은 「현재 시도 · `sending` · 명시적 거부 · 자동 재시도 전」 하나뿐이다.

| 현재 상태(현재 시도) | 수락 | 확실한 거부 | 응답 유실 | 기록 실패 |
|---|---|---|---|---|
| sending | accepted | retry_wait(재시도 뒤 failed) | unknown | unknown |
| unknown | accepted | 그대로 · 이력만 | 그대로 · 이력만 | 그대로 |
| queued · accepted · retry_wait · failed | 그대로 | 그대로 | 그대로 | 그대로 |
| (낡은 시도 — 모든 상태) | 그대로 · 이력만 | 그대로 · 이력만 | 그대로 · 이력만 | 그대로 |

## 4. 멱등 키와 발송 번호

- 큐 한 줄의 키는 「보고서 ID + 받는 사람 ID + 발송 번호(`try_no`)」다(DB 고유 제약).
- 같은 보고서를 같은 사람에게 다시 보내면 발송 번호가 하나 늘어난 **새 줄**이 생긴다.
  - 왜: 이전 발송의 결과(실패·불명)를 지우지 않아야 「몇 번 나갔을 수 있는지」 알 수 있다.
- 15분 자동 재시도는 새 줄이 아니라 **같은 줄**을 다시 보낸다(`retry_wait → sending`, `retried=true`).
- 이미 해소된 실패 줄에 「다시 보내기」를 누르면 409 `INVALID_TRANSITION`이다. 두 탭에서 동시에 눌러도 한 번만 나간다.
- 받는 사람을 삭제했으면 「다시 보내기」는 409 `INVALID_TRANSITION`(「받는 사람이 삭제되어 다시 보낼 수 없습니다」)이다. 원본도 같다(P resend L4969, UAT-MAIL-05).
  - 삭제한 사람의 실패는 「해소되지 않은 실패」(실패만 · 배지 · 알림 · 실패 건 모두 다시 보내기)에서 빠진다. 발송 기록은 주소와 함께 남는다.
  - 삭제와 다시 보내기가 겹치면 받는 사람 줄을 `for share`로 잡아 차례로 판정한다.
- 줄마다 발송 표시 번호 `ML-0001`(`log_key`)이 있다. 프로젝트 카운터(`counters` kind `mail_log`)로 매기며, 초기화하면 1부터 다시 시작한다.
  - 다시 보내면 사유가 원본처럼 「다시 보내기 (ML-0001)」이다. 어떤 실패 기록을 다시 보냈는지 가리킨다(P resend L4970).

## 5. 메일 본문 규칙(G L1049)

- 표(`<table>`) 레이아웃, 모든 모양은 인라인 스타일, 폭 640px.
- `<style>`·외부 CSS·class·flex/grid·외부 이미지·스크립트·웹 폰트를 쓰지 않는다.
  - 왜: Outlook·Gmail 같은 메일 앱은 이것들을 지우거나 무시한다.
- 글꼴 순서: `'Pretendard GOV','Apple SD Gothic Neo','Malgun Gothic',sans-serif`.
- 서식 없는 본문(text/plain)을 함께 보낸다(multipart/alternative).
- 본문은 보고서 전체가 아니라 요약이다(G L403).
  - 팀장용: 핵심 지표 4개 + 팀장 확인 필요 · 완료한 Task · 진행 중 · QA 실패 · 일정 재조정 · 다음 예정.
  - 보고용: 핵심 지표 4개 + 요약 · 주요 완료 항목 · 위험 · 이슈 · 다음 계획. Task ID 같은 내부 용어가 0건이다.
  - 지표 이름과 보고용 요약 · 위험 문장은 **원본 메일 문구**(P mailHtml L4006-4014) 그대로다.
    - 팀장용 지표: 완료 (기간) · 완료율 (작업량) · 완료 예상 (vN) · 가동률(중단 N회 / 중단 없음).
    - 보고용 지표: 완료 · 진척률 · 완료 예상일 · 목표일 대비.
    - 왜: 원본 프로토타입이 완료 기준이다(coordinator 판단 2026-11-27). 화면 보고서의 지표 이름 · 문장과는 조금 다르다.
  - 숫자는 화면 보고서와 같은 계산(shared `reportFigures`, `internalKpis`·`externalView`가 쓰는 것)에서 온다. 그래서 화면 · 메일의 숫자가 같다.
- 일간 보고서는 항상 팀장용이다(G L402).
- 「Agent WBS에서 전체 보고서 보기」 링크는 접속 주소(`app_settings.app_url`, 설정 → 알림)가 있을 때만 넣는다.
- 외부 수신자 메일에는 접속 주소가 있어도 링크를 넣지 않는다(§5-1).

## 5-1. 외부 수신자(Q-13 결정 A)

외부 수신자는 회사 밖이나 다른 네트워크에서 메일을 읽는 사람이다(예: 상급 기관 담당자, 협력사).
받는 사람마다 `external`(외부 여부)을 둔다. 기본값은 내부(false)라서 지금까지의 받는 사람은 그대로 동작한다.

- 근거: G L1052(링크는 같은 PC · 같은 네트워크에서만 열림, 외부 수신자는 PDF 첨부 권장), G L1153(미결 9), open-questions Q-13(결정 A).
- 원본 프로토타입에는 외부 구분이 없다. 원본의 상급자(RC-2)는 「보고용 + PDF」일 뿐 외부 표시는 없다(P L3640).
  - 그래서 원본 화면을 최소로 바꿨다: 받는 사람 행과 추가 폼에 「외부」 단추 하나를 더했다(화면 README §3).

규칙:

- 외부 수신자는 **보고용 · PDF 첨부**로 고정이고, **일간 보고서를 받지 않는다.**
  - 왜 일간을 막나: 일간 보고서는 팀장용(Task ID 같은 내부 용어 포함)만 있다(G L402). PDF도 일간은 팀장용만 만든다.
  - DB 검사(`recipient_external`, `mail_outbox_external`)도 같은 규칙을 지킨다. API를 거치지 않은 쓰기도 막기 위해서다.
- 외부 수신자 메일 본문에는 **앱 링크와 내부 경로가 0건**이다.
  - 「전체 보고서 보기」 링크를 빼고, 바닥글의 「설정 → 보고서 · 메일」 안내를 「보낸 담당자에게 알려 주세요」로 바꾼다.
  - 본문은 보고용이므로 Task ID 같은 내부 용어도 0건이다(§5).
- PDF를 만들지 못하면 외부 수신자에게는 보내지 않는다(보내기 전 실패 → 15분 뒤 한 번 다시).
  - 왜: 링크가 없으므로 PDF가 외부 수신자가 볼 수 있는 유일한 전체 보고서다.
- 한 번 발송에 내부 · 외부가 섞여도 **받는 사람마다 따로 한 통**이 나간다(큐 한 줄 = 한 사람).
  - 그래서 외부 수신자가 내부 메일의 받는 사람(To · Cc · Bcc)에 함께 들어가는 일이 없다.
- 멱등 키(§4)와 결과 전이표(§3-1)는 바뀌지 않았다. 외부 줄도 같은 표를 따른다.

변환 함수 하나와 검사기(Codex 리뷰 fix1 · fix2):

- 외부로 나가는 **모든 글**(헤더 · HTML · text/plain · 보고용 PDF · 첨부 이름)은 shared의 `externalText` 하나를 지난다.
  - **외부 수신자에게만** 적용한다(Q-13 fix4). 내부 수신자의 팀장용 · 보고용과 팀장 화면 · 다운로드 PDF는 바뀌지 않는다. 보고용에서는 작업 제목의 내부 용어만 뺀다(`scrubInternal`, M6-01 규칙).
    - 외부 수신자용 PDF는 따로 만들고(외부 변환 · 검사), 캐시하지 않는다. 팀장 다운로드 · 내부 수신자용 PDF 캐시를 덮어쓰지 않기 위해서다.
  - **마지막 규칙(Q-13 fix5 · 후속)**: 정규화한 글을 공백으로 나눈 토큰 가운데 (a) `@`가 있거나, (b) 두 글자 사이의 점(`.`) 바로 앞이나 뒤가 글자(숫자 · 공백 · 문장부호 · 기호가 아닌 것 — `\p{L}` 글자와 `\p{M}` 결합 문자 포함, 예: `कंपनी.example`, `a̸.local`)이거나, (c) 숫자만 점으로 4덩이 이상(IPv4 모양)이면 통째로 「(주소 생략)」이다.
    - (d) 의미 규칙(fix5 후속 3): 앞뒤 문장부호를 뗀 토큰을 `new URL('http://' + 토큰)`으로 읽어 성공하고, hostname에 점이 있으면 주소다. 단 hostname이 숫자와 점뿐이거나(숫자를 IPv4로 읽은 결과) 적힌 마지막 이름이 숫자로 시작하면(「2.5일」) 아니다.
      - 왜: 문자 분류를 하나씩 늘리면 빠짐이 남는다(`ג׳.example`의 U+05F3, Codex 재리뷰 7). 브라우저가 호스트로 받아들이는 것은 문자 종류와 무관하게 막는다. 밑줄 사설 별칭(`api_.local`)도 막힌다.
    - 숫자 사이 점(「2.5일」, `1.2.3`, `12.34%`)은 유지한다. 왜: 기간 · 수치 · 버전은 보고 내용이다.
    - 내부 호스트는 최상위 이름이 글자라 점 옆에 늘 글자가 있어 (b)에 걸린다. 숫자뿐인 호스트는 (c)가 잡는다. 이메일 · 혼합 표기(`내부.xn--…`, `"help"@intranet…`)도 같다(Codex 재리뷰 5).
    - 문장 끝 점(「완료했습니다.」)은 두 글자 사이가 아니라 해당하지 않는다.
    - 정보 손실(조정자 판단으로 수용): 점으로 이은 단어(「프로젝트.완료」, `e.g.`), 파일 이름(`file.txt`), 제품 이름(`Node.js`)은 생략된다.
    - 아래의 이메일 · IDN · 맨 호스트 규칙(fix3 · fix4)은 이 규칙으로 바뀌었다. 점이 없어도 링크인 스킴 주소 · 호스트:포트 · 경로 · 대괄호 IPv6만 따로 「(링크 생략)」으로 바꾼다.
  - **주소처럼 보이는 것은 모두 「(링크 생략)」으로 바꾼다.** 어느 서버 주소인지 가리지 않는다. 일반 외부 주소도 예외가 없다.
    - 주소 모양: 스킴 있는 주소(`http://` · `https://` · `ftp://` · `//…`), `www.…`, 대괄호 IPv6, 숫자 IP(점 셋 이상), 호스트:포트(`localhost:5173`, `127.1:5173`), 호스트/경로(`example.org/spec`), 경로형(공백 · 괄호 뒤 `/report/…`).
    - 왜: 결정 A는 「외부 수신자에게는 링크 없이」다. 같은 주소를 여러 글자(`127.1`, `2130706433`, `%77bs…`)로 적을 수 있어, 우리 앱 주소만 가려내려 하면 빠짐이 생긴다(Codex 재리뷰 1).
    - 맨 호스트(스킴 · 포트 · 경로 없음): 영숫자 · 하이픈 이름이 점으로 2개 이상 이어지고 마지막 이름이 글자 2자 이상(`wbs.corp.example`). 내부 호스트 이름이 새지 않게 한다. `file.txt` · `Node.js` 같은 이름도 지워지는 정보 손실은 받아들인다(조정자 판단).
    - 이메일 주소도 예외 없이 「(주소 생략)」(Q-13 fix4). 왜: `help@intranet.corp.example`처럼 이메일 뒤에도 내부 호스트 이름이 보인다. 바닥글의 받는 사람 자신의 주소(「수신: …」)와 From · To 헤더는 설정 · 받는 사람 값으로 따로 만들므로 상관없다.
    - 국제화 도메인(IDN, 「내부.한국」)은 표준 URL 해석기로 ASCII(punycode `xn--…`)로 바꾼 뒤 같은 맨 호스트 규칙으로 본다. `xn--…` 표기도 같다. 점으로 이은 한글 단어(「프로젝트.완료」)도 같은 모양이라 생략된다(정보 손실, 조정자 판단). 「2.5일」처럼 마지막 이름에 숫자가 있으면 아니다.
    - 내부 번호(Task ID · RP · 시도 번호)는 대소문자를 가리지 않는다(`task-0007`도 지운다).
    - 「1.2.3」처럼 숫자 세 덩이(점 둘 이상)도 IP 모양이라 바뀐다. 버전 번호 생략은 정보 손실이지만 받아들인다(조정자 판단). 「10.5%」 · 시각 「07:00」 · 날짜는 그대로다.
  - **판정 전에 정규화한다**(Q-13 fix3, `normalizeExternal`). 모양 규칙을 늘리지 않고 표기를 하나로 모은다.
    - HTML 글자 기호(`&#46;` · `&period;`)와 퍼센트 인코딩(`%2E`, 두 번 인코딩 포함)을 풀고, NFKC로 전각 글자를 기본 글자로 바꾼다.
    - 점류(。 ｡ ． 등)를 `.`으로 바꾸고, 폭 없는 글자 · 방향 제어 글자를 지운다.
    - 출력에도 정규화한 글을 쓴다. 예: 「프로젝트。완료」 → 「프로젝트.완료」.
    - 왜: 같은 주소를 여러 글자로 적을 수 있다(`192。168。0。10`, `wbs%2Ecorp%2Eexample`). 검사기도 정규화한 뒤 같은 규칙으로 본다.
  - 내부 용어(Task ID · RP · 시도 · 모델 · Effort · 토큰), 「설정 → …」 메뉴 안내, `href=`도 뺀다.
  - `scrubInternal`은 같은 함수의 옛 이름이다.
- 검사기 `externalLeaks`(글자) · `externalHtmlLeaks`(HTML: 보이는 글 + 링크 태그 · 속성)는 변환 함수와 **같은 기준**으로 「주소 모양 0건」을 본다. 세 곳에서 쓴다.
  - 메일 worker가 SMTP를 부르기 직전(`externalMailLeaks`): 보내는 사람 표시 이름 · 제목 · 첨부 이름 · 두 본문. 걸리면 보내기 전 실패.
  - 보고용 PDF를 만들기 직전(`externalPdfLeaks`). 걸리면 PDF를 만들지 않는다(메일은 보내기 전 실패).
  - 시험(단위 · 시나리오). 재리뷰 재현 자료(앱 주소의 다른 표기 · 일반 외부 주소)로 실제 메일과 실제 Chromium PDF를 검사한다.
- 헤더(Q-13 fix2, Codex 재리뷰 2):
  - 보내는 사람 표시 이름은 설정(`보내는 주소`의 `이름 <주소>`) 값을 **그대로** 쓴다. 대신 **허용 목록**을 통과해야 한다(Q-13 fix3, shared `parseSender`).
    - 형식: 「이름 <주소>」 또는 「주소」. 이름은 한글 · 영문 · 숫자 · 공백 · 하이픈만, 40자 이하, 내부 용어 0건. 그 밖의 글자(따옴표 · 괄호 · `=?…?=` · 줄바꿈 · 점 등)는 거부한다.
    - 왜 허용 목록인가: 메일 생성기는 인코딩 · 주석 · 따옴표 · 줄바꿈을 여러 방식으로 읽는다(Codex 재리뷰 3). 그 해석을 따라가며 검사하지 않고, 그런 문법이 될 글자를 받지 않는다.
    - 외부 메일의 From 헤더는 읽어 낸 이름 · 주소 두 값으로 만든다. 설정 글을 메일 생성기에 그대로 넘기지 않는다.
    - 저장할 때 걸리면 400(`from`, 규칙 `external`). 이미 저장된 옛 값이면 메일 서버 카드에 「설정 오류」가 뜨고, 외부 메일은 보내지 않는다(「설정 오류: 보내는 사람 이름이 허용 형식 …」, 15분 재시도 규칙).
  - 받는 주소(To)는 그 사람 자신의 주소다. Reply-To · Cc · Bcc는 넣지 않는다.
- 받는 사람을 외부로 바꾸면(`PATCH … external: true`) 그 사람의 아직 보내지 않은 줄을 그 자리에서 새 규칙으로 다시 정한다.
  - 대기(queued) · 재시도 대기(retry_wait)의 주간 · 기간 줄 → 외부 줄(보고용 · PDF · 링크 없음). 일간 줄 → 보내지 않고 `failed`.
  - 그 사람에게 팀장용 메일을 **보내는 중**(`sending`)이면 409 `INVALID_TRANSITION`이다. 왜: 이미 팀장용으로 만들어 SMTP로 가는 중이라 되돌릴 수 없다. 끝난 뒤 다시 바꾼다.
  - 외부 여부가 바뀌면(켜기 · 끄기 모두) 실패 목록 · 배지 · 대시보드 알림을 바로 다시 맞춘다(`syncMailAlert`).

경우별 처리:

| 경우 | 처리 |
|---|---|
| 수동 발송에서 「모두 팀장용」을 골랐는데 외부 수신자가 섞임 | 외부 수신자 줄만 보고용 + PDF로 큐에 넣는다 |
| 일간 보고서 수동 발송에 외부 수신자를 고름 | 400 `VALIDATION_FAILED`(`recipientIds`). 한 통도 큐에 넣지 않는다 |
| 외부 수신자 「테스트」 | 일간이 아닌 최신 보고서(주간 · 기간)로 보낸다 |
| 외부 수신자 · 일간 보고서 미리보기 | 400 `VALIDATION_FAILED`(`to`). 보낼 수 없는 메일은 미리 보이지 않는다 |
| 큐에 넣은 뒤 받는 사람을 외부로 바꿈(주간 · 기간) | 바꾸는 순간 그 줄을 외부 규칙(보고용 · PDF · 링크 없음)으로 바꾼다. 그때 다른 worker가 찜하던 줄은 찜하기 직전 확인이 같은 규칙으로 바꾼다 |
| 큐에 넣은 뒤 받는 사람을 외부로 바꿈(일간) | 보내지 않고 `failed`(「받는 사람이 외부 수신자로 바뀌어 보내지 않음」) |
| 그 사람에게 팀장용 메일을 보내는 중에 외부로 바꿈 | 409 `INVALID_TRANSITION`. 보내는 중인 메일은 되돌릴 수 없으므로 끝난 뒤 바꾼다(Codex 리뷰 fix1 §3) |
| 다시 보내기 | 처음 보낼 때 외부였거나 지금 외부면 외부 규칙으로 새 줄을 만든다. 일간이면 409 `INVALID_TRANSITION` |

- 「외부로 바뀐 사람의 일간 실패」는 다시 보낼 수 없으므로 「해소되지 않은 실패」(실패만 · 배지 · 알림 · 실패 건 모두 다시 보내기)에서 뺀다.
  - 왜: 빼지 않으면 다시 보내기가 늘 409라 알림이 영영 닫히지 않는다. 삭제한 받는 사람의 실패를 빼는 것(§4)과 같은 이유다.
- 「외부」를 켜면서 함께 보내지 않은 칸은 서버가 외부 규칙(일간 끔 · 보고용 · PDF)으로 맞춘다. 함께 보낸 칸이 규칙과 어긋나면 400이다.
  - 예: `{external: true}`만 보내면 일간이 꺼진다. `{external: true, daily: true}`는 400이다.
  - 일간이 꺼져 구독이 하나도 없으면, 지금까지처럼 자동으로 중지된다.

## 6. SMTP 설정과 비밀번호

- 비밀번호는 AES-256-GCM으로 암호화해 `secrets` 표에 둔다(키는 환경 변수 `AWBS_SECRET_KEY`). 형식은 GitHub 토큰 보관과 같다.
- API 응답·로그·내보내기에는 `pwSet`(등록 여부)만 나간다. 비밀번호 끝자리(`last4`)도 남기지 않는다.
  - 왜: 토큰과 달리 비밀번호는 일부만 보여도 추측에 도움이 된다.
- 편집 버전은 `settings_version`이다. 연결 확인 결과(정상/실패·시각·오류)는 같은 줄에 적지만 편집 버전을 올리지 않는다.
  - 왜: 수정 폼을 열어 둔 채 「연결 확인」을 눌렀다고 저장이 409 충돌이 되면 안 된다.
- 연결 확인은 시작할 때의 편집 버전을 기억한다. 확인하는 동안 설정이 바뀌었으면 결과를 저장하지 않고 「연결을 확인하는 동안 SMTP 설정이 바뀌었습니다」로 답한다(리뷰 지적 5).
  - 왜: 옛 서버의 「정상」이 새 서버에 붙으면, 연결할 수 없는 서버가 정상으로 보인다.
- 화면의 수정 폼은 **폼을 연 순간의 버전**으로 저장한다(리뷰 지적 4). 다른 탭이 먼저 저장했으면 409 → 충돌 창(최신 불러오기 / 최신에 다시 적용).
- 계약의 보안 값 셋(`STARTTLS` · `SSL/TLS` · `없음`)과 DB 구조는 유지한다. 운영(`NODE_ENV=production`)에서는 `없음` 저장을 400으로 거부하고, 이미 저장된 평문 설정도 연결 확인·발송 전에 거부한다.
- 화면은 `STARTTLS` · `SSL/TLS`만 고를 수 있다. `STARTTLS`는 로그인·본문 전에 TLS 협상이 성공해야 하며, 두 방식 모두 인증서와 서버 이름을 확인한다.

## 7. 초기화와 경합(data-model §5)

- 「설정 유지」 초기화: SMTP·받는 사람은 남고 큐·발송 기록은 지운다. 기본(설정 삭제): 모두 지우고 SMTP 비밀번호도 지운다(`reset_project`).
- worker의 찜하기와 기록은 모두 세대 번호(epoch) 잠금 안에서 한다.
  - 초기화가 먼저 끝났으면 옛 세대로 찜할 수 없다(AW001 → 아무것도 보내지 않음).
  - 이미 SMTP로 보낸 뒤 기록하려는데 세대가 바뀌었으면 결과를 버린다. 지워진 발송 기록을 새 세대에 되살리지 않는다.
- 이미 나간 메일은 회수할 수 없다. 그래서 초기화 확인 화면이 「보내는 중」 건수(`reset-preview`의 `sending.mail`)를 미리 보인다.

## 8. worker

- `runner/worker.ts`에 메일 주기(10초)를 따로 두었다. 시작 때 한 번 `recoverMail`(보내다 죽은 줄 → unknown)을 부른다.
  - 왜 따로인가: SMTP 응답을 오래 기다려도 Runner 생존 감시(20초 주기)가 밀리지 않게 하기 위해서다.
- 한 번에 최대 20통을 찜한다. 운영 SMTP 응답 대기는 60초, 연결 확인은 15초다.

## 9. M6 통합에서 붙일 연결 지점

M6-01(보고서 화면) · M6-02(PDF)가 끝난 뒤 M6 통합에서 붙인다. 지금은 연결 지점만 준비했다.

- **PDF 첨부(M6-02)**
  - 붙이는 곳: `deliverMail(pool, epoch, { pdf })`의 `pdf: (reportId, view) => Promise<Buffer | null>`. worker(`runner/worker.ts` 메일 주기)에서 넘긴다.
  - 이미 있는 것: 큐 줄의 `pdf`(첨부 여부, 일간은 항상 false), 파일 이름 `pdfName()`(예: `RPT-W-261027_보고용.pdf`), 미리보기 응답 `attachment`.
  - PDF를 만들지 못하면 보내기 전 실패(`rejected`)로 처리한다. 수락되지 않은 것이 확실하므로 15분 재시도 규칙을 따른다.
  - 지금은 `pdf`를 넘기지 않아, 받는 사람의 「PDF 첨부」가 켜져 있어도 HTML만 나간다.
- **보고서 화면의 「메일 미리보기 · 메일로 보내기 · 발송 기록 펼침」(M6-01 화면, G L405)**
  - 미리보기: `GET /api/reports/:reportId/mail/preview?view=&to=`. 화면 부품은 `features/settings/report/ReportMailTab.tsx`의 `MailPreview`(export)를 그대로 쓸 수 있다.
  - 메일로 보내기: `POST /api/reports/:reportId/mail {recipientIds, view?}`. 기본 선택은 그 종류 구독자(P openSend L4975), 보기는 「모두 팀장용 / 모두 보고용 / 수신자 기본값」(`view` 생략).
  - 발송 기록 펼침: `GET /api/mail/log` 결과를 `reportId`로 거른다.
- 실제 SMTP 계정 연결(Q-13 결정 A: owner SMTP. 계정은 M8-06 전에 owner가 설정한다).

## 용어

| 용어 | 뜻 |
|---|---|
| SMTP | 메일을 보내는 표준 방식(메일 서버). 응답 번호 2xx 성공, 3xx 계속, 4xx 일시 실패, 5xx 영구 실패 |
| 큐(outbox) | 보낼 메일을 적어 두는 작업 표. worker가 차례로 꺼내 보낸다 |
| 찜하기(claim) | worker가 한 줄을 「내가 보낸다」고 표시하고 커밋하는 것 |
| 멱등 키 | 같은 요청이 두 번 와도 한 번만 처리되게 하는 고유 키 |
| unknown(수락 여부 불명) | 보냈지만 서버가 받았는지 모르는 상태. 화면에는 「실패 — 수락 여부 불명」 |
| epoch(세대 번호) | 초기화할 때마다 1씩 느는 번호. 초기화 전 작업이 초기화 뒤 데이터를 건드리지 못하게 막는다 |
| multipart/alternative | HTML 본문과 글자만 있는 본문을 함께 담는 메일 형식. 메일 앱이 읽을 수 있는 쪽을 보인다 |
| text/plain | 서식 없이 글자만 있는 본문 형식 |
| fake(가짜) SMTP | 실제 메일 서버 대신 시험에서 쓰는 로컬 서버. 메일을 밖으로 내보내지 않는다 |
| 외부 수신자 | 회사 밖 · 다른 네트워크에서 메일을 읽는 사람. 앱 링크가 열리지 않으므로 링크 없이 보고용 + PDF만 받는다(Q-13 결정 A) |
| 내부 경로 | 앱 안의 화면 위치(예: `/report/…`, 「설정 → 보고서 · 메일」). 외부 수신자 메일에는 넣지 않는다 |
| multipart/mixed | 본문과 첨부 파일(PDF)을 함께 담는 메일 형식. 본문(multipart/alternative)이 그 안에 들어간다 |
