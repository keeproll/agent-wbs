# 보고서 PDF (M6-02)

보고서 PDF(인쇄·배포용 문서 파일 형식)를 서버에서 만든다.
주소는 `GET /api/reports/:reportId/pdf?view=int|ext`이다(G§8.5 L944). 팀장 세션이 필요하다.

## 한눈에 보기

1. 저장된 보고서 기록과 **스냅샷**(어느 순간의 데이터를 그대로 찍어 둔 것)만 읽는다.
   - 프로젝트 이름도 스냅샷의 `projectName`이다. 지금의 프로젝트 이름 같은 현재 값은 읽지 않는다.
   - 옛 보고서(M6-01 형식, 이름 없음)는 마이그레이션 0047이 다룬다. **추측하지 않는다.**
     - 스냅샷 계약: `projectName`(문자 또는 null) + `projectNameStatus`(이름의 출처).
       - `snapshot`: 생성할 때 기록한 이름(새 보고서는 늘 이것이고 이름이 반드시 있다).
       - `filled`: 이름을 바꾼 기록이 전혀 없는 프로젝트의 옛 보고서. 이름이 한 번도 바뀌지 않았으니 지금 이름이 그때 이름이다.
       - `unknown`: 이름을 바꾼 기록이 하나라도 있는 프로젝트의 옛 보고서. 그때 이름을 확실히 알 수 없어 `projectName = null`이다. 화면·PDF는 「이름 미상(기존 보고서)」을 보인다.
       - 출처와 이름이 맞는지(snapshot·filled는 이름 있음, unknown은 null)는 공유 계약 검사(`snapshotProblem`)가 본다. 새 보고서 저장 때도 이 검사를 지난다.
     - 왜 추측하지 않나: DB에는 이름 변경의 커밋 시각이 남지 않는다. 기록 시각은 트랜잭션 시작 시각이고, 트랜잭션 번호는 커밋 순서가 아니다. 이런 값으로 고르면 겹친 요청에서 다른 시점의 이름을 영구히 저장하게 된다(Codex 재리뷰 3차 재현).
     - 새 보고서는 생성할 때 이름을 스냅샷에 넣으므로 이 문제가 없다.
   - 그래도 이름이 없는 스냅샷을 읽으면 오류 대신 「프로젝트 이름 없음」을 보인다(shared `reportProjectName`). 화면도 같다.
   - 왜: 보고서는 생성 시점 기록이다. 나중에 이름을 바꿔도 그때의 보고서와 같아야 한다.
2. 화면과 같은 마크업·같은 CSS로 HTML을 만든다(`html.ts`).
3. 그 HTML의 hash(문서 hash) 앞 16자를 캐시 키로 쓴다.
4. 같은 키의 파일이 있고 지문이 맞으면 그 파일을 준다(캐시).
5. 없으면 Playwright(브라우저를 코드로 조작하는 도구)의 Chromium으로 A4 PDF를 만든다(`render.ts`).
6. 파일을 `<데이터 루트>/<세대>/pdf/<보고서 id>-<보기>-<문서 hash 16자>.pdf`에 저장하고, `report_pdfs`에 경로와 지문(sha256)을 적는다(`service.ts`).

## 파일

- `model.ts` — 팀장용·보고용 글자를 만드는 계산. 화면 계산(`apps/web/src/features/report/model.ts`)을 그대로 옮겼다.
  - 왜 옮겼나: 서버 빌드는 `apps/api/src`만 담는다. 그래서 웹 소스를 불러올 수 없다.
  - 어긋남 막기: 시나리오 시험이 모든 보고서에서 두 계산의 결과가 같은지 비교한다. 화면 쪽을 고치면 그 시험이 실패한다.
- `assets.ts` — PDF 자산(화면 CSS `prototype.css`와 글꼴 파일 4개).
  - 빌드(`pnpm --filter @awbs/api build`)가 `dist/pdf/assets/`에 복사한다(`scripts/copy-pdf-assets.ts`).
  - 빌드 산출물에서 실행하면 그 복사본만 읽는다. 왜: 운영에는 api만 배포한다. 웹 소스나 글꼴 패키지가 없어도 동작해야 한다.
  - 소스에서 실행하면(개발·시험) 웹 CSS와 글꼴 패키지를 바로 읽는다.
- `html.ts` — PDF용 HTML. 화면 `ReportDocument`의 `<article class="rpt-doc">`와 같은 순서·클래스다.
  - CSS는 웹 파일(`apps/web/src/shared/styles/prototype.css`)과 같다. 빌드 산출물에서는 빌드 때 복사한 것을 읽는다.
  - 화면과 다른 점은 원본 인쇄 경로(P L5000–5012)와 같다. 보기 전환·PDF 버튼 줄과 「생성 이후 변경」 안내는 넣지 않는다. Task 링크는 글자만 남긴다.
  - 모든 값은 HTML 특수 문자를 바꿔 넣는다. 예: 제목이 `<script>`여도 글자로만 보인다.
- `render.ts` — Chromium 변환기. 브라우저는 처음 쓸 때 한 번 띄워 계속 쓴다. 동시에 2개까지, 한 번에 30초까지 변환한다.
  - 자원을 남기지 않는다(Codex 리뷰 P1).
    - 변환마다 작업 공간(context, 다른 변환과 분리된 탭 묶음)을 하나 쓰고, 성공·실패·시간 초과 모든 경로에서 닫는다.
    - 시간 초과면 그 작업 공간을 닫아 변환을 강제로 멈춘다. 시간 초과 뒤에 늦게 만들어진 작업 공간도 바로 닫는다.
    - 동시 실행 자리는 정리가 끝난 뒤에만 다음 요청에 넘긴다. 왜: 정리 전에 넘기면 「동시에 2개」가 지켜지지 않고 탭과 메모리가 쌓인다.
    - 정리가 5초 안에 끝나지 않거나(브라우저가 멈춤) 브라우저 연결이 끊기면, 브라우저 프로세스를 죽이고 다음 변환이 새로 띄운다.
    - 브라우저 손잡이 관리(`BrowserHandle`)는 규칙 세 가지뿐이다(Codex 재리뷰 3차: 땜질 대신 한 곳으로 모음).
      1. 손잡이를 바꾸거나 지우는 일은 모두 한 함수(`serial`, 한 번에 하나씩 차례로 실행하는 뮤텍스) 안에서만 한다.
      2. 브라우저를 띄울 때마다 세대 번호를 준다. 늦은 띄우기 성공·실패, 정리, 연결 끊김은 모두 자기 세대 번호를 들고 와서, 손잡이가 아직 그 세대일 때만 손잡이를 바꾼다.
      3. 손잡이가 아닌 세대의 브라우저(포기한 띄우기가 늦게 성공한 것 포함)는 반드시 죽인다.
      - 그래서 손잡이는 0개 또는 1개이고, 손잡이가 아닌 브라우저는 남지 않는다.
      - 왜: 옛 세대의 늦은 결과나 정리가 새 브라우저의 손잡이를 지우거나 죽이면, 정상 변환이 실패하거나 브라우저를 끌 방법을 잃는다.
      그래서 브라우저를 서버 방식(`launchServer`)으로 띄워 프로세스를 직접 쥔다.
    - Playwright 자체 기다림 한도(30초 + 5초)는 예비 장치다. 강제 중단이 먼저 일한다.
- `service.ts` — 캐시와 저장 규칙. 메일 첨부(M6-03)도 `reportPdf()`를 부르면 같은 파일을 쓴다.
- `routes.ts` — 경로 등록과 응답 머리글(파일 이름).

## 규칙과 이유

- **A4, 여백 14mm.** 원본 인쇄 CSS(`@page{size:A4;margin:14mm}`)와 같다.
- **부록은 새 쪽에서 시작한다.** 원본 CSS `.rpt-appx{break-before:page}`를 그대로 쓴다(G L392).
- **100% 배율로 찍는다(줄이지 않는다).** 본문(13px)은 9.75pt, 표(12.5px)는 9.4pt다. 시험은 본문 9pt 이상을 확인한다.
  - 예외: 원본이 11~11.5px인 태그·배지·꼬리말(8.3~8.6pt)은 원본 크기 그대로 둔다(조정자 승인).
- **원본 인쇄 경로(P L5000–5012)와 다른 점은 두 가지뿐이다(조정자 결정 C).** 화면 CSS는 바꾸지 않는다. 자세한 값은 `html.ts`의 `PDF_CSS`.
  1. 표 3개(실행 기록 .at·다음 예정 .nx·부록 .al)의 고정 열 너비.
     - 왜: 원본 고정 열 너비 합(부록 약 770px)이 인쇄 폭(182mm, 약 688px)보다 넓다.
       원본대로 찍으면 Chromium이 문서 전체를 약 0.89배로 줄여 본문이 9pt 밑이 되고, 제목 열이 몇 px로 줄어 한두 글자씩 줄바꿈된다.
     - 등급 열은 모델 ID(예: `claude-sonnet-5-5`)가 통째로 들어가게 넓혔다.
  2. 표 칸 `word-break:keep-all`(한글도 띄어쓰기에서만 줄바꿈) + 문서 `overflow-wrap:anywhere`(한 줄에 다 안 들어가는 긴 글만 줄 끝에서 끊음).
     - 왜: Chromium은 한글을 음절 사이 어디서나 줄바꿈해 좁은 칸에서 「개발」이 「개/발」이 된다.
       keep-all만 두면 띄어쓰기 없는 긴 글이 칸 밖으로 넘치므로 overflow-wrap:anywhere를 함께 둔다.
  - 시험 규칙: 표의 모든 머리글·칸에서 한글 음절·영문 글자 중간 줄바꿈 0. 줄바꿈은 공백 또는 하이픈(-) 바로 뒤에서만 허용한다.
    모든 칸·표·문서가 인쇄 폭을 넘지 않는다(띄어쓰기 없는 아주 긴 글 포함).
  - 한계: 요약 같은 자유 글 안의 하이픈·가운뎃점(·) 뒤에서는 줄이 바뀔 수 있다(마크업은 화면과 같게 둔다). 지금 자료에서는 가운뎃점 줄바꿈이 없도록 요약 열 폭을 잡았다.
- **글꼴은 Pretendard GOV 1.3.9의 굵기별 고정 파일(400·500·600·700)을 넣는다.**
  - 화면은 가변 글꼴(Variable, 굵기를 자유롭게 바꾸는 글꼴 파일 하나)을 쓴다.
  - 그런데 Chromium PDF는 가변 글꼴의 굵은 글자를 그림 글자(Type3)로 넣는다. 그림 글자는 글꼴 파일이 아니라서 「폰트 embed(PDF 안에 글꼴을 함께 넣는 것)」가 아니다.
  - 글꼴 이름은 화면과 같다. 그래서 CSS는 그대로 쓴다.
- **바깥 주소에 접속하지 않는다.** 문서와 글꼴은 가짜 주소로 요청하게 하고 변환기가 직접 응답한다. 나머지 요청은 끊는다.
- **글꼴을 다 읽은 뒤에만 PDF를 만든다.** 하나라도 실패하면 변환 실패다. 왜: 다른 글꼴로 찍힌 PDF가 캐시에 남지 않게 한다.
- **캐시 키는 문서 hash다.** 스냅샷으로 만든 HTML이 같으면 같은 PDF다.
  - 서식(CSS·마크업)이 바뀌면 HTML이 달라져 키가 바뀌고 PDF를 다시 만든다. 그때 옛 키 파일은 지운다.
  - 파일 지문이 `report_pdfs.sha256`과 다르거나 파일이 없어도 다시 만든다. 왜: 다른 문서나 바뀐 파일을 내보내지 않는다.
- **같은 보고서·보기를 동시에 요청하면 변환은 한 번만 한다.**
- **일간 보고서는 팀장용만 있다.** 일간 보고용 요청은 400이다(원본 P canToggle L6416, 화면도 같다).

## 생성 중 초기화(contracts §8 초기화 경합)

- 변환하는 동안에는 DB 잠금을 잡지 않는다. 왜: 변환은 몇 초 걸린다. 그동안 잠금을 잡으면 초기화가 그만큼 기다린다.
- 저장할 때만 **세대 잠금**(`inEpoch`, 요청을 받은 세대 번호로 거는 잠금)을 건다.
  - 변환하는 사이에 초기화됐으면 세대가 달라 잠금이 실패한다. 이때는 아무것도 저장하지 않고 404를 준다. 초기화로 보고서가 지워졌기 때문이다.
  - 그래서 옛 세대의 PDF가 새 프로젝트 폴더에 섞이지 않는다.
- 세대별 폴더는 초기화 뒤 파일 삭제 작업이 폴더째 지운다(`reset/files.ts`).

## 화면(웹)

- 「PDF 다운로드」는 서버에서 받아 성공하면 파일로 저장한다(`apps/web/src/shared/api/client.ts` `downloadFile`, 기다림 60초).
- 실패하면 오류 막대에 「PDF를 만들지 못했습니다」와 서버 안내(다시 시도·기간을 나눠 생성)를 보이고 「다시 시도」를 둔다. 보고서 본문은 그대로 볼 수 있다(G L49, P L6850).
  - 왜 `<a download>`만 쓰지 않나: 서버가 503을 주면 브라우저가 오류 본문을 파일로 저장해 버린다.

## 오류

- 변환 실패 → 503 `PDF_FAILED`. 안내: 「잠시 후 다시 시도하세요. 계속 실패하면 기간을 나눠 보고서를 생성하세요.」(G L49)
  - 원인 문구는 응답에 싣지 않고 서버 기록에만 남긴다.
- 없는 보고서·생성 중 초기화 → 404 `NOT_FOUND`.
- `view` 없음·잘못된 값·일간 보고용 → 400 `VALIDATION_FAILED`.

  - 변환기 자원 정리(`pdf-render.test.ts`): 끝없이 도는 스크립트로 멈춘 변환을 만들어, 동시 4개·연속 시간 초과·늦은 작업 공간·브라우저 정지·밖에서 죽음·닫기 뒤에 작업 공간·탭·렌더러 프로세스가 남지 않는지 본다.
  - 늦은 정리와 브라우저 교체가 겹치는 경합은 시각을 맞춘 가짜 브라우저(launcher 옵션)로 본다: 옛 정리가 새 브라우저의 정상 변환을 죽이지 않는다.
  - 손잡이 관리는 늦은 띄우기 성공·실패 일정과, 무작위 일정 60가지(늦은 성공·늦은 실패·멈춤·정리 겹침·밖에서 죽음)로 본다: 끝나면 살아 있는 브라우저는 손잡이 하나 이하, 닫으면 0.
- 옛 보고서 이름 채우기: `pnpm test:db -- upgrade-0047`
- 화면: `pnpm --filter @awbs/web e2e:api:report` (실제 PDF 내려받기, 실패 막대·다시 시도)
- 실행 전 준비: Chromium이 설치되어 있어야 한다(`pnpm --filter @awbs/web e2e:install`, 같은 Playwright 판 1.65.1).
