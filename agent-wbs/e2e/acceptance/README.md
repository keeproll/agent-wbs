# M8-01 인수 시험

인수 시험은 사용자가 제품을 받아들일 수 있는지 확인하는 시험이다.
완료 명령은 저장소 루트에서 실행한다.
기존 설치 절차에 따라 `agent-wbs`와 `agent-runner` 양쪽 의존성을 설치해야 한다.
Docker(시험 DB를 별도 실행 공간에 띄우는 도구)와 Playwright Chromium(화면 자동 시험용 브라우저)도 필요하다.
왜 양쪽인가: 서버와 브라우저뿐 아니라 기존 Runner(개발 PC의 실행·보고 프로그램) 코드까지 같은 시험에서 사용하기 때문이다.

```sh
pnpm -C agent-wbs e2e -- acceptance
```

먼저 가짜 API(화면과 서버의 통신 창구)로 오류·빈 상태·입력 보호·화면 폭을 확인한다.
같은 실행에 실제 HTTP(요청과 응답을 주고받는 규약) 서버와 빈 PostgreSQL 데이터베이스(DB)를 쓰는 연속 시나리오도 들어 있다.
이후 연결표에 지정한 기존 Runner 시나리오·DB 시험과 실제 API 화면 시험을 실행한다.
어느 단계든 실패하면 최종 종료 코드는 1이다.
왜 함께 실행하나: 화면에 정해 둔 답을 보여 주는 시험만으로 실제 저장·실행 연결까지 통과했다고 판단할 수 없기 때문이다.

## 처음 설치한 사람의 흐름

`apps/web/e2e/acceptance.spec.ts`의 시험 하나가 아래 흐름을 끝까지 수행한다.

1. 마이그레이션(DB 구조를 만드는 SQL 파일)과 system seed(운영 기본 설정)만 넣는다.
2. 프로젝트·Task·실행·보고서가 모두 0건인지 확인한다.
3. 실제 인증 CLI(명령줄 도구)로 LAN(사내 네트워크) 접속 비밀번호를 설정한다. 브라우저에서 로그인한다.
4. Runner(개발 PC에서 실행과 보고를 맡는 프로그램)가 모델·준비 상태·GitHub(코드 저장소 서비스) 연결 상태를 보고한다. 팀장은 화면에서 모델을 허용한다.
5. GitHub 저장소 접근 확인을 요청한다. 가짜 Runner가 실제 보고 API로 확인 결과를 보낸다.
6. 프로젝트를 등록한다. 기존 Planning(분석과 계획 수립) 실행기가 가짜 Agent(자동 분석·개발 도구) 두 명의 분석을 받아 진행한다.
7. 팀장이 기술 결정을 확정한다. 새 초안을 승인해 WBS(프로젝트를 단계·묶음·Task로 나눈 목록)를 만든다.
8. 화면에서 개발을 요청한다. 기존 Runner가 실제 작업 폴더 준비·가짜 CLI 실행·① Task 검사·결과 수집을 수행한다.
9. QA(품질 검증)가 FAIL을 보고한다. 자동 재작업의 Effort(생각 깊이)가 high에서 xhigh로 올라가는지 확인한다.
10. 재검증 PASS 뒤에도 Task는 Gate(완료 전에 통과할 조건 묶음)에 머문다.
11. ② 통합 검사와 가짜 GitHub 병합을 마쳐야 `done`이 된다. 열린 보유도 0건이어야 한다.
12. 방금 만든 기록으로 보고서와 PDF(인쇄용 문서 파일)를 만든다. 완료 1건·전체 2건을 화면과 서버에서 대조한다.
13. 별도 취소 CP(변경 제안)를 실제 반영한다. 시작 전 SS(Start-to-Start, 선행 시작 후 후속 시작) 선행이 취소되면 관계를 제거한다. 다른 FS(Finish-to-Start, 선행 완료 후 후속 시작) 선행이 남으면 계속 차단한다(D-27).

프로젝트 이후 업무 데이터를 SQL(DB를 읽고 고치는 언어)로 미리 넣지 않는다.
왜: 미리 넣은 완성 데이터를 읽는 시험은 등록·분석·승인 사이의 연결 누락을 찾지 못한다.

## 외부 서비스와 격리

- 데이터베이스는 실행마다 새 Debian `postgres:16` 컨테이너다. `track_commit_timestamp=on`을 사용한다.
- 포트는 운영체제가 고른 빈 포트다. 다른 작업의 DB·서버를 재사용하지 않는다.
- 종료할 때 만든 컨테이너만 `docker rm -f -v`로 지운다. 익명 볼륨도 함께 지우기 위해서다.
- GitHub HTTP API는 기존 가짜 서버다. git 원격 저장소도 임시 로컬 저장소다.
- Claude·Codex는 기존 가짜 CLI다. 실행 비용과 실제 외부 쓰기는 없다.
- Agent 작업 폴더의 git·파일 읽기는 기존 전용 계정 래퍼의 사본에 넘긴다. 계정 전환만 가짜 sudo가 대신한다.
- 이 시험은 운영체제 계정 격리 자체의 실환경 인수를 대신하지 않는다. 그 인수는 M8-04·M8-05 범위다.
- 메일·Telegram 보충 시험도 기존 가짜 SMTP(메일 전송 서버)·Bot API(봇 전송 API)를 사용한다.

준비 대기는 상태 확인을 반복한다.
UI(화면) 대기는 Playwright의 조건 확인을 쓴다.
고정 시간 뒤에 성공했다고 가정하지 않는다.
DB 준비 제한은 시계가 뒤로 가도 줄어들지 않는 `performance.now()`로 잰다.
Runner 보충 시험의 준비 제한은 DB 시험과 같은 60초다.
왜: 빈 DB에 구조를 만드는 시간은 같은 PC의 다른 작업 부하를 받기 때문이다. 시험 본문의 판정과 제한은 유지한다.

## 시나리오와 화면 대조

G§12의 17·18은 D-05에 따라 30·31로 대체한다.
옛 Windows 경로·zip 첨부 화면은 만들지 않는다.
`scenarios.tsv`는 가이드 번호별로 연결한 화면 시험과 Runner 보충 시험이다.
`uat-map.tsv`는 `docs/ui/acceptance-cases.tsv`의 UAT(User Acceptance Test, 사용자 인수 판정 항목) 149개를 한 행씩 연결한다.
대표 시험 이름이나 연속 시나리오의 단계 이름도 지정한다. 보고서에서 해당 소스 줄을 바로 열 수 있다.
시험 이름이 소스에서 사라지면 시작 단계에서 실패한다. 이름만 남은 낡은 연결표를 막기 위해서다.
화면 파일과 서버 보충 파일의 검증 범위는 서로 다르다.
따라서 연결표가 있다는 사실만으로 UAT 전체를 합격으로 표시하지 않는다.

기존 시각 비교 시험도 실행한다.
원본 스크린샷은 `~/.cache/agent-wbs-baseline` 또는 `AWBS_BASELINE_DIR`에서 읽는다.
허용 차이와 예외는 기존 시험의 판정값을 사용한다.
화면 전체가 다른 영역은 차이 이미지만 남기는 기존 규칙도 유지한다.
왜: 승인된 제품 차이를 원본 결함에 맞춰 되돌리면 안 되기 때문이다.

`acceptance-print.spec.ts`는 브라우저 인쇄의 본문 원점·A4 폭·본문 좌우 경계·부록 페이지를 검사한다.
서버가 만든 PDF와 브라우저 인쇄는 별도 경로라 각각 시험한다.

## 결과와 부분 실행

기본 보고 폴더는 `~/.orca/bots/agentwbs/archive/2026-11-28/M8-01`이다.
`AWBS_ACCEPTANCE_OUT`으로 다른 폴더를 지정할 수 있다.
`commands.json`에 단계별 명령과 종료 코드가 남는다.
`playwright.json`에는 화면별 결과가 남는다.
시각 비교 이미지는 `visual/`에 남는다.
실패 추적 파일은 `artifacts/`의 실행별 폴더에 남는다.

```sh
# 부분 실행. 완료 명령을 대신하지 않는다.
pnpm -C agent-wbs e2e -- acceptance acceptance.spec
pnpm -C agent-wbs e2e -- acceptance acceptance-print
pnpm -C agent-wbs e2e -- acceptance --list
```

최신 유료 CLI의 관측 검증은 M8-04다.
비밀값 전수 보안 검토는 M8-03이다.
연결표에는 이 두 항목을 해당 범위로 표시한다.
가짜 보고 시험 통과를 실환경 인수 통과로 바꾸지 않기 위해서다.

## 용어

| 용어 | 뜻 |
|---|---|
| E2E(End-to-End) | 화면을 열어 사용자의 흐름을 끝까지 확인하는 시험. |
| fixture | 특정 오류나 빈 상태를 재현하는 고정 시험 자료. |
| 가짜 API | 브라우저 요청에 정해 둔 응답을 주는 시험 도구. 서버 구현의 증거는 아니다. |
| 보유 | 프로세스 종료가 확인될 때까지 실행 자리를 사용 중으로 계산하는 기록. |
| system seed | 빈 DB에 넣는 운영 기본 설정. 프로젝트 예시 데이터와 다르다. |
| 마이그레이션 | DB 테이블·제약·함수의 구조를 만드는 SQL 파일. |
| Docker | 시험 DB를 다른 작업과 분리된 실행 공간에 띄우는 도구. |
| Playwright Chromium | 사용자의 조작을 자동으로 재현하는 시험용 브라우저. |
| DB | 데이터베이스. 프로젝트와 실행 기록을 저장하는 곳. |
| API | 화면이나 Runner가 서버에 요청을 보내는 통신 창구. |
| HTTP | 요청과 응답을 주고받는 통신 규약. |
| CLI | 명령줄에서 실행하는 도구. |
| LAN | 사내 네트워크. |
| Runner | 개발 PC의 실행과 보고를 맡는 프로그램. |
| Agent | 분석·개발·검증을 맡는 자동 도구. |
| GitHub | 코드 저장소와 검토 요청을 관리하는 서비스. |
| Planning | 독립 분석과 계획 수립 과정. |
| WBS | 프로젝트를 단계·묶음·Task로 나눈 목록. |
| Task | 개발하거나 검증할 작업 한 건. |
| QA | 품질 검증. |
| Effort | Agent의 생각 깊이를 지정하는 값. |
| Gate | 완료 전에 통과해야 하는 검사 묶음. |
| CP | 변경 제안. |
| SS | 선행 시작 후 후속 시작 관계. |
| FS | 선행 완료 후 후속 시작 관계. |
| CI | 자동 빌드와 검사. |
| PDF | 인쇄용 문서 파일. |
| SQL | DB를 읽고 고치는 언어. |
| SMTP | 메일을 보내는 통신 규약. |
| UI | 사용자가 보는 화면. |
| UAT | 사용자 인수 판정 항목. |
| 변이 | 실패 검출 능력을 확인하려고 일부러 잘못 바꾼 코드. |
