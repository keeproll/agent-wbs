# 가짜 Runner 시나리오

가짜 Runner(Agent를 실제로 실행하는 대신 정해진 결과를 보고하는 시험 도구)는 실제 HTTP 서버와 PostgreSQL 데이터베이스를 사용한다. Claude·Codex 유료 호출과 실제 개발 프로세스 실행은 없다. 예를 들어 재부팅은 새 부팅 식별자를 서버에 보고하며, 서버가 기존 시도를 중단시키는지 확인한다.

`runner.ts`는 `agent-runner/src/api`의 생성된 계약과 기존 HTTP 클라이언트만 사용한다. 서버 내부 함수와 데이터베이스를 직접 부르지 않는다. 테스트 준비 파일 `test/scenario.ts`가 빈 시험 데이터베이스를 만들고 초기 자료·인증 정보를 넣는다. 팀장 동작은 실제 HTTP 요청으로 수행하며, 서버 감시 시간은 준비 코드에서 앞당긴다. 그래서 연결 끊김마다 몇 분씩 기다리지 않아도 같은 서버 판정을 확인할 수 있다.

## 실행

`agent-wbs` 폴더에서 자기 전용 PostgreSQL 컨테이너 주소를 지정한다. 아래 이름의 데이터베이스와 `_runner_scenario`가 붙은 데이터베이스는 실행할 때 지우고 다시 만들므로 기존 자료가 없는 전용 주소만 쓴다. 이름은 기존 안전 검사에 맞게 `awbs_test_`로 시작해야 한다.

```sh
TEST_DATABASE_URL=postgresql://postgres:시험비밀번호@127.0.0.1:26709/awbs_test_m209 pnpm test:scenario -- runner-basic
```

다른 작업의 컨테이너나 포트를 공유하지 않는다. 시험이 끝나면 직접 만든 컨테이너를 삭제한다. `pnpm test`는 데이터베이스 없는 일반 검사이고, 위 시나리오는 별도 명령으로 실행한다.

## 확인하는 내용

| 가이드 번호 | 실제 확인 |
| --- | --- |
| 6 | `runner-basic`: Claude 개발 → Codex 품질 검증(QA) 실패 → 생각 깊이(Effort) 상향 재작업 → 재검증 통과. `attempt-complete`: 실제 ①·② 검사와 병합·완료까지 확인한다. |
| 8 | 연결 끊김 → 메시지 전달 실패 → 재연결 → 같은 메시지 재전송 → 수신 확인. |
| 9 | 재부팅 → 기존 시도 중단 → 종료 증거 없는 재개 거절 → 증거 제출 뒤 같은 등급의 새 시도. |
| 10 | Claude 한도 도달 → Claude만 실행 보류 → 리셋 뒤로 일정 이동 → 사용량 리셋 후 실행 허용·일정 복구. |
| 보충 | 메시지 중복 조회·중복 수신 확인 후에도 메시지는 하나이고, 수신 확인을 업무 완료로 바꾸지 않는다. |

선행 서버 기능이 빠지면 해당 테스트는 실패한다. 데이터베이스를 직접 바꿔 시나리오를 성공시키거나 실패를 건너뛰지 않는다. `runner-basic`은 명시적인 ① 준비 기록을 보고한다. 서버에는 ① 기록 없이 QA로 넘기는 자리표시가 없다.

## M7-06: 실제 검사와 병합 연결

```sh
TEST_DATABASE_URL=postgresql://postgres:시험비밀번호@127.0.0.1:26709/awbs_test_m706 pnpm test:scenario -- attempt-complete
```

`attempt-complete.ts`는 기존 `runTaskCheck`(① Task 검사)와 `IntegrationQueue`(② 통합 검사와 병합 대기열)를 그대로 호출한다. 로컬 git 저장소에서 개발·재작업 커밋을 만든다. 기존 fake CLI(정해진 결과를 내는 시험용 실행 파일)를 실제 자식 프로세스로 실행한다. GitHub HTTP API도 기존 fake 서버를 사용한다. 유료 Agent와 외부 서비스는 호출하지 않는다.

M5-05가 아직 이 기준선에 없다. 따라서 작업 예약·CLI 실행·결과 보고의 연결은 시험 준비 코드다. M5-05를 병합하면 이 부분을 실제 시도 실행기로 교체해야 한다. 왜 구분하나: ①·② 검사 자체의 결합을 확인한 것과 Runner 앱 전체를 실행한 것을 혼동하지 않기 위해서다.

- QA한 H와 main A를 합친 H′를 실제로 만든다. H′에서 ①·②를 다시 검사한다. 서버는 커밋 번호(SHA), 파이프라인 정의 번호와 병합 파일 전체의 번호(tree SHA)를 대조한다.
- Gate(완료 전 통과해야 하는 조건 묶음)의 다섯 조건을 각각 깨뜨린다. 이 실패 시험만 데이터베이스에 늦은 변경을 주입한다. 수동 완료 요청과 자동 병합 보고가 모두 거절되어야 한다.
- 검사 실패 뒤 재실행은 새 CI(자동 검사 실행) ID와 실제 결과를 남긴다. 통과 기록은 다시 실행하지 못한다. 검사 통과만으로 Task를 완료하지 않는다.
- QA·통합 실패의 자동 재작업은 합산 세 번이다. 프로세스 실패의 자동 재시도는 두 번이다. BLOCKED(원인 해결 전 진행 불가)와 같은 재작업 안의 프로세스 재시도는 재작업 회차를 늘리지 않는다.
- 병합 보고는 Runner outbox(연결이 끊겨도 디스크에 남는 전송 대기함)를 다시 열어 재전송한다. 같은 보고를 다시 보내도 완료 이력과 `done` 알림은 하나여야 한다.
- 알림은 서버의 `notify_events` 대기열 저장까지 검증한다. 승인된 M6-04를 합친 뒤 fake BotAPI(시험용 Telegram 발송 서버) 전달을 별도로 확인한다. 왜 나누나: 승인 전 알림 발송 구현을 이 작업에 섞지 않기 위해서다.

시험 임시 저장소와 fake CLI 기록은 운영체제의 임시 폴더를 쓴다. 기록 위치를 지정하려면 표준 환경 변수 `TMPDIR`를 원하는 폴더로 설정한다. 조건 대기에는 10초를 주며 고정 시간 대기를 쓰지 않는다.
