# DB 시험 준비

DB(데이터베이스) 시험에는 자기 전용 PostgreSQL 16 컨테이너와 포트를 사용한다.
`TEST_DATABASE_URL`의 DB 이름은 `awbs_test_`로 시작해야 한다.
`pnpm test:db`는 이 DB를 삭제하고 다시 만든다.
다른 개발 DB를 지우지 않도록 이름과 실제 연결 대상을 검사한다.

`recreateTestDatabase`는 `template0`에서 UTF8·C.UTF-8로 DB를 만든다.
`LC_COLLATE`는 문자열 정렬 규칙이다.
`LC_CTYPE`는 문자 분류 규칙이다.
둘을 C.UTF-8로 고정한다.
컨테이너의 기본 언어가 달라도 모델 목록 순서와 한글 정규식 결과가 같아야 하기 때문이다.

마이그레이션의 `journal`은 적용 순서와 시각을 적은 목록이다.
병합 직전에는 새 항목을 마지막 순번으로 두고 `when`을 기존 최댓값보다 크게 정한다.
SQL 파일 이름과 snapshot(DB 구조 기록)의 연결도 함께 맞춘다.
이미 적용한 항목보다 작은 `when`이 나중에 들어오면 Drizzle이 이를 건너뛸 수 있기 때문이다.
`runMigrations`는 실행 후 모든 journal 항목의 hash(파일 내용의 고유 번호)를 DB와 대조한다.
빠진 항목이 있으면 서버를 시작하지 않고 오류로 멈춘다.
오류가 나면 운영 데이터를 지우지 말고 마이그레이션 적용 순서를 먼저 바로잡는다.

## 시험 컨테이너 이미지와 설정

시험 컨테이너는 Debian 기반 `postgres:16` 이미지를 쓴다(`postgres:16-alpine`이 아니다).
왜: alpine 이미지의 C.UTF-8 정렬은 Debian과 결과가 달라 정렬을 확인하는 시험이 실패한다.
개발용 `compose.yaml`도 같은 이유로 Debian 이미지를 쓴다(M5·M7 통합 결정).

예시(이름·포트·비밀번호는 자기 것으로 바꾼다):

```sh
docker run -d --name <이름>-pg -e POSTGRES_USER=awbs_owner -e POSTGRES_PASSWORD=<비밀번호> -e LANG=C.UTF-8 \
  -p 127.0.0.1:<포트>:5432 postgres:16 -c fsync=off -c synchronous_commit=off -c full_page_writes=off
docker rm -f -v <이름>-pg   # 끝나면 익명 볼륨까지 지운다
```

`fsync=off` 등 세 설정은 시험 컨테이너에만 쓴다. 개발·운영 DB에는 쓰지 않는다.
이 설정은 커밋할 때마다 디스크에 기록이 끝날 때까지 기다리는 일을 생략한다.
시험 DB는 매번 새로 만들므로 전원이 꺼져 데이터가 깨져도 잃을 것이 없다.

왜 필요한가: 여러 시험 파일의 `beforeAll`은 DB를 새로 만들고 마이그레이션 전체를 적용한다.
마이그레이션은 파일마다 따로 커밋하므로, 파일이 늘수록 디스크 기록 대기도 늘어난다.
같은 PC에서 다른 DB 컨테이너가 함께 돌면 이 대기가 수십 배로 길어질 수 있다.
그동안 `security-review`·`schema-review`의 `beforeAll` 60초 초과가 여러 브랜치에서 반복된 가장 유력한 원인이 이것이다.
그때 같은 실행의 `upgrade-stages`도 120초를 넘겼고 전체 시간이 평소의 2배 이상이었다(M6-03 기록: 901초).

측정(M5·M7 통합, 마이그레이션 27개, 같은 PC):

- 기본 설정: DB 새로 만들기 + 마이그레이션 약 2.5초
- 세 설정을 끈 컨테이너: 약 0.4초

## 이미 옛 번호로 적용한 DB

병렬 작업 브랜치는 배정받은 번호(예: `0041`)로 마이그레이션을 만들고, 통합 때 최종 순번(예: `0026`)으로 다시 매긴다.
내용(hash)은 바뀌지 않으므로 옛 번호로 이미 적용한 DB도 같은 마이그레이션을 다시 실행하지 않는다.

옛 번호의 `when`(예: `1795740000041`)이 DB 기록에 남아 있으면 문제가 하나 생긴다.
Drizzle은 「마지막으로 적용한 기록의 시각」보다 작은 `when`을 이미 적용한 것으로 보고 건너뛴다.
예를 들어 통합에서 더한 `0027`(`when` `1795740000027`)이 건너뛰어진다.
그래서 `runMigrations`는 마이그레이션 전에, 이미 적용한 hash의 기록 시각을 지금 journal의 `when`으로 맞춘다.
내용이 다른 기록은 건드리지 않는다.
왜: 같은 내용을 다시 매긴 것뿐이므로 시각만 맞추면 된다. 진짜 순서 오류는 그대로 누락 검사가 잡아야 한다.

같은 이름이라도 내용이 다른 옛 판(예: 브랜치에서 여러 번 고친 `0041`의 이전 내용)을 적용한 DB는 누락 검사가 오류로 멈춘다.
이런 DB(브랜치 시험 DB, 미리보기 DB 등)는 마이그레이션을 고치지 말고 DB를 새로 만든다.
