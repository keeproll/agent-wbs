# M8-03 보안 검토와 비밀값 검사

기준은 main `1ce62aa`다. 검사 대상은 Agent WBS와 Agent Runner다.
원본 근거는 G L1040·L1051·L1070, `architecture.md` §4, `contracts.md` §8이다.
화면 인수 항목은 `UAT-GITHUB-02`, `UAT-MAIL-02`, `UAT-TG-01`·`UAT-TG-06`이다.

## 무엇을 검사하나

검사 표식(canary)은 시험에만 쓰는 가짜 비밀값이다.
먼저 이 값을 실제 저장·출력 경로에 넣는다.
그다음 기록과 응답에 원문이 남았는지 찾는다.
왜 이렇게 하나: 마스킹 함수만 검사하면 그 함수를 빠뜨린 저장·출력 경로를 놓칠 수 있다.

| 경계 | 자동 검사 |
| --- | --- |
| 로그 | 요청 URL·인증 헤더·쿠키·오류·자식 로거의 고정 필드. `apps/api/test/log.test.ts`, Runner `test/log.test.ts` |
| 응답·오류 | GitHub·SMTP 설정 재조회. 오류의 문장·조치·필드 경로. Runner가 받은 오류와 거부 기록. 양쪽 `secrets` 시험 |
| DB(데이터베이스) | GitHub·SMTP·Telegram 저장 뒤 모든 공개 스키마 표에서 가짜 평문 부재 확인. SMTP·Telegram은 복호화도 확인. WBS `secrets.db.test.ts` |
| 보고서 | 새 스냅샷의 DB 저장·조회. 메일 본문·PDF용 HTML. 실제 PDF를 다시 열어 글자 검사. WBS `secrets` 시험 |
| 파일·환경 변수 | 내보내기 ZIP의 JSON, Runner 거부 기록·CI(빌드와 시험 자동 실행) 로그·실행 요약. Agent 환경의 허용 목록. `.env`와 키 파일 권한 `0600` |
| 메일·Telegram | 로컬 가짜 서버로 설정·발송·실패를 검사. 본문·로그·DB·오류의 비밀값 부재 확인. `e2e/fakes/test/{mail,telegram}.scenario.test.ts` |
| 인증·권한 | 모든 Runner 계약 경로의 무토큰·팀장 세션·낡은 세대·재전송 검사. Runner의 팀장 경로 호출 거부. `security.db.test.ts`, `security-review.db.test.ts` |
| CSRF·세션 | CSRF(다른 사이트가 로그인한 사용자를 속여 요청을 보내는 공격) 방어. Origin(요청을 시작한 사이트 주소)·CSRF 헤더 일치. 링크 1회 소비·만료·로그아웃·비밀번호 재설정 검사 |
| 입력 | 알 수 없는 필드·형식 오류·본문 크기·경로 이탈 거부. `validation`·`reset` 시험과 Runner의 Agent 작업 폴더 경계 시험 |

팀원 전용 로그인·권한은 현재 계약에 없다.
현재 인증 주체는 팀장(`lead`)과 Runner(`runner`)다.
팀원 합류 때 권한과 다른 작성자 검증을 정한다는 기존 결정은 그대로다(`open-questions.md` §0.1·§2.1 Q-09).
왜 새 권한을 추가하지 않았나: 이번 보안 검토가 승인되지 않은 계정 정책을 만들면 기존 계약을 바꾸기 때문이다.

## 발견해서 고친 것

1. child logger(기존 로그 도구에 고정 필드를 붙인 기록 도구)의 필드가 기존 마스킹 훅을 지나지 않았다.
   이제 Runner와 같이 serialization(객체를 로그 문자열로 바꾸는 과정)이 끝난 뒤 가린다.
   요청 URL과 오류 부가 객체를 줄이는 기존 규칙도 유지한다.
2. `SMTP_PASSWORD="공백 있는 값"` 같은 출력이 가려지지 않았다.
   두 프로젝트의 기존 마스킹 규칙에 따옴표·공백·줄 끝까지 처리하는 규칙을 넣었다.
   `AWBS_SECRET_KEY` 같은 기존 키 이름도 계속 가린다.
3. 업무 오류의 상세 객체만 가리고 문장·조치·입력 오류 목록은 원문으로 답했다.
   공통 업무 처리기와 프로젝트·Task 처리기에서 해당 문자열도 가린다.
4. 보고서 자유 입력의 토큰이 메일·PDF에 남았다.
   새 스냅샷은 저장 전에 가린다.
   기존 스냅샷을 출력할 때도 메일·PDF 생성기가 가린다.
   왜 두 곳인가: 이미 저장된 보고서도 안전하게 출력해야 한다.
5. Runner가 서버 오류 본문을 그대로 받아 거부 기록 파일에 보관했다.
   이제 API(프로그램 사이 요청 규약) 클라이언트가 오류를 넘기기 전에 가린다.
   현재 인증에 쓰는 Runner 토큰은 모양과 관계없이 알려진 값으로 가린다.
6. CI 로그는 표준 출력·오류 출력을 가렸지만 명령 인자를 가리지 않았다.
   로그 파일과 실행 요약을 쓰기 직전에 가린다.

수정 전 시험이 위 누출로 실패하는 것을 확인한다.
변이 검사(mutation test)는 안전장치를 잠깐 제거한 뒤 같은 시험이 실패하는지 보는 방법이다.
왜 필요한가: 항상 통과하는 시험을 완료 근거로 삼지 않기 위해서다.
변이 뒤에는 원래 코드를 복원하고 완료 명령을 다시 실행한다.

## 의존성 취약점

`pnpm audit --json`은 설치된 의존성(다른 패키지를 사용하기 위해 함께 설치한 코드)을 알려진 취약점 목록과 대조한다.
2026-11-28 첫 검사에서 Runner는 0건이었다.
WBS는 개발 도구 `drizzle-kit` 아래의 `esbuild 0.18.20`에서 중간 등급 1건이 나왔다.

- 식별자: [GHSA-67mh-4wv8-2f99](https://github.com/advisories/GHSA-67mh-4wv8-2f99).
- 내용: 개발 서버를 사용하면 다른 웹사이트에서 응답 내용을 읽을 수 있다.
- 조치: `pnpm-workspace.yaml`에서 `@esbuild-kit/core-utils>esbuild`만 `0.25.12`로 고정한다.
- 이유: 같은 도구가 이미 쓰는 패치 버전을 재사용한다. 다른 의존성 전체를 바꾸지 않는다.
- 다시 확인: 양쪽 모두 취약점 0건. Drizzle 스냅샷·마이그레이션 생성 시험도 완료 명령에 포함한다.

## Q-08 격리에 남은 위험

owner가 정한 전용 OS(운영체제) 계정 방식은 유지한다.
다음 항목은 마스킹 시험을 통과해도 사라지지 않는다.
자세한 설치 경계는 `agent-runner/docs/isolation.md` §11·§12에 있다.

- 모든 Task가 같은 `awbs-agent` 계정이다. 다른 세션의 작업 폴더와 검사 사본에 접근할 수 있다.
  Task별 계정이나 컨테이너는 Q-08 범위 밖이다.
- 같은 PC의 네트워크 서비스와 추상 유닉스 소켓에는 닿을 수 있다.
  API 인증과 DB 비밀번호가 계속 필요하다. 계정별 방화벽은 설치하지 않는다.
- 공용 `/tmp`·`/var/tmp`·`/dev/shm`은 계정 격리만으로 비밀을 보호하지 못한다.
  개인 임시 폴더와 파일 권한을 써야 한다. 제거 스크립트는 다른 프로그램 파일을 함께 지우지 않는다.
- WSL(Windows에서 리눅스를 실행하는 환경)의 보호는 부팅 순서에 영향을 받는다.
  실행 전 래퍼 점검이 실패하면 실행을 거부해야 한다.
- 관리자 권한으로 계정을 지우고 같은 UID(계정의 숫자 번호)를 다시 쓰는 극히 짧은 경합은 남는다.
  Agent에게 관리자 권한은 없다. 자세한 조건은 격리 문서 §11에 있다.
- Runner는 Agent가 쓰는 폴더에서 git을 실행하지 않는다.
  작업 결과는 전용 계정의 `git-inspect`·`git-bundle`로 받아 검사한다.
  이번 완료 명령에 해당 경계의 회귀 시험을 포함한다.
- 전용 계정·WSL·cgroup(프로세스 묶음의 자원을 재고 정리하는 리눅스 기능)의 실제 설치 상태는 이번 작업에서 바꾸지 않는다.
  실제 CLI 관측과 운영 실측은 M8-04·M8-05의 확인 대상이다.
- 계약 추출·임시 SQL 실행기가 실제 앱에 연결될 때도 같은 계정 경계를 써야 한다.
  이미 확인된 것처럼 표시하지 않는다.

## 확인 범위의 한계

마스킹은 알려진 인증 형식과 비밀 필드 이름을 기준으로 한다.
문맥 없는 임의 문자열이나 바이너리 첨부 안의 비밀번호를 모두 찾아내는 검사는 아니다.
사용자가 일반 제목·코드·이미지에 붙여 넣은 비밀을 모든 과거 이력에서 지우는 작업도 아니다.
왜 원본을 덮어쓰지 않나: 보고서·이력의 불변 규칙과 파일 무결성 검사를 깨뜨릴 수 있기 때문이다.

서버의 `.env`·키 파일과 SMTP·Telegram 인증 요청에는 기능상 비밀이 있어야 한다.
검사는 이 값을 허용된 인증 목적에만 쓰는지 확인한다.
팀장 세션 쿠키와 CSRF 값도 로그인한 팀장에게 발급해야 한다.
이 정상 발급을 누출로 세지 않는다.

기준 코드에는 `/api/runner/github/key`·`/api/runner/github/credential` 계약은 있으나 실제 서버 처리기가 없다.
이번에는 암호화 저장과 Runner 봉인 형식의 시험을 구분해 기록한다.
운영 토큰 전달 전체가 검증됐다고 주장하지 않는다.
이 기능 공백은 M8-05 실환경 연결 전에 별도 확인이 필요하다.

## 다시 실행하는 방법

`W`는 `pnpm -C agent-wbs`, `R`은 `pnpm -C agent-runner`다.
WBS 시험에는 전용 Debian `postgres:16`을 쓴다.
`track_commit_timestamp=on`이 필요하다.
`TEST_DATABASE_URL`은 이 컨테이너의 `awbs_test_` DB를 가리켜야 한다.
기존 확인 서버와 `verum-*`·`25432`는 사용하지 않는다.

```sh
TEST_DATABASE_URL=postgres://postgres:<시험 비밀번호>@127.0.0.1:<전용 포트>/awbs_test_m803 pnpm -C agent-wbs test:secrets
pnpm -C agent-runner test:secrets
pnpm -C agent-wbs audit --json
pnpm -C agent-runner audit --json
```

검사가 끝나면 전용 컨테이너는 `docker rm -f -v <이름>`으로 지운다.
왜 `-v`가 필요한가: 익명 데이터 볼륨을 남기지 않기 위해서다.
명령별 결과와 독립 리뷰 기록은 작업 보고서 `M8-03/REPORT.md`에 남긴다.
