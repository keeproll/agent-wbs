# Agent WBS 구현 기준선 — owner 결정과 미결 사항

> **이 문서가 답하는 질문**
> - owner(이 프로젝트의 최종 결정권자)가 이미 정해 준 것은 무엇인가?
> - 아직 답을 받지 못한 질문은 무엇이고, 답이 없을 때 어디까지 만들어도 되는가?
>
> 처음 읽는다면 [docs/README.md](../README.md)의 읽는 순서를 먼저 보세요. 낯선 용어는 [용어집](../glossary.md)에 모아 두었습니다.

**표기 약속**

- `G` = 가이드다. 원본 설계 문서 `prototype/docs/Agent-WBS-설계의도-및-구현가이드.md`를 말한다.
- `P` = 프로토타입이다. 화면 시안 `prototype/uiux/Main.dc.html`을 말한다.
- `L` = 줄 번호다. 예를 들어 `G L257`은 가이드 257번째 줄이다.
- 우리가 스스로 정한 해석은 이 문서가 아니라 [architecture.md §7](architecture.md#7-해석-결정-기록)에 있다.

**이 문서를 읽을 때 꼭 기억할 두 가지**

- **§2의 미결은 답이 없다.**
  - 「추천」은 제안일 뿐 기본값이 아니다.
  - 무응답을 승인으로 보지 않는다.
  - 왜: 추천을 기본값으로 쓰기 시작하면, owner가 고르지 않은 선택이 몰래 제품에 들어가기 때문이다.
- gate(답을 받아야 열리는 관문) 전에 만들 수 있는 것은 정해져 있다.
  - 골격·어댑터·fake(실제 외부 서비스 대신 쓰는 가짜 구현)는 만들 수 있다.
  - 「잠정」으로 표시한 테스트 fixture(테스트용 고정 데이터)도 만들 수 있다.
  - 운영 seed(운영 DB에 처음 넣는 기본 데이터)에 넣으면 안 된다.
  - gate 작업을 완료로 닫으면 안 된다.
  - 왜: 답이 나오기 전 만든 것은 나중에 바뀔 수 있다. 그래서 바꾸기 쉬운 곳(테스트·가짜)에만 둔다.

### 0.1 Q-05 상태 전이 표 (owner 승인 2026-11-25)
- 출처: G L630-643, L1012, L1145. 상세·claim 조건: [data-model §3.1](data-model.md#31-task-대표-상태).

이 표는 Task(일 한 건)가 어떤 사건을 만나 어떤 상태로 바뀌는지 정한다. 표에 없는 바뀜은 서버가 거절한다. 그래서 화면이나 Runner가 실수해도 상태가 엉뚱하게 바뀌지 않는다.

| # | 현재 | 사건 | 다음 |
|---|---|---|---|
| 1 | 없음 | 초기 WBS 승인 / 수동·CP 추가 | 실행 대기 / 계획 중 |
| 2 | 계획 중 | 명세 완료 → 착수 승인 요청 | 승인 대기 |
| 3 | 승인 대기 | 팀장 승인 / 반려 | 실행 대기 / 계획 중 |
| 4 | 실행 대기 | 팀장 시작 + 선행·자원·설치 통과 | 실행 중 |

| 6 | QA·검증 진행 | PASS / FAIL | Gate 대기 / 재작업 필요 |
| 7 | QA·검증 진행 | BLOCKED | 유지 → 원인 해결 후 새 검증 시도 |

| 9 | 실행 중·QA·검증 | Runner 중단·한도 | 중단·재개 대기 |
| 10 | 중단·재개 대기 | 재개 버튼 + 보유 해제 확인 | 중단된 단계(실행/QA/검증), 새 시도·같은 등급(모델 허용 해제 시 D-29) |
| 11 | 실행 중·QA·검증 | 프로세스 실행 실패 | 실패 |

**표를 읽는 법**

- 「/」로 나뉜 칸은 짝을 이룬다. 예를 들어 3행은 「팀장 승인이면 실행 대기, 반려면 계획 중」이라는 뜻이다.
- ①은 Task 검사(빌드·테스트 등 첫 번째 자동 검사 단계)이고, ②는 통합 확인(main과 합친 상태로 다시 하는 검사)이다.
- CP(Change Proposal)는 계획을 바꾸자는 변경 제안이다.
- 완료·취소됨은 종료 상태, 「차단」은 상태가 아니라 계산값.
- 왜 「차단」은 상태가 아닌가: 차단 여부는 선행 Task의 상태에 따라 매 순간 달라진다. 저장해 두면 실제와 어긋나기 쉬우므로 그때그때 계산한다.
