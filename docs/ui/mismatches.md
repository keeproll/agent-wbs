# 불일치·죽은 동작·미결 사항

> 처음 읽는다면 [README.md](README.md)의 ID 읽는 법과 용어집을 먼저 본다.

## 이 문서의 역할과 읽는 법

이 문서는 원본 프로토타입이 가이드·제품 기대와 **다른 곳**(MM, MisMatch = 불일치)을 모은 목록이다.
프로토타입을 그대로 베끼면 안 되는 곳을 알려 주는 것이 목적이다.

- 판정 우선순위는 **owner 결정 → 계획 기준선 a60216d → 가이드 → 원본**이다.
- 아래 `원본`은 Main.dc.html이다. `가이드`는 Agent-WBS-설계의도-및-구현가이드.md다. 숫자는 각 파일의 줄 번호다.
- 이 문서는 제품 코드를 수정한 보고서가 아니다.
- 단순 Mock 교체 작업(흉내만 내는 동작을 실제 연결로 바꾸는 일)과 실제 모순을 구분했다.
- 저자의 최초 브라우저 재현은 환경 제한으로 못했다. 대신 독립 리뷰가 브라우저로 확인한 증거를 추가했다(screenshots.md).
- `VM 확인` 표시는 [probe.mjs](probe.mjs)에서 원본 로직을 실행해 확인한 결과다(VM = Node의 가상 실행 환경).

각 항목은 세 부분으로 읽는다.

- **원본 사실**: 원본 코드에서 실제로 확인한 동작과 줄 번호.
- **기대·인수 기준**: 가이드·계획이 요구하는 동작, 그리고 제품을 판정하는 기준.
- **왜 중요한가**: 원본을 그대로 따라 하면 생길 수 있는 문제를 쉽게 풀어 쓴 설명. 판정 기준은 앞의 두 부분이다.

## 구현 완료 판정에 직접 영향을 주는 차이

### MM-01 / UI-03E, UI-06D — 완료 판정 근거 누락

- **원본 사실**
  - Gate는 5조건만 계산한다(3689–3699).
  - UI의 완료 가능 여부도 5조건·선행 차단만 검사한다(5298–5303).
  - `completeTask`는 확인 뒤 done을 직접 저장한다. Gate 재검사도 CI·병합 검사도 없다(5389–5397).
- **기대·인수 기준**
  - 가이드 495–496,657–668: 완료는 서버 Gate 판정 + ①Task 검사 근거 + ②통합 통과·PR 병합 후에만 된다.
  - 이 요구를 인수 기준으로 삼는다. 프로토타입의 조기 done을 복제하면 안 된다.
  - 확인창을 연 뒤 데이터가 바뀌는 경우도 서버에서 다시 판정해야 한다.
- **왜 중요한가**: 검사를 통과하지 않은 Task가 완료로 표시되면 일정·보고서가 모두 틀어진다.

### MM-02 / UI-12-05B — Telegram이 확인 안 된 사실을 확정 문구로 전송

- **원본 사실**
  - tgDiff는 done 상태전이만 보고 「통합 확인 통과·PR 병합」을 적는다(3957).
  - 첫 failed 전이도 재시도 횟수를 확인하지 않고 「재시도 한도 초과」로 적는다(3958).
- **기대·인수 기준**
  - 가이드 508–524: 검증된 완료 근거가 있거나 재시도 한도를 실제로 초과했을 때만 해당 이벤트를 보낸다.
  - 실제 CI/PR/재시도 근거가 충족된 경우에만 발송한다.
- **왜 중요한가**: 원본 문구를 조건 없이 재사용하면 잘못된 업무 알림이 나간다.

### MM-03 / UI-12-05A, SYS-02 — 저장 실패 시 Telegram 초안 소실

- **원본 사실**
  - `tgSave`는 mutate 실패 결과를 검사하지 않고 tgF=null로 만든다(6581–6588).
  - 복구 스냅샷 pickUi에 tgF/tgR/appUrlF가 없다(5044).
  - VM에서 확인: 저장된 이름은 그대로인데 초안은 null이 되고, 오류는 e500이다.
- **기대·인수 기준**
  - 가이드 70: 저장 실패 시 입력을 보존한다.
  - Telegram 연결·규칙·주소를 포함해 편집 초안을 유지하고, 성공했을 때만 편집창을 닫아야 한다.
- **왜 중요한가**: 검증된 현재 동작과 인수 기대가 다르다. 저장에 실패하면 사용자가 입력한 내용이 사라진다.

### MM-04 / UI-02E — 입력 문서 경로에 옛 정규식

- **원본 사실**
  - 신규 md 수집이 `/^docs\/prototype\/.*\.md$/`를 쓴다(4661). 현재 입력은 `prototype/docs/`이다.
  - 변경 파일 영역 분류도 `/^docs\//`로 검사한다(6945).
- **기대·인수 기준**
  - 가이드 225–240: 입력 문서는 prototype/docs/ 기준이다.
  - 실제 경로를 기반으로 인수해야 한다.
- **왜 중요한가**: 지금은 새 md가 md 목록에 추가되지 않고, 설계 문서가 프로토타입으로 잘못 분류된다.

### MM-05 / MOD-06A — 존재하지 않는 WP 선택 가능

- **원본 사실**
  - Wizard select는 WP-01~WP-06을 고정으로 표시한다(2794).
  - 초기 승인 직후에는 WP-01~WP-05뿐이다(3774–3782; VM 확인).
  - wizErrs는 wp가 존재하는지 검사하지 않는다. createTask는 일치하는 WP에만 삽입한다(6787,6795–6811).
- **기대·인수 기준**
  - 없는 WP-06을 선택하면 Task 사전에는 생성되지만 트리에는 배치되지 않는다.
  - 이후 상세는 wp.id를 기대하므로(5284–5290) 오류가 난다. 독립 리뷰 desktop/MM-05-browser.png에서 renderVals의 undefined.id와 메뉴 소실을 확인했다.
  - 제품은 실제 현재 WP 목록만 제공하고, 서버에서 존재·부모를 검증한다.
- **왜 중요한가**: 화면에서 고를 수 있는 값이 실제로는 없으면 데이터가 꼬이고 화면이 깨진다.

### MM-06 / UI-04-06 — 「코드 수정 요청」이 메시지/작업을 만들지 않음

- **원본 사실**
  - dsDrift는 drift.st='done'과 res 문자열만 바꾼다(4831–4835).
  - VM에서 메시지 수 before3→after3이다. 그런데 res에는 「메시지로 전달」이 표시된다.
  - 「계약에 반영」 역시 파일을 수정하지 않는다.
- **기대·인수 기준**
  - 가이드 449–452: 코드 수정 요청/계약 반영은 실제 Runner·계약 변경 경로가 필요하다.
  - 실제 요청 ID·전달·결과가 있어야 완료다.
- **왜 중요한가**: 현재 버튼은 처리된 것처럼 표시하지만 요청 증거가 없다.

### MM-07 / UI-08-01A, UI-08-02 — CI 재작업 요청·재실행은 상태 문구뿐

- **원본 사실**
  - ciIntFail은 CI/대기열/알림을 만들지만 원인 Task의 재작업 시도·메시지는 생성하지 않는다(4736–4745).
  - ciRetry는 항상 pass인 새 기록을 복제하고 병합됨으로 저장한다(4729–4735).
- **기대·인수 기준**
  - 가이드 475·491: Runner 실검사 → 실패 로그 전달 → 재작업 순서이고, 성공해야 실제 PR 병합이다.
  - 고정 성공이나 「요청됨」 문구를 통합 증거로 인정하지 않는다.
- **왜 중요한가**: 재실행이 늘 성공으로 기록되면 실제 실패를 놓친다.

### MM-08 / UI-03-09 — 실행 중 메시지 범위 협소

- **원본 사실**
  - deliver는 t.status==='running'일 때만 liveInject=false를 보고 pendingNext로 둔다(5419–5425).
  - QA/재검증의 실제 실행 상태는 qa/verifying이다(5811).
- **기대·인수 기준**
  - 가이드 355는 실행 중 세션 일반에 대해, 즉시 전달을 지원하지 않으면 다음 실행까지 대기하라고 한다.
  - QA/재검증 세션에도 즉시 전달 지원 여부가 맞게 반영되어야 한다.
- **왜 중요한가**: 이 범위를 프로토타입만으로 확정하면 안 된다. QA 중 보낸 메시지가 잘못 처리될 수 있다.

### MM-09 / UI-03-03 — SS의 「시작」을 상태만으로 판단

- **원본 사실**
  - depMet의 SS는 planning/approval/ready 외에는 전부 true다(3677–3681).
  - VM에서 failed/cancelled/paused도 actStart 유무와 관계없이 충족으로 나온다.
- **기대·인수 기준**
  - 가이드 652: SS는 선행의 시작을 기준으로 한다.
  - 계획 a60216d D-27: 시작 전 취소된 선행의 SS 관계를 제거해 후속을 풀고, 취소 CP 영향에 해소될 후속을 표시한다.
  - 상태 전이표도 owner Q-05가 승인했다.
  - 실패/중단을 시작으로 간주하는 다른 경로는 실제 시작 기록으로 확인한다.
  - 다른 미충족 선행은 계속 차단하고, CP의 제거 관계와 실제 해소 후속을 구분한다.
  - 원본의 상태 열거 배제를 곧바로 업무 규칙으로 확정하지 않는다.
- **왜 중요한가**: 시작한 적 없는 선행을 "시작함"으로 보면 후속이 너무 일찍 풀린다.

### MM-10 / UI-02 — 프로젝트 정보 저장 이력·기준 갱신 없음

- **원본 사실**
  - pjVM save는 project 필드를 Object.assign한 뒤 mutate entries=[]이고 pj=null만 처리한다(6487–6492).
  - 명시적 replan이나 프로젝트 변경 이력 생성이 없다.
  - 현재 화면 forecast 계산은 다음 렌더에서 바뀔 수 있다.
- **기대·인수 기준**
  - 가이드 122–123,1016: 모든 상태 변화를 기록하고, 날짜 변경과 재조정 정책을 따른다.
  - 프로젝트 수정 이력과 재계산·기준 버전 정책을 실제 구현에서 확인한다.
  - 원본에 없는 기록을 있다고 간주하지 않는다.
- **왜 중요한가**: 목표일을 바꿔도 기록이 남지 않으면 일정 변경의 이유를 추적할 수 없다.

### MM-11 / UI-06A/B — 실행 결과 토큰 검증 없음

- **원본 사실**
  - 결과 폼 tok는 `+f.tok || 0`로 저장·차감한다(5883–5914).
  - exErrs는 tok를 검사하지 않는다(5870–5876).
  - VM에 tok=-10을 넣어도 오류0이다.
- **기대·인수 기준**
  - 음수면 사용량 계산을 되돌릴 수 있고, NaN은0으로 취급된다.
  - 실제 Runner trust boundary(신뢰 경계, 바깥에서 들어오는 값을 검사해야 하는 지점)에서 비음수 유효 숫자·범위를 검증해야 한다.
  - 원본에 검증이 있다고 문서화하지 않는다.
- **왜 중요한가**: 잘못된 숫자 하나로 사용량 통계가 틀어진다.

### MM-12 / UI-12-01A, UI-02A — 권한 부족인데 연결 정상

- **원본 사실**
  - ghSaveToken은 statuses가 false일 수 있는데도 ok=true로 둔다(4804–4808).
  - checkGh는 gh.ok만 검사하고 scopes는 검사하지 않는다(3744–3763).
- **기대·인수 기준**
  - 가이드 233,1040–1041: 저장소 접근/작업에 필요한 4권한을 확인한다.
  - 누락 권한을 정상 연결·등록 가능으로 취급하지 않도록 실제로 검증해야 한다.
- **왜 중요한가**: 권한이 모자란데도 연결 정상으로 보이면, 등록 뒤 작업 단계에서야 문제가 드러날 수 있다.

### MM-13 / UI-12-05B — Telegram 메시지 길이 제한 없음

- **원본 사실**: tgMsg는 프로젝트/대상/사유/다음행동 문자열을 그대로 join한다(3922–3928). 길이 절단이 없다.
- **기대·인수 기준**
  - 가이드 540·1075: 4096자 제한, 대상명 절단.
  - 긴 사용자 입력을 포함한 실제 발송으로 인수해야 한다.
- **왜 중요한가**: 길이 제한을 지키지 않으면 긴 입력이 들어간 알림을 제대로 보낼 수 없다.

### MM-14 / UI-12-05B/D — 빌드 실패 중복 해소 범위 과대

- **원본 사실**
  - 통합/배포 등의 pass 한 건이 `R('buildFail|' + r.stage)`로 해당 stage의 모든 미해결 키를 닫는다(3988–3989).
  - 실패 키는 stage+PR/main이다(3990–3991).
- **기대·인수 기준**
  - 가이드 523: 이벤트+대상+원인별로 해소한다.
  - PR #A 성공이 같은 stage의 실패 PR #B를 해소하면 안 된다.
- **왜 중요한가**: 다음 #B 실패를 새 알림으로 보내는 오동작이 생길 수 있다(정적 추론, 즉 실행하지 않고 코드만 읽고 추론한 결과).

### MM-15 / UI-12-05A/D — 429의 실제 대기와 상태 불일치

- **원본 사실**
  - TG_ERR는 retry_after15다(3660–3662).
  - mutate는2500ms 후 tgDrain을 부른다(5032). tgDrain은 「15초 후 성공」 문구를 쓴다(6590).
  - 테스트 실패는 log만 자동으로 바뀌고 conf.test 실패 상태는 남는다(6571–6580,6590).
- **기대·인수 기준**
  - 가이드 1070–1072: 실제 retry_after를 지키고, 오류별로 재시도한다.
  - Mock 시간은 제품 동작 기준이 아니다. 실제 큐와 최종 연결 상태를 별도로 검증한다.
- **왜 중요한가**: 표시 문구와 실제 대기 시간이 달라 사용자가 상태를 잘못 이해할 수 있다.

### MM-16 / UI-12-04C — 메일 자동 재시도는 고정 이력뿐

- **원본 사실**
  - seed가 실패+15분 후 성공 행을 미리 만든다(3381–3385).
  - mailReport는 즉시 성공/실패 기록만 생성한다(4036–4047).
  - 동적 실패를15분 후 재시도하는 워커가 없다.
- **기대·인수 기준**
  - P2569와 가이드 407의 자동15분1회 재시도는 실제 서버 요구다.
  - 표기 정정: 이전 판에는 `UI2569`로 적혀 있었다. 원본 `Main.dc.html` 2569줄에 「실패한 메일은 15분 후 1회 자동 재시도」 문구가 실제로 있으므로 원본 줄 번호 표기 P2569로 고쳤다(독립 리뷰 B항 확인). 요구 내용은 바뀌지 않았다.
  - 원본 화면만으로 자동 재시도 완료로 판정할 수 없다.
- **왜 중요한가**: 화면에 재시도 기록이 보여도 실제로는 재시도하는 기능이 없다.

### MM-17 / SYS-01 — 응답 지연·reduced motion 설명과 실제가 다름
