## 대조 방법과 판정 범위

### 어떻게 대조하나

`python3 -B docs/ui/audit-milestones.py` 및 `--check`로 재현한다.

1. 계획 §3의 작업 행과 줄 번호, §2의 단계 선행, 각 작업의 ‘후’ 선행을 실제 a60216d 객체에서 읽는다.
2. M3 업무 화면은 공통 M3-01 후에 온다. 같은 단계의 ∥(병렬) 작업 사이에는 번호순 완료를 가정하지 않는다.
3. 모든 UAT에 필요한 **실제 대상 화면·이동 목적지, 서버 API, 실제 Runner 기능**을 표에 적는다.
4. 그 작업이 끝난 뒤 해당 UAT가 통과하도록 선행을 보탠다.
5. 자기 작업에서 구현한 기능을 그 작업의 인수에서 시험하는 것은 자기 의존으로 세지 않는다.
6. 합친 그래프를 위상 정렬(선행 관계를 지키는 순서로 줄 세우기)해 역방향 단계 의존과 순환을 검사한다.

### ‘M3-04에서 판정’의 뜻

‘M3-04에서 판정’은 M3-08보다 무조건 먼저라는 뜻이 아니다.

- 예: PROJECT-02의 GitHub 설정 화면은 M3-08 완료가 선행이다.
- 예: DASH-01은 M3-08의 설정 이동을 포함한다.
- M4의 화면 인수도 해당 M3 화면을 선행으로 둔다.

이 부가 선행들은 계획의 ∥ 허용 안에서 UAT 실행 순서를 정한 것이다. 계획 파일을 수정하거나 새로운 기능을 추가한 것이 아니다.

### API 작업 매핑

API 작업 매핑은 계획 범위를 따른다.

| 작업 | 범위 |
|---|---|
| M2-01 | 공통 인증/오류 |
| M2-02 | Task/명세/의존성 |
| M2-03 | 프로젝트 |
| M2-04 | 초기화 |
| M2-05 | Runner/시도 예약 |
| M2-06 | 결과/검증/Evidence/Gate |
| M2-07 | Planning/CP/일정 |

- 후속 보고서/PDF/메일/알림/설계/CI는 각각 M6-01/02/03/04/05·M7-04다.
- M3에는 M2 API와 보고 fixture를 쓴다.
- M4-01은 실제 client/outbox와 시험 명령 처리만 판정한다. 실제 Git 정리·PR 삭제를 확인하는 RESET-03과 구분한다.
- MAIL-04의 공용 주소 정책은 M6-04 API가 필요하다. 그래서 M6-03 인수 전에 M6-04를 완료한다.

### 이동과 링크를 세는 규칙

- 표에서 셸의 후속 메뉴는 **라우트만** 판정한다(P2-A).
- 그 외 실제 이동은 목적 화면 구현을 선행으로 둔다.
- 단순 링크 표시·API로 만든 기록 fixture는 대상 화면을 열거나 후속 Runner orchestration을 실행한 것으로 세지 않는다.
  - 왜: 링크가 보이는 것과 그 링크가 실제로 동작하는 것은 다르기 때문이다.
- M3 모달 검수는 M3 모달만 본다. 메일/TG 모달은 기존 MAIL-03/TG-04에서 판정한다.
- MSG의 링크 표시와 TG의 CI 사건 fixture는 실제 CI 결합 통과가 아니다. 실제 CI 상세를 여는 TASK-10-CI/TG-09는 M7-05에 둔다.

### 계획에 남은 참고 사항

- APPROVE-01의 ‘승인 요청’ 별도 API 경로는 contracts §2.1에 없다. `/approve`·`/reject`와 명세 충족 전이만 정의되어 있으므로 구현 전 계획 계약 정리가 필요하다.
- 아래 M2-02 매핑은 기존 전이·승인 기능의 배정 확인이다. 미정 엔드포인트가 이미 존재한다는 뜻이 아니다.
- a60216d의 D-29~32와 Q-09는 인용 기준만 갱신했으며, 이번에 새로운 인수 문장을 추가하지 않았다.
