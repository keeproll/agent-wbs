# Verum-SDN Agent WBS — 설계 의도 및 구현 가이드

> 이 문서는 함께 전달하는 **Agent WBS Standalone HTML Prototype**의 설계 의도, 확정된 결정, 실제 구현 시 주의할 점을 정리한 것입니다.
> 프로토타입은 "무엇이 보이고 어떻게 동작하는가"를, 이 문서는 "왜 그렇게 동작해야 하는가"와 "어디까지가 확정이고 어디부터가 임시값인가"를 설명합니다.
> 둘이 충돌하면 **이 문서가 우선**합니다.

## 0. 읽는 방법

### 0.1 전달물

| 전달물 | 내용 | 용도 |
|---|---|---|
| Standalone HTML | 9개 메뉴, Task 상세 9개 탭, Mock 데이터, 실제로 상태가 바뀌는 Interaction | 화면 구성 · 문구 · 흐름 확인, 기대 동작의 기준 |
| 이 문서 (MD) | 설계 의도, 도메인 규칙, 일정 모델, Agent 실행 정책, API 계약, 주의 사항 | 구현 판단의 기준 |

### 0.2 표기

- **[확정]** 팀장이 결정한 사항. 구현에서 임의로 바꾸지 않습니다.
- **[Mock]** 프로토타입에서 동작을 보여주려고 임시로 정한 값 · 규칙. 실제 구현에서 교체하거나 다시 정해야 합니다.
- **[미결]** 아직 정하지 않은 사항. 구현 전에 팀장에게 확인합니다.

### 0.3 프로토타입은 모든 화면 상태를 코드로 보여줍니다 [확정]

이 프로토타입은 제품에서 **발생할 수 있는 모든 화면 상태**를 그대로 구현하는 기준입니다. 데이터가 많은 상태만이 아니라 미등록 · 분석 중 · 빈 목록 · 연결 끊김 · 오류 같은 상태도 화면과 문구를 갖추고 있으니, 같은 상태에서 같은 화면이 나오도록 구현합니다.

- **설정 → 「점검 · Prototype」 탭 → 「화면 상태 미리보기」(Prototype 전용)** 로 아래 상태를 바로 열 수 있습니다. 이 미리보기 기능 자체는 실제 제품에 구현하지 않습니다.

| 상태 | 확인할 화면 |
|---|---|
| 진행 중 프로젝트 | 기본 Mock — Task 12건, 실행 · 검증 · 메시지 · 보고서가 있는 상태 |
| 미등록 | 빈 「프로젝트 등록」, 다른 메뉴 잠금(프로젝트 · 설정만 사용 가능) |
| 미등록 · 경로 확인 완료 | 등록 정보 입력, Runner 경로 확인 결과(Windows → WSL 경로, 크기 · 해시 · 저장소 기준 커밋) |
| 초기 분석 진행 중 | 단계 진행 표시(일시정지 상태), Runner 보고 로그 |
| WBS 초안 · 승인 대기 | 초안 트리, 재분석 요청, 초기 WBS 승인 |
| 승인 직후 · 기록 없음 | Task 11건만 있고 실행 · 검증 · 메시지 · Change Proposal · 보고서 0건 — **모든 메뉴의 빈 상태** |
| 초기화 후 Runner 정리 대기 | Runner 끊김 상태의 초기화 · 정리 대기 배너 · 초기화 기록 |
| Runner 연결 끊김 | 진행 중 프로젝트에서 Runner 중지 — 실행 불가 사유, 메시지 전달 실패 |

| 저장소 확인 실패 (주소 형식 · 접근 권한 · 필수 구조 없음) | 등록 화면 — 실패 사유 · 구조 표(없는 경로 빨강) | 주소 수정 / 권한 부여 / prototype/ (uiux · docs) push 후 다시 확인 |
| 입력 checkout 실패 (Git LFS 미설치) | 초기 분석 실패 배너 | git-lfs 설치 후 다시 시도 |
| 통합 확인 실패 | 빌드 · 통합 실행 상세(실패 단계 · 로그) · 병합 대기열 「통합 실패 — 재작업 요청」 · 대시보드 알림 | PR 병합 안 함 → 원인 Task 재작업 → 다시 실행 |
| 보호 경로 변경 거부 | Task 검사 첫 단계 실패 · 로그에 변경 경로 | Agent가 되돌림 |
| 배포 확인 실패 | 배포 확인 탭 「실패」 · 실행 상세 로그(포트 사용 중 등) · 알림 | 원인 해결 후 다시 실행 |
| 계약 파일 읽기 실패 (예: Neo4j 모델 파일 문법 오류) | 설계 메뉴 빨간 배너 · 계약 파일 「읽기 실패」 · 대시보드 알림 — 해당 항목은 마지막 성공 버전으로 표시 | 파일 수정 후 다시 읽기 |

| 미검증 CLI 버전 (예: Codex 0.168.0 업데이트) | Runner 준비 상태 「CLI 버전 — 하위 Agent 관측 검증」 주의 · 관측 등급 「미검증」 · 「검증 버전과 다름」 · 대시보드 알림 | 실행은 계속(보수 계산) · 재검증 후 등록 또는 검증 버전으로 고정 |
| 하위 Agent 관측 끊김 (실행 중 세션의 출력 단절) | 동시 실행 카드 「관측 미확인」 배너 · 세션 행 「관측 끊김」 · 새 실행 보류 사유 · 대시보드 알림 | 스트림 재연결 / 프로세스 그룹 확인 (그전까지 수를 줄이지 않고 보유) |
| 보고서 메일 발송 실패 (예: SMTP `535` 인증 실패) | 설정 → 보고서 · 메일: 「메일 서버 연결 실패」 배너 · 발송 기록에 실패 행(오류 원인) · 탭 배지 / 대시보드 알림 | 다시 보내기(행별 · 전체) / SMTP 수정 → 연결 확인 |
| Telegram 알림 전송 실패 (예: `403` 봇 차단 · 그룹에서 내보내짐) | 설정 → 알림: 연결 상태 「전송 권한 없음 · 봇 차단」 · 빨간 배너 · 전송 이력에 「실패」 행(오류 요약) · 탭 배지 / 대시보드 알림 | 원인 조치(봇 차단 해제 · 그룹 재초대) 후 테스트 알림 → 성공하면 배지 · 알림 해제. **Task · Agent 실행에는 영향 없음** |
| 화면 불러오는 중 | **메뉴별 스켈레톤** — 실제 화면 배치와 같은 모양(WBS: 도구 막대 + 트리 표 + 상세 패널, 대시보드: 지표 카드 4 + 패널 6, 목록 · 상세 화면: 왼쪽 목록 + 오른쪽 상세 등). 처음 접속 · 메뉴 이동 시 API 응답을 받을 때까지 표시 | — (10초 초과 시 「불러오기 실패」로 전환) |
| 화면 불러오기 실패 `503` | 메뉴 제목 + 오류 카드: 원인 · 확인할 것 · 마지막으로 불러온 시각 | 다시 시도 |
| 없는 Task 열기 `404 TASK_NOT_FOUND` | WBS 상단 안내: 취소 · 초기화로 삭제되었을 가능성 | 닫기 |
| 초기 분석 단계 실패 (예: zip 손상) | 실패 단계 빨간 표시 + 원인 · 조치 안내 | 다시 시도(실패 단계부터) / 등록 취소(초기화) |
| 입력 자료 차이 분석 실패 (예: Agent 세션 응답 없음) | 진행 표시의 실패 단계 + 원인 | 다시 시도(끝난 단계는 다시 하지 않음) |

오류 처리 규칙 [확정]:

- **저장에 실패하면 변경은 반영하지 않고, 편집 중이던 입력은 화면에 그대로 남깁니다.** 「다시 시도」가 성공하면 원래 동작처럼 편집 창이 닫힙니다. 입력을 잃게 하지 않습니다.
- Runner 보고 · 자동 처리(타이머)의 실패는 팀장 화면의 오류 막대로 띄우지 않습니다. 서버가 재시도하고, 반복되면 알림으로 올립니다.
- 오류 문구에는 **무엇을 하려다(대상 동작) · 왜 실패했고(코드 · 원인) · 무엇을 하면 되는지(조치)**를 함께 씁니다.
- 동시 수정 충돌은 Runner가 같은 Task의 상태를 먼저 바꾼 경우에 자주 생깁니다. 모든 수정 API는 `updatedAt`(버전)을 함께 보내고, 서버가 비교해 409를 돌려줍니다.

- **로딩 표시 규칙** [확정] — 상황에 따라 다르게 표시합니다. 프로토타입의 시간(0.8초 · 0.45초 등)은 Mock 지연이고, **실제 구현에서는 응답을 받을 때까지만** 표시합니다.

| 상황 | 표시 | 이유 |
|---|---|---|
| 처음 접속, 처음 여는 메뉴 (보여줄 이전 화면 없음) | **메뉴별 스켈레톤** (실제 배치와 같은 모양) | 데이터가 들어와도 레이아웃이 튀지 않음 |
| 이미 본 메뉴로 이동, 필터 · 정렬 변경 | **이전 화면 유지 + 헤더 아래 상단 진행 막대**, 응답이 오면 교체 (메뉴 강조는 즉시 이동) | 서버가 같은 PC에서 돌아 응답이 빠름 — 화면이 비지 않아 깜빡임이 없음 |
| 일정 재계산 (재조정 · 상한 변경 등) | **화면을 흐리게 + 「일정 다시 계산 중」 표시**, 그동안 클릭 막음 | 무엇이 갱신 중인지 분명히 하고, 갱신 전 값으로 판단하지 않게 함 |
| 화면 안 일부 영역만 다시 불러올 때 (예: 보고서 문서 전환) | **그 영역만 작은 스피너** | 다른 영역은 계속 사용 가능 |
| 저장 · 확인 · 승인 · 생성 · 초기화 버튼 | **버튼 안 진행 표시 + 「…중」 문구**, 그동안 버튼 비활성 (다른 동작 버튼도 비활성) | 두 번 누르기 방지, 무엇을 기다리는지 분명 |

보조 규칙: 응답이 약 0.2초 안에 오면 표시를 생략합니다. 한 번 띄운 스켈레톤은 최소 약 0.3초 유지합니다. 이미 받은 데이터는 바로 보여주고 뒤에서 갱신합니다. 약 10초 응답이 없으면 「화면 불러오기 실패」로 전환합니다. 전체 화면을 가리는 스피너는 쓰지 않습니다. 애니메이션은 「동작 줄이기」 설정 시 멈춥니다. 프로토타입에서는 설정 → 화면 상태 미리보기의 「페이지 로딩 (Mock 지연)」으로 끌 수 있습니다.
- **빈 목록 안내는 두 가지를 구분합니다:** 「아직 기록이 없음」(무엇이 생기면 여기에 표시되는지 안내)과 「조건에 맞는 결과 없음 — 필터를 바꿔 보세요」. 빈 목록을 아무 안내 없이 비워 두지 않습니다.
- **메뉴 잠금:** 프로젝트 등록 · 초기 WBS 승인 전에는 「프로젝트」와 「설정」만 열립니다. 설정(실행 PC · 동시 실행 · 실행 정책 · 일정 재조정 정책 · 작업 불가일)은 등록 전에 미리 정해 둘 수 있어야 하기 때문입니다. 다른 메뉴는 흐리게 표시하고, 누르면 이유를 안내합니다.
- 초기 WBS를 승인하면 각 Task에 「초기 분석 PL-000에서 식별 — 초기 WBS 팀장 승인으로 생성」 이력이 남습니다.

### 0.4 프로토타입을 볼 때 주의

- 모든 데이터는 Mock이며 **새로고침하면 초기 상태로 돌아갑니다.**
- Runner가 보고해야 할 결과(실행 결과, QA 결과, 가동 중단, 사용량 한도 등)는 화면의 Mock 버튼으로 직접 발생시킵니다. 실제 서비스에서는 이 버튼들이 없고 Runner API 호출로 대체됩니다.
- 설정 → 「데이터 정합성 점검」은 Mock 데이터의 일관성을 확인하는 개발용 기능입니다. 실제 서비스에서는 서버 측 무결성 검사 · 테스트로 옮깁니다.

## 1. 제품의 목적과 핵심 원칙

Agent WBS는 일반 프로젝트 관리 도구가 아닙니다. **개발 프로젝트를 Task 단위로 쪼개고, 각 Task의 상세 작업 명세 · 선행 관계 · Codex/Claude 협업 Workflow · 검증 Evidence · 승인 · 재계획을 관리하는 시스템**입니다.

### 1.1 가장 중요한 품질 기준

개발자(또는 Agent)가 Task 하나를 선택했을 때, 별도 해석 없이 다음에 답할 수 있어야 합니다.

- 무엇을 만들고, 왜 필요한가
- 어떤 선행 Task가 끝나야 하는가 (지금 실행 가능한가, 아니면 왜 차단되었는가)
- 어떤 작업 유형(분석 · 설계 · 구현 …)이고 어느 기술 영역(FE · BE · DB …)인가
- 어떤 파일 · API · 테이블 · 컴포넌트를 만들어야 하는가
- 무엇을 하지 않아야 하는가 (제외 범위)
- 완료 판단 기준(Acceptance Criteria)과 체크리스트, 필요한 산출물 · Evidence는 무엇인가
- 누가 작업하고, 누가 검증하고, 누가 승인하는가
- 지금 어느 단계이고, 언제 끝날 것으로 예상되는가

**Task 목록보다 Task 상세 명세의 품질이 이 제품에서 가장 중요합니다.** 화면을 단순화하더라도 Task 상세의 정보 구조는 줄이지 않습니다.

### 1.2 운영 원칙 [확정]

1. **실제 작업은 Agent가 합니다.** Runner 안의 Planning Agent(Codex · Claude 합의)가 VERUM-SDN 프로토타입을 분석해 Task를 식별하고, 소요 시간과 실행 등급(모델 · Effort)을 추정해 자동 등록합니다.
2. **팀장 개입은 최소화합니다.** Agent끼리 합의한 변경은 정책에 따라 자동 반영하고, 팀장은 정책 · 경계값을 정하고 예외만 처리합니다.
3. **일정은 고정 가정으로 확정하지 않습니다.** "1일 8시간 · 주말 제외 · Agent별 동시 1개" 같은 가정을 쓰지 않고, Runner가 보고한 실제 가동 기록 · 사용량 · 작업 불가일로 계속 다시 계산합니다.
4. **모든 상태 변화는 기록됩니다.** 재작업은 기존 결과를 덮어쓰지 않고 새 시도로 남기고, 일정 재조정은 기준 일정 버전으로 남기며, 모든 변경은 변경 전/후 값과 주체를 가진 이력으로 남깁니다.
5. **화면에서 한 동작은 실제 상태를 바꿉니다.** Toast만 띄우고 상태는 바뀌지 않는 가짜 Interaction을 만들지 않습니다.
6. **규모:** Task 100~200개 이상, 프로젝트 기간 최소 3개월을 전제로 설계합니다.

## 2. 시스템 경계와 아키텍처

### 2.1 2계층 구조 [확정]

```
┌──────────────────────────┐   REST (Runner → WBS 호출, Polling)   ┌─────────────────────────────┐
│ Agent WBS (이번 구현 대상) │ ◀──────────────────────────────────── │ Agent Runner (별도 개발)      │
│  - Web UI (팀장)          │   heartbeat · 세션 · 사용량 · 모델 보고  │  - 개발 PC(WSL)에서 실행       │
│  - REST API               │   실행 상태 · 결과 · Evidence 업로드    │  - Codex / Claude Code 세션 실행│
│  - PostgreSQL             │   메시지 Polling · ack                 │  - Planning Agent 포함         │
└──────────────────────────┘                                       └─────────────────────────────┘
```

- **WBS는 Runner로 push하지 않습니다.** Runner가 WBS API를 호출(Polling)해 대기 메시지와 작업을 가져가고, 결과를 보고합니다.
- 별도 채팅 서버, Session Observer, 실시간 세션 관찰 시스템을 만들지 않습니다.
- Runner의 내부 실행 화면은 범위 밖입니다.

### 2.2 기술 스택 [확정]

| 영역 | 기술 |
|---|---|
| Frontend | React + TypeScript + Vite + Mantine |
| Backend | Node.js + Fastify + TypeScript |
| Database | PostgreSQL + Drizzle ORM |
| Monorepo | pnpm Workspace (`apps/web`, `apps/api`, `packages/shared`, `packages/db`) |
| 통신 | Agent Runner와 REST API |

> 주의: 프로토타입 「설계」 메뉴의 Mock 구성(Neo4j · Kafka · QuestDB · Redis · WebSocket · SSE)은 **저장소 · 통신 종류별 화면을 보여주기 위한 예시**입니다. Agent WBS 자체의 기술 스택은 위 표가 기준이며, Mock 구성을 Agent WBS 구현에 도입하라는 뜻이 아닙니다.

### 2.3 프로토타입 코드 구조와 이식 대응

프로토타입 JavaScript는 이식을 고려해 4개 계층으로 나뉘어 있습니다.

| 프로토타입 | 역할 | 실제 구현 대응 |
|---|---|---|
| `MOCK`, `SCHED_MOCK`, `RUNNER_MOCK`, `EXEC_MOCK` | Mock 데이터 | DB Seed 또는 테스트 Fixture |
| `Api.loadProject()` | 데이터 접근 지점 | REST 호출 (`GET /api/projects/:id/wbs` 등)로 교체 |
| `Sel.*` | 순수 계산 (번호 · 차단 · Gate · 순환 · 일정 · 등급 판단 · CP 시뮬레이션) | **서버 Service 계층**으로 이동 (아래 주의) |
| `Component` (`*VM()`, `mutate`) | 화면 상태 · Interaction | React 컴포넌트 · 훅 · 상태 관리 |

> ⚠️ **`Sel`의 계산은 서버가 판정해야 합니다.** 선행 차단, 순환 검사, Completion Gate, Change Proposal 시뮬레이션, 일정 산정, 재조정은 클라이언트에서만 계산하면 Runner와 UI가 서로 다른 판정을 하게 됩니다. 클라이언트는 표시 · 미리보기 용도로만 같은 로직을 쓰고, 결정은 서버 결과를 따릅니다. `packages/shared`에 순수 함수로 두고 양쪽에서 쓰는 구성을 권장합니다.

## 4. 화면별 설계 의도

공통 원칙: **WBS가 중심 업무 화면**이고, 나머지 메뉴는 특정 업무의 전용 목록 · 관리 화면입니다. 메뉴 간 기능 중복을 피하고, **모든 주요 화면에서 관련 Task로 바로 이동**할 수 있어야 합니다.

### 4.1 대시보드 — "지금 무엇을 해야 하는가"

- 숫자와 차트는 다음 행동을 결정하는 데 필요한 것만 둡니다.
- **모든 요약 항목은 클릭하면 관련 Task 목록(WBS 필터 적용) 또는 해당 화면으로 이동**합니다. 이동할 곳이 없는 숫자는 만들지 않습니다.
- 구성: 일정 · 진행(진행률, 완료율, 예상 완료일과 범위, 작업량 · 가용 용량) → Task 현황 → 행동 패널 6개(일정 지연, Planning · 승인 대기, 실행 진행 · 대기, QA 실패 · 재작업, Gate 미통과, 메시지 확인 필요) → 분포 → **실행 등급별 결과** → 최근 실행 · 검증.
- 최상위 등급에서 재작업이 반복되면 상단에 팀장 확인 알림이 뜹니다.

### 4.2 프로젝트 — 등록 · 입력 자료 · 초기화 [확정]

프로젝트는 **하나만** 등록합니다. 프로젝트 화면에는 세 가지 흐름이 있고, 서로 다른 기능입니다.

**① 프로젝트 등록 (처음 한 번)**

- 등록 전에는 프로젝트 메뉴만 열리고 다른 메뉴는 잠깁니다(「먼저 프로젝트를 등록하세요」).
- 입력: 프로젝트 이름, **GitHub 저장소 주소**, 목표일(선택), **기술 제약(선택, 여러 개)**, **팀장 지시(자유 문장)**. [확정] 로컬 파일 경로 · zip 첨부 방식은 **없앴습니다** — 입력 자료와 개발 소스는 모두 GitHub 저장소 하나로 일관되게 다룹니다.
  - 기술 제약: 기술 이름 + 수준 **필수**(무조건 사용) / **조건부 선호**(조건이 맞으면 반드시 이것 — 조건 문장 함께 입력) / **금지**. 이미 정한 것만 적습니다. 예: PostgreSQL 16 필수, Redis 7 필수, QuestDB 조건부 선호(「시계열 데이터가 있으면」), 외부 클라우드 관리형 서비스 금지.
- **저장소 주소는 저장소까지만** 받습니다: `https://github.com/<owner>/<repo>` (`.git` 허용). 브랜치 · 폴더 · 파일 주소(`/tree/…`, `/blob/…`)는 거부합니다. 기준 브랜치는 **main** [확정]. private 저장소입니다.
- **저장소 디렉토리 규칙 [확정]:**

| 경로 | 내용 | 규칙 |
|---|---|---|
| `prototype/uiux/` | 입력 — 프로토타입 (**압축 해제 상태** HTML · JS · CSS · 이미지, zip 불가) | 필수 · Agent 수정 금지 |
| `prototype/docs/` | 입력 — 설계 의도 · 구현 가이드 · 디자인 정의 등 구현에 필요한 md (**여러 개 가능**) | 필수(md 1개 이상) · Agent 수정 금지 |
| `src/` | 개발 소스 — Agent 작업 영역, **빌드 기준** | 소스 코드만. 없으면 첫 커밋에서 생성 |
| `contracts/` | 계약 — API(OpenAPI) · 이벤트(AsyncAPI) · DB 스키마 · 마이그레이션 · 캐시 키 (4.12) | `src/`와 분리. 없으면 계약 설계 Task가 생성 |
| `.agentwbs/` | Agent WBS 설정 — 빌드 파이프라인 정의 `pipeline.yaml` (4.13) | 없으면 첫 커밋에서 생성 · 변경 시 팀장 승인 |

- 입력 자료는 모두 `prototype/` 아래에 둡니다 — 화면은 `prototype/uiux/`, 문서는 `prototype/docs/`. 「입력 변경 감지」 · 보호 경로 · 초기화 제외는 `prototype/` 전체 기준입니다.
- 이전 규칙(`prototype/` 바로 아래 프로토타입, `prototype/docs/` 문서)은 쓰지 않습니다 [변경 2026-11-23].

- 「저장소 접근 확인」 → Runner가 GitHub 인증(설정의 GitHub 연결)으로 접근 권한 · private 여부 · main 최신 커밋 · **필수 구조**(prototype/uiux/ 파일 구성, prototype/docs/ md 목록, src/ · contracts/ · .agentwbs/ 유무)를 보고합니다. 필수 구조가 없으면 등록할 수 없습니다(무엇이 없는지 표시).
- 등록 시 **main 최신 커밋을 입력 v1로 고정**하고, 그 커밋을 초기화 기준 커밋으로 기록합니다.
- **초기 분석(PL-000)** — Runner가 단계별 진행을 보고: GitHub 접근 · 커밋 고정 → 입력 자료 checkout(`prototype/` (uiux · docs) 을 읽기 전용 폴더로, **안의 스크립트 · 설치 명령은 실행하지 않음**) → 작업 준비(로컬 clone, 없는 `src/` · `contracts/` · `.agentwbs/` 생성 커밋, 기준 커밋 기록) → Codex 독립 분석 → Claude 독립 분석(설계 문서 반영) → 교차 검토 · 이견 조정 → **기술 결정 확정(팀장 별도 승인)** → WBS 초안 작성 → **팀장 승인**.
- **기술 결정 확정 [확정]** — 초기 WBS 승인과 **별도 단계**입니다. 팀장 지정 제약은 그대로 확정되고, Planning Agent가 프로토타입 · 설계 문서 분석으로 제안한 결정(저장소 추가, 통신 방식, 메시지 형식 등 — 근거 · 대안 포함)과 조건부 선호의 조건 충족 판단을 팀장이 하나씩 승인 · 반려합니다. 모두 정해야 「기술 결정 확정」이 눌리고, 확정된 결정 위에서 WBS 초안(계약 설계 Task가 먼저 오는 구조)을 작성합니다. 「재분석 요청」은 Codex · Claude 분석부터 다시 하되 확정된 기술 결정은 유지합니다.
- **초기 WBS는 팀장이 한 번 승인합니다** (이후 3개월 일정과 모든 Task의 출발점이므로). 초안은 Phase · Work Package · Task(분류, 담당, 작업량 범위, 선행 관계)로 보여주고, 「재분석 요청」(지시 추가)과 「초기 WBS 승인」을 제공합니다. 승인하면 WBS가 되고 기준 일정 v1이 만들어지며, 이후 변경은 Change Proposal로 진행합니다.
- Runner가 연결되어 있지 않으면 저장소 확인 · 초기 분석이 진행되지 않고 대기합니다. GitHub 인증이 실패하면 등록 · 입력 변경 확인 · push · PR이 모두 멈추고 설정과 대시보드에 알립니다.

**② 입력 자료 변경 → 팀장 확인 → Planning (진행 중 여러 번) [확정]**

- 프로토타입 · 설계 문서가 바뀌면 팀장(또는 담당자)이 **GitHub main에 push**합니다. 화면에서 파일을 첨부하는 기능은 없습니다.
- Runner가 **몇 분마다 main을 확인**해 `prototype/` (uiux · docs) 을 바꾼 커밋만 골라 알립니다(`src/` 등 Agent 작업 커밋은 무시). 프로젝트 화면 「입력 자료 변경 감지」 + 대시보드 알림 — 커밋 목록, 바뀐 파일(프로토타입 / 설계 문서 · 수정 / 추가 / 삭제 · 줄 수).
- **분석은 팀장이 시작합니다 (A 방식):** 팀장이 확인하고 「이 버전으로 분석」(선택: 팀장 지시) → 최신 커밋을 새 입력 버전으로 고정 → 변경 파일 checkout → **이전 버전 커밋과 git diff 비교**(바뀐 화면 · 기능 · 문서 문단) → **Planning(Codex · Claude 영향 분석)이 Task 추가 · 수정 · 재작업 · 취소를 Change Proposal로 작성** → 팀장 승인(또는 자동 반영 정책) → 일정 재조정. 중간 저장용 push마다 계획이 흔들리지 않게 자동 분석은 하지 않습니다.
- 「분석 안 함」은 「확인함 · 분석 안 함」으로 남기고, 다음 분석 때 그 변경도 함께 비교합니다.
- 입력 버전 v1, v2, …는 **커밋 번호**로 기록합니다(해시 대신). 이전 버전은 지우지 않습니다. 감지는 「누가 push했는지」가 아니라 「입력 경로가 바뀌었는지」로 판단하므로 GitHub 웹에서 직접 고친 경우도 같은 흐름입니다.
- 진행 중인 Task는 고정된 옛 입력 버전 기준입니다. 영향받는 진행 중 Task는 Change Proposal에서 「입력 변경 영향」으로 표시하고 재작업 여부를 정합니다.
- 각 Task에 **출처 입력 자료 버전(srcV)**을 기록합니다. 버전 목록에서 버전별 출처 Task 수를 보여줍니다.
- 이미 완료된 Task에 영향이 있으면 그 Task를 고치지 않고 수정 Task 또는 재작업 후보로 제안합니다(완료 Task · 검증 결과 보존 원칙).

**③ 프로젝트 초기화 (처음부터 다시)**

- 의미 [확정]: **진행 중인 모든 작업을 중지하고, 지금까지의 모든 기록 · 결과 · 산출물을 삭제**합니다. 보관하지 않습니다. Agent WBS와 Runner는 프로젝트 등록 전 상태가 되고, 화면은 빈 「프로젝트 등록」으로 돌아갑니다.
- 삭제 대상:
  - Agent WBS: Task · 의존성 · 명세 · 체크리스트 · 실행 시도 · 검증 · Evidence 파일 · Change Proposal · 메시지 · 이력 · 기준 일정 · 재조정 · 보고서 · 알림 · 입력 자료 버전 기록 · 등록 정보
  - Runner: 실행 중 Agent 세션(하위 Agent 포함) 종료, 작업 대기열 · 입력 checkout 사본 · worktree · 실행 로그 · 임시 파일 삭제
  - 작업 저장소(GitHub): **Agent 브랜치 삭제 · 열린 Agent PR 닫기, main에 「되돌림 커밋」을 push해 `src/` · `contracts/` · `.agentwbs/` 를 등록 시점 기준 커밋 상태로** 되돌림. **강제 push(history 덮어쓰기)는 하지 않고**, 입력(`prototype/` (uiux · docs))은 그대로 둡니다.
- 삭제하지 않음: **입력 자료(prototype/ (uiux · docs) — GitHub에 그대로)**, **GitHub 연결 설정**, **등록 이전부터 저장소에 있던 코드**, **초기화 기록 한 줄**(시각 · 실행자 · 초기화 번호 · 삭제 Task 수 · 설정 유지 여부 · Runner 정리 상태 — 프로젝트 데이터와 별도 보관).
- 설정 · 실행 환경 정보(동시 실행 상한, 실행 정책, 재조정 정책, 작업 불가일, 실행 PC 사양, 세션 메모리 관측, Runner 가동 기록): **「설정 유지」 선택, 기본은 함께 삭제**. 삭제하면 Runner가 다시 연결될 때 PC 사양을 새로 보고합니다.
- 안전장치: 삭제 항목 · 건수와 Runner 정리 내용을 먼저 보여주는 확인 창, **프로젝트 이름 직접 입력**, 초기화 전 데이터 내보내기(선택).
- **초기화 번호(epoch)** — 초기화할 때마다 1 증가. 모든 Runner 보고에 초기화 번호를 붙이고, 번호가 다르면 Agent WBS가 거부합니다(409 `EPOCH_MISMATCH`). Runner가 꺼져 있으면 Agent WBS는 즉시 삭제하고 Runner 정리는 「정리 대기」로 두었다가, Runner가 다시 연결되면 정리 명령부터 실행합니다. 정리가 끝나기 전에는 새 초기 분석이 시작되지 않습니다. 이렇게 하면 PC가 꺼져 있거나 중간에 끊겨도 이전 작업이 새 프로젝트에 섞이지 않습니다.
- 초기화 직후에는 WBS가 비어 있으므로 승인할 것이 없습니다. 다시 등록하면 만들어지는 초기 WBS 초안을 그때 팀장이 승인합니다.

**프로젝트 정보:** 기본 정보, Phase / Work Package 구조, 상태 · 기간.
- 기간 표시는 **기준 일정 버전(vN)과 최초 기준(v1), 완료 예상의 범위**를 함께 보여줍니다. 하나의 날짜로 단정하지 않습니다.

### 4.3 WBS — 중심 화면

- **계층:** Project → Phase → Work Package → Task. 불필요한 계층을 강제하지 않습니다.
- **Task ID(`TASK-0024`)와 WBS 번호(`1.2.3`)는 다릅니다.** WBS 번호는 위치에 따라 서버가 계산하는 표시값이고, 모든 참조(의존성, 이력, 메시지, CP)는 Task ID로 합니다. 트리 구조가 바뀌어 번호가 바뀌어도 참조가 깨지지 않아야 합니다.
- **Tree Table**이 기본이고 **Gantt 보기**를 제공합니다. Kanban만으로 표현하지 않습니다.
- 필터 9종(검색, 작업 유형, 기술 영역, 상태, 담당 Agent, 우선순위, Phase, 선행 차단, 검증 상태), 정렬, 트리 펼치기/접기, 컬럼 표시 설정.
- **가로 스크롤 없음 [확정]** — Task가 많아 위아래 스크롤만으로 보게 합니다. 표는 화면 폭에 맞춰 늘고 줄며(고정 px 대신 `minmax(최소, fr)`), 관련 값은 한 칸에 두 줄로 묶습니다: 「유형 · 영역」, 「상태 · 검증」, 「진행률 · 체크리스트」, 「완료 예상 · 기준 대비(+범위)」. 기본 컬럼 8개(유형 · 영역, 담당, 상태 · 검증, 우선순위, 선행 Task, 진행 · 체크리스트, 완료 예상 · 기준 대비, 예상 실행) + 선택 1개(최근 변경). 셀 안 글자는 줄바꿈(한글은 단어 단위). 목록 영역 폭 약 1,000px(화면 1,280px)까지 가로 스크롤 없이 표시됩니다. 더 좁은 화면은 컬럼 설정에서 일부를 끕니다.
- **Gantt도 가로 스크롤 없이** 전체 기간을 화면 폭에 맞춰 표시합니다(일 · 주 확대 버튼 제거, 날짜 눈금은 주 단위 월요일 표시). 기간이 매우 길어지면(예: 6개월 이상) 실제 구현에서 기간 범위 선택을 추가합니다.
- 필터 결과에는 **매칭 Task의 상위 Phase · Work Package가 항상 함께** 표시됩니다.
- **목록 ↔ 상세 전환 [확정]:**
  1. 처음에는 원래의 표(Tree Table / Gantt)를 전체 폭으로 보여줍니다. Task 레일은 없습니다.
  2. Task를 클릭하면 표가 왼쪽으로 줄어들며 **Task 레일(260px)**이 되고, 오른쪽 나머지 영역 전체에 그 Task의 상세가 나옵니다(약 0.24초 전환 효과, 「동작 줄이기」 설정 시 없음).
  3. 레일 맨 위 오른쪽 **「펼치기」**를 누르면 상세가 닫히고 레일이 오른쪽으로 다시 펼쳐지며 원래 표로 돌아갑니다(필터 · 정렬 · 스크롤 유지).
  4. 레일을 40px 막대로 접는 기능은 두지 않습니다. 레일은 「있음(상세 열림) / 없음(표)」 두 상태뿐입니다.
  - 레일 내용: 표와 같은 필터 · 검색 · 정렬, Work Package 구분선, 상태 · ID · 제목. Phase/WP 접힘은 무시하고 모두 표시. 필터가 걸려 있으면 「목록 필터 n개 적용 중」.
  - 상세 상단: 위치 `7 / 12`, 「↑ 이전 · ↓ 다음」(레일 순서), 링크로 이동한 경우 「← TASK-xxxx로 돌아가기」. 열린 Task가 필터에 맞지 않으면 「목록 밖」.
  - 실제 구현: 주소 `/wbs/TASK-0007`(새로고침 · 뒤로 가기 · 공유), 키보드 ↑ ↓(또는 J / K) 이전 · 다음, Esc = 펼치기(프로토타입은 버튼만).
  - 넓은 팝업은 쓰지 않습니다. Task 상세 안에 편집 · 확인 · 변경 제안 팝업이 있어 겹치고, 다른 Task로 옮기기 어렵기 때문입니다. 팝업은 짧게 끝나는 편집 · 확인에만 씁니다.
- Task 생성은 **3단계 Wizard**(필수 항목 검증). 목록 Inline 편집만으로 모든 정보를 입력하게 만들지 않습니다.
- **Gantt:** 위 막대 = 기준 일정(최신 버전), 아래 막대 = 완료 예상(진행 중이면 진행률로 채움), 가는 선 = 낙관 ~ 비관 범위, 빗금 = 작업 불가일, 빨간 선 = 현재, 보라 점선 = 목표일. 일/주 확대.

### 4.4 Task 상세 — 가장 많은 설계 시간을 투자한 화면

**상단 고정 Summary:** Task ID / WBS 번호 / 제목, 작업 유형 / 기술 영역, 상태, 담당 Agent, 선행 차단 여부, 체크리스트 진행률, 검증 결과, Gate 상태.

**탭 9개:**

| 탭 | 의도 |
|---|---|
| 개요 | 목적 · 배경 · 범위 · 제외 범위 · 선행 조건 · 완료 조건 · 예상 산출물, **작업량 · 일정**, **실행 등급(모델 · Effort)** |
| 작업 명세 | **가장 중요한 영역.** 상세 요구사항, 수행 작업, 구현 절차, 입력 자료, 예상 출력, 관련 파일, 기술적 제약, 예외 처리, 관련 문서, Acceptance Criteria를 **섹션별 구조화 편집**. 자유 텍스트 하나에 몰아넣지 않습니다. Markdown · 코드 블록 · 파일 경로 표현 |
| 의존성 | 선행 · 후속 Task, 유형(FS/SS), 선행 상태, 차단 여부와 사유. 검색으로 추가 · 삭제, **자기 참조 · 중복 · 순환은 저장 차단**(순환 경로 표시) |
| 기술 설계 | 기술 영역에 맞는 설계만: DB(실제 컬럼 정의 테이블), BE/API(Endpoint, Request/Response, Validation, Error), FE(화면 · Interaction · 상태), DevOps(구성 파일 · 환경 변수 · 명령 · Health Check). **모든 Task에 모든 항목을 강제하지 않습니다** |
| 체크리스트 | 항목 ID, 내용, 필수/선택, 완료, 검증 방법, Evidence, 비고. 필수 미완료 시 Gate 통과 불가 |
| 실행 | 실행 시도(Attempt) 목록 — 시도마다 Agent, **실제 모델 · Effort**, 등급 조정 사유, 시작/종료, 결과, 변경 파일, 실패 사유 |
| 검증·Evidence | PASS/FAIL/BLOCKED, 명령, 기대/실제 결과, Evidence 경로, 결함, 재검증 |
| 이력 | 시각 · 주체 · 유형 · 내용 · 변경 전/후 |
| 메시지 | 팀장 ↔ Runner 작업 지시 · 응답 (아래 4.10) |

- **기본은 읽기 모드**, 편집 버튼으로 해당 영역만 편집, 저장/취소 명확. 편집 중 이동 시 「저장하지 않고 이동」 확인.
- 선행 · 후속 Task는 클릭 가능한 참조이고, 이동 후 **원래 Task로 복귀**할 수 있습니다(복귀 스택).
- 긴 기술 명세를 좁은 카드에 넣지 않습니다. DB 테이블 · API Schema는 충분한 가로폭을 확보합니다.

### 4.5 Planning

- Workflow: Codex 독립 분석 → Claude 독립 분석 → 교차 검토 → 이견 조정 → Change Proposal → (정책) 자동 승인 · 반영 → 일정 자동 재조정.
- 두 분석을 **나란히 비교**하고, 일치 · 이견 · 조정 결과를 구분합니다.
- **「일정 재조정 이력」 탭:** 재조정(RP-xxx)마다 계기, 실행 주체, 새 기준 버전, 완료 예상과 범위, 적용 가동률, **밀리거나 당겨진 Task의 전후 날짜**를 보여줍니다.

### 4.6 작업 실행

- 3분할: 왼쪽 Task · 실행 목록 / 가운데 선택 실행의 상태 · 결과 · 다음 작업 / 오른쪽 연결 메시지.
- Workflow: Claude 개발 → Codex QA → Claude 재작업 → Codex 재검증 → Completion Gate → 완료.
- 현재 단계, 담당 Agent, 다음 작업과 **실행할 수 없는 이유**(Runner 끊김, 사용량 한도, 슬롯 모두 사용 중, 선행 차단)를 표시합니다.
- **실행 이력과 메시지 이력을 섞지 않습니다.** Execution Attempt는 실행 단위, Message는 지시 · 응답 단위입니다.

### 4.7 검증

- 검증 결과 목록, Evidence 목록(Task · Checklist · Verification 연결), Completion Gate 현황(Task × 5개 조건).
- 결과 등록 자체는 작업 실행 화면에서 시도 단위로 합니다(기능 중복 방지).

### 4.8 변경 제안 (Change Proposal)

- 변경 사유, 대상 Task, 변경 전/후 Diff, 신규 · 삭제 · 수정 Task, 선행 관계 변경, 영향받는 후속 Task(차단 상태 변화), 승인 상태와 이력.
- **승인 전 미리보기와 실제 반영이 같은 로직**(`Sel.simulate`)을 씁니다. 미리보기에서 보인 결과와 반영 결과가 달라지면 안 됩니다.
- 완료 Task와 검증 결과는 임의로 삭제 · 수정하지 않습니다(삭제는 「취소됨」 상태 + 이력 보존).

### 4.9 이력 · 설정

- 이력: 기간 · 주체 · 유형별 필터, 변경 전/후, 관련 Task로 이동.
- 설정: 항목이 많아 **6개 탭**으로 나눕니다 [확정]. 한 번에 한 영역만 보이게 해 집중도를 높입니다.

| 탭 | 내용 | 탭 배지 |

| Agent | Agent 역할 · 기본 Workflow, 실행 정책(모델 · Effort), 하위 Agent | — |

### 4.10 팀장 ↔ Runner 메시지

- 일반 채팅이 아니라 **Task와 Execution Attempt에 연결된 작업 지시 · 응답 관리**입니다. 메신저식 말풍선을 쓰지 않습니다.
- 유형: 추가 지시 / 수정 요청 / 질문 / 일반 의견. 대상 Agent: Codex / Claude. 관련 실행 시도 지정 가능.
- **전달 상태:** Draft → Queued → Sent → Acknowledged, 또는 Failed / Cancelled. **Runner의 수신 확인(ack)은 작업 완료가 아닙니다.** Agent의 응답 · 작업 완료는 전달 상태와 별도로 표시합니다.
- **실행 중 추가 지시:** Runner가 실행 중 세션에 즉시 전달할 수 있는지는 Runner 기능에 따라 다릅니다(설정 「실행 중 전달」). 지원하지 않으면 **「다음 실행 대기」**로 두었다가 다음 실행 시작 때 전달합니다. 실시간 세션 제어를 지원하는 것처럼 표현하지 않습니다.
- **메시지는 공식 명세를 바꾸지 않습니다.** 범위 · AC · 선행 관계 · 기술 설계에 영향을 주는 요청은 메시지에서 「Change Proposal 작성」으로 연결합니다. 승인(또는 자동 반영 정책)을 우회하는 별도 변경 경로를 만들지 않습니다.
- 작성 중 내용 유실 방지(초안 유지), 전달 실패 사유와 재전송, 새 응답 표시.

### 4.11 보고서 [확정]

**용도:** 팀장 본인이 자주 확인하는 용도 + 상급자에게 주기적으로(주간보고) 보고하는 용도, 두 가지 모두.

| 종류 | 생성 | 대상 기간 | 보기 | 용도 |
|---|---|---|---|---|
| 일간 | 매일 07:00 자동 | 전날 00:00~24:00 | 팀장용 | 짧은 확인 — 어제 무엇이 진행됐고, 무엇을 확인해야 하는가 |
| 주간 | 매주 월요일 07:00 자동 | 지난주 월~일 | 팀장용 + **보고용** | 추세 — 일별 가동률 · 실행 · 완료 · 완료 예상 변화. 보고용은 상급자 주간보고 |

**핵심 원칙 — 보고서는 생성 시점의 스냅샷입니다.**

- 이 시스템은 일정이 계속 자동 재조정되므로, 나중에 다시 계산하면 "그 당시 무엇을 예상하고 있었는지"가 사라집니다. 보고서는 생성할 때 계산한 결과를 **그대로 저장**하고, 열 때 다시 계산하지 않습니다.
- 생성 이후 일정이 재조정되었으면 보고서는 고치지 않고 「생성 이후 일정 재조정 N회 — 현재 완료 예상 X (보고서 기준 Y)」만 표시합니다.
- 기간 지정 보고서는 이력(추가 전용) · 기준 일정 버전 · 재조정 기록 · Runner 세션 기록으로 해당 기간을 재구성하고, 생성 시점 스냅샷으로 저장합니다. 따라서 **이력 · 기준 일정 · 재조정 기록 · 세션 기록은 절대 덮어쓰거나 지우면 안 됩니다.**

**생성 주체:** Runner가 아니라 **Agent WBS 서버**가 생성합니다(Runner가 꺼져 있어도 생성). WBS 서버도 같은 PC에서 돌면 PC가 꺼진 날은 생성되지 않으므로, **서버 시작 시 누락분을 보충 생성**하고 「누락분 보충 — 예정 YYYY-MM-DD 07:00」으로 표시합니다.

**팀장용(상세) 구성 — PDF만 보고도 현황을 파악할 수 있어야 합니다** [확정]. PDF에서는 링크로 Task 상세를 열 수 없으므로, 판단에 필요한 Task 단위 내용을 보고서 안에 직접 담습니다.

- **보고서 화면:** 「메일 미리보기」(실제 보낼 HTML · 보내는 사람 · 받는 사람 · 제목 · 첨부), 「메일로 보내기」(받는 사람 선택 — 해당 종류 구독자가 기본 선택), 이 보고서의 발송 기록 펼침.
- **설정 → 보고서 · 메일:** 받는 사람 표(구독 · 보기 · PDF · 최근 발송 · 미리보기 · 테스트 · 중지 · 삭제), 받는 사람 추가, 메일 서버(SMTP: 서버 · 보안/포트 · 보내는 주소 · 계정 · 비밀번호 — 연결 확인 · 수정), 발송 기록(전체 / 실패만, 행별 「다시 보내기」, 「실패 건 모두 다시 보내기」).
- **실패 처리:** 실패는 발송 기록에 원인과 함께 남기고, 15분 후 1회 자동 재시도, 그래도 실패하면 대시보드 알림 + 설정 탭 배지. 팀장이 다시 보내면 스냅샷이므로 같은 내용이 갑니다. 발송 기록은 수신자를 삭제해도 남습니다.
- **초기화:** 「설정 유지」를 고르면 SMTP · 받는 사람을 유지하고 발송 기록만 지웁니다. 기본(삭제)이면 SMTP · 받는 사람 · 발송 기록 모두 지웁니다.

**PDF:** 화면용 HTML 하나로 만들고, 서버에서 **같은 HTML을 Playwright(Chromium)로 PDF 변환**합니다. PDF를 따로 그리면 화면과 내용이 어긋납니다. 서버에 Pretendard GOV 폰트를 함께 설치해야 합니다. A4, 섹션 단위 페이지 나눔. 파일 이름 예: `RPT-W-261027_보고용.pdf`. (프로토타입은 보고서 부분만 별도 프레임에 복사해 브라우저 인쇄 → 「PDF로 저장」으로 대신합니다.)

### 4.12 설계 — 제품 전체의 기술 결정 · 인터페이스 · 데이터 [확정]

Agent WBS로 만드는 제품은 Web 제품이며, FE · BE가 어떻게 통신하는지(인터페이스)와 데이터가 어떻게 저장 · 조회되는지(데이터)가 구현 전체의 기준입니다. Task별 「기술 설계」 탭은 그 Task가 다루는 부분만 보여주므로, 제품 전체를 보는 **「설계」 메뉴**(WBS 다음)를 둡니다.

**기준(정본) — 코드 우선 + 계약 먼저 [확정]**
- 기준은 **작업 저장소 main 브랜치 `contracts/` 의 계약 파일**입니다(`src/`는 소스 코드만 — 빌드 기준이므로 계약을 섞지 않음 [확정]). Agent WBS DB에 설계를 따로 두지 않습니다(이중 관리 · 불일치 방지). 형식별 파일 예:

| 대상 | 계약 파일 (예) | 표준 형식 |
|---|---|---|
| REST API | `contracts/api/openapi.yaml` | OpenAPI 3.1 |
| WebSocket · SSE · Kafka 이벤트 | `contracts/events/asyncapi.yaml` | AsyncAPI 3.0 |
| gRPC · Protobuf (채택 시) | `contracts/proto/*.proto` | Protocol Buffers |
| PostgreSQL | `contracts/db/postgres/migrations/*.sql` | SQL 마이그레이션이 기준 — `src/`의 Drizzle 스키마는 이것과 대조 |
| Neo4j | `contracts/db/neo4j/model.cypher` + `migrations/` | 모델 정의(라벨 · 관계 · 제약) + Cypher 마이그레이션 — 그래프 DB는 스키마를 강제하지 않으므로 모델 파일을 명시적으로 둠 |
| QuestDB | `contracts/db/questdb/tables.sql` | CREATE TABLE (기준 타임스탬프 · 파티션 · 보관 기간 · 중복 제거 키) |
| Redis | `contracts/cache/redis-keys.yaml` | 키 카탈로그(키 패턴 · 용도 · 값 · TTL · 무효화 · 영속성) |

- **계약 먼저:** 계약 설계 Task가 계약 파일 변경을 먼저 만들고, 팀장 승인으로 main에 병합되면 「확정 설계」가 됩니다. 구현 Task는 그 뒤에 진행합니다(FE · BE 병렬 가능). 진행 중 Task 브랜치의 차이는 「구현 중 · 브랜치」(변경 제안)로 보입니다.
- Agent WBS는 Runner가 읽어 보낸 계약 파일 내용을 **보여주고 대조만** 합니다. 처음에는 자주 쓰는 형식(OpenAPI · AsyncAPI · Drizzle · SQL)만 해석하고, 해석기가 없는 형식은 파일 그대로 보여줍니다.

**결정 권한 3단계 [확정]**

| 권한 | 대상 | 결정 방식 |
|---|---|---|
| 팀장 지정 — 필수 · 조건부 선호 · 금지 | 이미 정해진 것 (예: PostgreSQL · Redis 필수, 시계열 데이터면 QuestDB, 외부 클라우드 금지) | 프로젝트 등록 「기술 제약」. Agent가 바꿀 수 없음. 조건부 선호는 조건 충족 여부만 Agent가 근거와 함께 판단 → 팀장 승인 |
| Agent 제안 → 팀장 승인 | 정해지지 않았고 되돌리기 어려운 것 — 저장소 추가, 통신 방식(WebSocket · SSE · gRPC), 메시지 형식, 인증 방식 | Planning Agent가 근거 · 대안을 붙여 제안, 팀장 승인. 구현 중 바꿔야 하면 「기술 결정 변경」 제안(Change Proposal 유형) |
| Agent 재량 (기록만) | 되돌리기 쉬운 것 — 인덱스, 캐시 만료 시간, 모듈 내부 라이브러리 | Agent가 정하고 기록 |

- 조건부 선호의 판단 기준은 조건 문장에 함께 적습니다(예: 시계열 — 시간 순 대량 쓰기 · 거의 수정 없음, 하루 수백만 행 이상 또는 초당 수백 건 이상, 구간 집계 위주 조회, 보관 기간 정책). 기준에 못 미치는 소량의 시간 데이터(작업 이력 · 감사 로그)는 운영 DB에 둡니다.
- 결정을 나중에 추가 · 변경할 수 있지만 **데이터가 쌓인 뒤에는 이전 비용이 큽니다.** 그래서 조건부 선호로 미리 걸어 두어 분석 단계에서 걸러지게 합니다.

**화면 (프로토타입) — 탭 6개**
1. **구성도 · 계약 파일** — 계층별 구성 요소(클라이언트 · 서버 · 팀장 PC · 데이터), 연결(보내는 쪽 → 받는 쪽 · 방식 · 계약 파일), 계약 파일 목록(형식 · 기준 커밋 · 읽음 / 브랜치 초안 / 읽기 실패). 승인 대기 결정의 구성 요소는 점선, 반려된 것은 취소선.
2. **기술 결정** — 권한별 묶음, 결정 · 조건 · 근거 · 대안 · 결정자 · 시각 · 상태(확정 · 승인됨 · 승인 대기 · 반려 · 기록 · 변경 제안). 승인 대기는 승인 / 반려, 확정된 Agent 제안 · 조건부 선호는 「변경 제안」.
3. **인터페이스** — 방식별(REST · WebSocket · SSE · Kafka) 목록 → 클릭하면 레일 + 상세. REST: 인증 · 요청 · 응답 · 검증 규칙 · 오류 코드 · 읽고 쓰는 테이블(클릭 시 데이터 탭으로). 메시지 계열: 메시지(방향 · 스키마) · 규칙, Kafka는 파티션 키 · 파티션 수 · 보관 · 전달 보장 · 실패 메시지(DLQ) · 호환 규칙 · 소비 그룹.
4. **데이터** — 저장소별(PostgreSQL · Neo4j · QuestDB · Redis). PostgreSQL: 컬럼 · 제약 · 인덱스 · **사용하는 API**(API × 테이블 연결), Neo4j: 라벨 · 관계 · 제약, QuestDB: 기준 타임스탬프 · 파티션 · 보관 · 중복 제거 키 · SYMBOL · 수집 · 집계, Redis: 키 패턴 · 용도 · 값 · TTL · 무효화 · 영속성.
5. **소유권 · 흐름** — 데이터마다 원본 저장소 · 복제 · 동기화 경로 · 지연 허용. 저장소가 둘 이상이면 필수 — Agent는 원본에만 쓰고 복제는 정해진 경로로만 갱신.
6. **변경 · 불일치** — Runner가 Task 완료 · 병합 때 코드에서 실제 명세를 추출(OpenAPI 생성, DB 스키마 조회, 마이그레이션 확인)해 계약 파일과 대조한 결과. 호환 차이는 「계약에 반영」(기록 후 반영), 호환을 깨는 차이는 설계 변경 승인 또는 「코드 수정 요청」. 설계 버전(v1, v2, …, 호환 깨짐 표시).

- **상태 구분:** 각 항목의 상태는 담당 Task 상태에서 계산 — 계획 / 구현 중 · 브랜치 / 구현됨 / 검증됨 / 폐기.
- **Task 상세 → 기술 설계 탭**에 「제품 전체 설계에서 보기」 링크(그 Task의 API · 테이블)를 둡니다. Task 기술 설계는 「이 Task가 원장에 무엇을 추가 · 변경하는가」이고, 설계 메뉴가 전체 그림입니다.
- **빈 상태 · 오류:** 기술 결정 없음(등록 전 · 초기화 직후 — 메뉴 잠금 또는 안내), 계약 파일 없음(계약 설계 Task 전), 계약 파일 읽기 실패(배너 · 대시보드 알림 · 마지막 성공 버전으로 표시), 승인 대기 결정(배너 · 탭 배지), 불일치(탭 배지 · 대시보드 알림).
- 초기화하면 설계 원장 표시는 비워집니다(기준인 계약 파일은 저장소와 함께 기준 커밋으로 되돌아감).

**WBS · 실행과의 연결**
- Planning: 초기 WBS에 **계약 설계 Task가 먼저** 옵니다(인터페이스 · 스키마 계약 → 승인 → 구현).
- 분할 기준: 「계약 먼저」, **같은 설계 항목(같은 테이블 · 엔드포인트 · 토픽)을 바꾸는 Task는 자동으로 같은 충돌 묶음** — 동시에 실행하지 않음.
- Runner: Agent 지시문에는 원장 전체가 아니라 **그 Task가 다루는 항목과 직접 연결된 항목만** 넣습니다.
- 검증: Task가 건드린 항목의 계약 일치 · 마이그레이션 존재 · 계약 테스트 통과를 Verification 자동 검사 항목으로 둡니다(실패 시 QA FAIL). Completion Gate 5조건은 그대로입니다.

### 4.13 빌드 · 통합 — Runner가 직접 실행 [확정]

**왜:** 코드만 보고 정상 실행을 판단하지 않습니다. Agent가 「테스트 통과」라고 보고하는 것은 근거가 아니며, **Runner가 실제로 빌드 · 테스트 · 기동 · 브라우저 접속을 실행하고 그 결과(종료 코드 · 로그 · 스크린샷)를 근거로** 남깁니다.

**외부 CI(Jenkins 등) 대신 Runner [확정]:** 팀장 PC 한 대 · 1~3명 규모에서 Jenkins는 상시 메모리 · 플러그인 관리 부담이 있고, Runner와 CPU를 두고 따로 스케줄링해 서로를 모릅니다. Runner는 이미 「무거운 작업 상한」 · 대기열을 가지고 있으므로 Agent 세션과 빌드를 한 조절기로 관리합니다. 단 **CI 엔진을 새로 만들지 않습니다** — 단계 정의는 저장소 `.agentwbs/pipeline.yaml`, 서비스 기동은 Docker Compose에 두고 Runner는 순서대로 실행 · 기록만 합니다. 팀이 커지면 같은 정의를 GitHub Actions로 옮길 수 있습니다.

**GitHub 연결:** Task마다 브랜치 → **PR**. Runner의 검사 결과를 PR **commit status**(`agentwbs/task`, `agentwbs/int` …)로 보고해 합류할 1~2명이 GitHub에서도 봅니다. main 보호 규칙: 「agentwbs/int 통과」 필수. 입력(`prototype/` (uiux · docs))만 바꾼 PR은 통합 확인 대신 경로 검사만 하는 예외(입력 갱신은 팀장이 직접 push하므로 보통 해당 없음).

**4단계 확인**

| 단계 | 언제 · 어디서 | 내용 | 통과 조건 · 실패 시 |
|---|---|---|---|
| ① Task 검사 | Agent 작업 종료 직후 · Task worktree | 의존성 설치 → **보호 경로 검사**(`prototype/` · `.agentwbs/` 변경, 빌드 결과물 커밋 거부) → 타입 검사 → lint → 단위 테스트(영향 패키지) → 빌드(영향 패키지, `src/`) → **계약 테스트**(`contracts/` 대조) | 통과해야 검증 Agent에게 넘어감. 실패 로그를 Runner가 Agent에게 전달 → 같은 시도 안에서 수정 |
| ② 통합 확인 | 검증 PASS 후 **병합 대기열** · 한 번에 하나 | main + PR 병합본 → 전체 빌드 → 전체 테스트 → 마이그레이션(빈 DB부터) → docker compose 서비스 기동 → 앱 기동 · health check → **E2E 핵심 경로(Playwright)** | 통과해야 PR 병합. 실패하면 **병합하지 않고**(main 보호) 원인 Task에 재작업 요청 · 대시보드 알림 |
| ③ 야간 점검 | 매일 02:00 · main | 전체 E2E · **화면 스크린샷 ↔ `prototype/uiux/` 비교** · 주요 API 응답 시간 · 불안정 테스트 판정 | 실패 시 알림 · 원인 Task 추적 |
| ④ 배포 확인 | 팀장 요청 또는 Phase 완료 | 운영 빌드(Docker 이미지) → compose up → health check → **Playwright로 실제 URL 접속**(로그인 · 핵심 화면 · 주요 API) → 스크린샷 · URL 기록 | **「Web Service 정상 기동 + 브라우저 접속」 = 배포 확인** [확정]. 이 PC든 다른 서버든 같은 절차 |

**규칙**
- 파이프라인 정의는 **main 기준 버전**으로 실행합니다. Task 브랜치에서 정의를 바꾸거나 테스트를 지워 통과시킬 수 없습니다. `.agentwbs/` 변경은 팀장 승인, 기존 테스트 삭제 · 약화는 검증 Agent가 따로 확인합니다.
- **자원:** 데이터 서비스(PostgreSQL · Redis · 필요 시 Neo4j · Kafka · QuestDB)는 Docker Compose로 **한 벌만** 띄워 공유하고, Task 검사는 worktree별 DB · 스키마 · 토픽 이름으로 분리합니다. 전체 기동 E2E는 통합 확인에서 한 번에 하나만.
- **불안정 테스트:** 실패 테스트는 1회 자동 재시도, 재시도로만 통과하면 「불안정 후보」. 격리된 테스트는 통과를 막지 않되 결과를 기록하고 담당 Task에 수정을 배정합니다.
- **병합 대기열이 길어지면** 여러 PR을 묶어 확인하고 실패 시 나눠서 원인을 찾습니다.
- **캐시**(pnpm 저장소, 작업 캐시)는 사실상 필수입니다.
- **결과 보관 [확정 2026-11-23]:** 보관하는 것은 **커밋 해시와 실행 기록**뿐입니다. Runner가 API(`/api/runner/ci/runs`)로 Agent WBS 서버에 보고하고, 서버가 **PostgreSQL**에 저장합니다 — 실행 ID · 단계 · 커밋 해시 · 브랜치 · PR · 결과 · 단계별 시간 · 실패 단계 · 근거 파일 위치. 같은 결과는 GitHub commit status로도 커밋에 붙습니다.
  - **빌드 결과물(jar · 번들 · Docker 이미지)은 보관하지 않습니다.** 저장소에 커밋하지 않고(`.gitignore`), 컨테이너 저장소(GHCR 등)에도 올리지 않습니다. 필요하면 **커밋 해시로 다시 빌드**합니다.
  - 다시 빌드해도 같은 결과가 나오도록: lockfile 고정 설치(`--frozen-lockfile`), Dockerfile의 기반 이미지는 digest로 고정, 파이프라인 정의는 해당 커밋의 `.agentwbs/` 사용.
  - 근거 파일(로그 원문 · 스크린샷)은 Runner PC의 저장소 밖 폴더(예: `~/.agentwbs/runs/<실행 ID>/`)에 두고 일정 기간(기본 30일) 후 삭제 — DB에는 위치와 요약만.
  - Runner PC의 로컬 Docker 이미지는 배포 확인에 쓰고 나면 다음 배포 확인까지만 남습니다(보관 대상 아님). 배포를 되돌릴 때는 직전 통과 커밋 해시로 다시 빌드 · 기동합니다(수 분).
  - 배포 파일 제공은 나중에 GitHub Releases로 합니다 — 릴리즈 태그도 「배포 확인을 통과한 커밋 해시」에 붙입니다.
- Completion Gate 「필요한 Verification 통과」의 근거에 ①(Task 검사) 결과가 들어가고, 완료(done)는 ② 통과 · PR 병합 후입니다. **기계 검사 통과는 필요조건일 뿐 충분조건이 아닙니다** — 수용 기준은 검증 Agent가 따로 판정합니다(Mock CI-0118 → ATT-0007-2 FAIL 예).

**화면 (프로토타입) — 「빌드 · 통합」 메뉴 (검증 다음)**
- 상단: main 상태(정상 / 깨짐 · 커밋 · E2E) · 요약(실행 수 · 미해결 실패 · 병합 대기 · 마지막 배포 확인).
- 탭: **실행 기록**(단계 필터 → 클릭 시 레일 + 상세: 대상 · Task · 시도 · 계기 · GitHub 보고 상태 · 단계별 결과 · 실패 로그 · 스크린샷 · 다시 실행) / **병합 대기열** / **배포 확인**(실행 · 마지막 결과 · URL) / **파이프라인 정의**(단계 · 통과 조건 · 규칙 · 실행 설정) / **불안정 테스트**(격리 · 해제).
- Task 상세 · 작업 실행의 실행 시도에 「Task 검사 통과 / 실패 · CI-xxxx」 표시 → 클릭 시 해당 실행.
- 오류 상태: 통합 확인 실패, 보호 경로 변경 거부, 배포 확인 실패(포트 사용 중), 빈 상태(실행 기록 없음).

### 4.14 알림 — Telegram [확정]

**목적:** 팀장이 PC 앞에 없어도 「지금 사람이 봐야 하는 일」을 휴대폰으로 받습니다. 알림은 **알려 주기만** 하고, 승인 · 조치 · 읽음 처리는 모두 WBS 화면에서 합니다(Telegram에서 버튼 · 응답으로 승인하지 않음).

**구성 [확정]**
- 봇 1개(BotFather 발급 토큰) → 수신 대화 1개(개인 대화 또는 일반 그룹 · 슈퍼그룹). 채널 · 토픽 · 여러 수신 대화는 이번 범위 밖.
- 범위는 **현재 프로젝트 하나**입니다. 화면에는 「현재 프로젝트: …」만 읽기 전용으로 표시하고 프로젝트 선택은 두지 않습니다(다중 프로젝트는 추후 — 그때 프로젝트별 규칙 · 수신 대상을 추가).
- 발송은 **Agent WBS 서버**가 대기열로 처리합니다. 브라우저가 닫혀 있어도 보내고, Runner PC에서 보내지 않습니다.

**이벤트와 정확한 의미 [확정]** — 기본값: 실패 · 관리자 개입 · 승인 요청 · 빌드 실패 켜짐, Task 완료 · 빌드 성공 꺼짐

| 이벤트 | 보내는 시점 (상태 전이) | 보내지 않는 것 |
|---|---|---|
| Task 완료 | WBS 최종 완료 판정 — Completion Gate 통과 · 통합 확인 통과 · PR 병합 후 | Agent 시도 완료, Runner 종료 코드 0, 검증 PASS만 |
| Task 실패 | 검증(QA) FAIL **확정**, 실행 시도 실패가 **재시도 한도 초과** | 시도마다 · 자동 재시도 중의 실패 |
| 관리자 개입 필요 | CLI 로그인 만료 등 Runner 준비 상태 「실패」, GitHub 인증 실패, 하위 Agent 관측 미확인(보유), 입력 자료 변경 커밋 감지(팀장 확인 대기) | 「로그인 만료 7일 전」 같은 경고 |
| 승인 요청 | Change Proposal 승인 대기, 기술 결정 승인 대기 · 변경 제안, 초기 분석의 기술 결정 확정 · 초기 WBS 승인 | 자동 반영된 Change Proposal |
| 빌드 성공 | ② 통합 확인 · ④ 배포 확인 통과 | ① Task 검사(너무 잦음), ③ 야간 점검 통과 |
| 빌드 실패 | ② 통합 확인 · ③ 야간 점검 · ④ 배포 확인 실패 — **실패 단계(빌드 / 테스트 / E2E / 기동)를 메시지에 명시** | ① Task 검사 실패(Agent가 같은 시도 안에서 고침) |

「빌드 성공 ≠ 테스트 성공」입니다 — 메시지에 어떤 단계까지 통과했는지 적습니다.

**생성 방식 — 상태 전이(방식 A) [확정]**
- 서버가 데이터를 저장할 때 **저장 전 · 후 상태를 비교**해 위 전이가 생긴 경우에만 알림을 만듭니다. 대시보드 알림 목록을 그대로 보내지 않습니다(대시보드 알림은 「현재 상태」, Telegram은 「변화」).
- **중복 생략:** 키 = 이벤트 + 대상 + 원인(예: `admin|ready-codex`, `buildFail|int|#9`, `approve|cp|CP-002`). 같은 키는 **해소될 때까지 1번만** 보내고, 다시 생기면 이력 행에 「중복 생략 n회」만 늘립니다. 해소(로그인 복구 · 인증 복구 · 통과 · 승인 처리 · 분석 시작)되면 키를 닫고, 그 뒤 다시 생기면 새 알림입니다.
- 알림 끄기 · 규칙 꺼짐 상태에서 생긴 이벤트는 나중에 몰아서 보내지 않습니다.

**메시지 형식 [확정 — 고정, 템플릿 편집 없음]** — 일반 텍스트(parse_mode 없음)

```
[Agent WBS] 빌드 실패
프로젝트: Verum-SDN Agent WBS — Self Development
대상: ② 통합 확인 — PR #9 (TASK-0004)
상태: 실패 — 실패 단계: E2E (task-detail.spec.ts). PR 병합 보류, main은 그대로
이유: 원인 후보: 마이그레이션 번호 충돌 (미확정)
발생: 2026-11-05 10:20
다음 행동: WBS 빌드 · 통합에서 실패 로그 확인 · 원인 Task 재작업
WBS에서 확인: http://192.168.0.10:5173/ci/CI-0127
```

- 「상태」는 확정된 사실만, 확인되지 않은 원인은 「이유」에 **(미확정)** 으로 표시합니다.
- 토큰 · 비밀값 · 로그 원문 · 실행 명령어 · 사내 경로는 넣지 않습니다. 4096자 제한을 넘지 않게 대상 이름을 자릅니다.
- 「WBS에서 확인」 링크는 **Agent WBS 접속 주소** 설정으로 만듭니다(아래). 비어 있으면 링크 줄을 뺍니다.

**Agent WBS 접속 주소 [확정]** — 메일 「전체 보고서 보기」와 Telegram 링크가 함께 씁니다(이전의 `localhost:5173` 하드코딩 제거).
- 비어 있으면 링크를 넣지 않습니다. `localhost` · `127.0.0.1` 이면 링크는 넣되 「이 PC에서만 열림 — 휴대폰에서 열 수 없음」 경고를 보여 줍니다. 같은 네트워크 주소(예: `http://192.168.0.10:5173`)를 권장합니다.

**연결 설정 흐름 (화면: 설정 → 알림)**
1. **Bot Token** 입력 → 「봇 확인」(getMe) — 토큰 유효성 · 봇 이름만 확인합니다.
2. **수신 대상 찾기**: 안내(봇에서 /start, 그룹은 초대 후 `/start@봇`) → 「최근 대화 조회」(getUpdates) → 후보 목록에서 **팀장이 직접 선택** → 「이 대화 선택」. 자동 선택 · 자동 저장하지 않습니다. 결과 없음 → 재시도 안내, **다른 서비스가 Webhook 사용 중 → 직접 입력 안내(Webhook을 자동 해제하지 않음)**.
3. 또는 **Chat ID 직접 입력**: 숫자만(`^-?\d{5,20}$`), 그룹은 음수 그대로(`-100…` 포함). 전화번호 · `@사용자명`은 거부하고 이유를 보여 줍니다.
4. **테스트 알림 보내기** — 저장 전 현재 입력값으로 보냅니다. 성공(「전송 요청 수락」)해야 **「알림 사용」을 켤 수 있습니다**.
5. **저장 / 변경 취소** — 연결 설정과 알림 규칙은 각자 저장 · 취소합니다.

- **테스트 상태 초기화:** Bot Token 또는 Chat ID가 바뀌면 테스트 결과를 지우고(토큰 변경 시 봇 확인도) 다시 테스트해야 합니다. 「수신 대상 이름」(표시용)만 바꾸면 유지합니다.
- **토큰 처리 [확정]:** 저장 후에는 다시 보여 주지 않고 「●●●● 등록됨 (끝 4자리)」만 표시합니다. 「토큰 교체」(새 토큰 입력 모드)와 「교체 취소」(등록 토큰 유지)를 구분하고, 교체 모드에서 빈 값 저장은 거부합니다. **마스킹 문자열을 새 토큰으로 저장하지 않습니다**(형식 검사로 거부). 토큰은 서버에만 암호화 저장하며 console · URL · 전송 이력 · localStorage · 로그에 남기지 않습니다.
- **연결 상태 표시:** 설정 전 / 봇 확인 필요 / 수신 대상 테스트 필요 / 테스트 성공 / 토큰 오류(401) / 대화 없음(400 chat not found) / 전송 권한 없음 · 봇 차단(403) / 통신 실패 / 요청 제한 · 재시도 대기(429 retry_after).

**전송 이력**
- 열: 발생 시각 · 프로젝트 · 대상 Task/빌드 · 이벤트 · 수신 대상 · 전송 상태(대기 / 전송 요청 수락 / 실패 / 재시도 대기) · 시도 횟수 · 오류 요약 · 구분(업무 / 테스트). 필터 전체 · 업무 · 테스트.
- 행 선택 → 보낸 메시지 · 「WBS에서 확인」(Task → Task 상세, Change Proposal → 변경 제안, 빌드 → 빌드 · 통합 실행, 기술 결정 → 설계, 준비 상태 · GitHub → 설정 Runner 탭, 입력 자료 → 프로젝트).
- 「전송 요청 수락」은 Telegram API가 요청을 받았다는 뜻이며 **도착 · 읽음이 아닙니다**. 이력에 읽음 · 승인 상태를 두지 않습니다.
- **알림 전송 실패는 Task · Agent 실행 · 상태에 영향을 주지 않습니다.** 연결 오류가 생기면 탭 배지 · 대시보드 알림으로 알립니다.

**초기화 [확정]** — 프로젝트 초기화 시 전송 이력은 **항상 삭제**, 연결 설정 · 규칙은 기본 삭제(「설정 유지」를 고르면 남김).

**프로토타입 (Mock)** — 실제 Telegram API · 백엔드 · DB를 호출하지 않습니다. 화면 맨 위에 「실제 Bot Token을 입력하지 마세요」 배너, 「가상 토큰 채우기」(`000000000:MOCK_TOKEN_DO_NOT_USE_…`)만 사용. 「Mock 응답」(정상 · 토큰 오류 · 대화 없음 · 봇 차단 · 통신 실패 · 요청 제한)으로 봇 확인 · 테스트 · 업무 알림의 응답을 고릅니다. 기본 Mock은 설정 완료 · 켜짐 상태와 이력 5건(테스트 2 — 그룹 403 실패 포함, Task 실패 · 관리자 개입(429 재시도 후 성공) · 승인 요청(중복 생략 1회)), 「Mock: 처음 설정 상태로」로 빈 상태를 봅니다. 업무 알림은 다른 화면의 실제 Mock 동작(통합 확인 실패 · 준비 상태 실패 · GitHub 인증 실패 · 입력 변경 · 기술 결정 변경 제안 · Task 완료 등)에서 상태 전이로 생깁니다.

### 5.2 Task 분류 [확정]

**작업 유형과 기술 영역은 서로 다른 속성입니다.** 하나의 혼합 분류로 만들지 않습니다.

- 우선순위: 긴급(0) · 높음(1) · 보통(2) · 낮음(3)

### 5.2-1 Task 분할 기준 [확정]

**Task의 정의:** 혼자 검증할 수 있고, 혼자 되돌릴 수 있으며, 합쳐도 시스템이 정상 동작하는 **가장 작은 변경**. 부작용(side effect)을 최소화해, 다른 작업 중에 다시 고칠 일과 버그 추적 범위를 줄이는 것이 목적입니다.

**누가 정하나:** 팀장은 기준을 한 번 정하고(설정 → Task 분할 기준), **Planning Agent가 Task를 식별할 때 기준을 적용**해 Task마다 「분할 근거」를 남기며, **시스템이 Task 등록 · 수정 때마다 자동 점검**합니다. 기준 없이 Agent에게 맡기면 Agent · 분석 시점마다 크기가 들쭉날쭉해집니다.

**값:**

| 항목 | 값 |
|---|---|
| 크기 상한 | **Agent 실행 시간 4시간** — 상한이지 목표가 아님. 꽉 채울 필요 없음 |
| 크기 하한 | 30분 — 더 작으면 같은 목적 Task와 합치는 것을 검토 (Task마다 실행 · QA · Gate 비용이 붙음) |
| 바뀌는 파일 상한 | 8개 |
| 테스트 | **Task에 포함** — Acceptance Criteria를 확인하는 테스트는 그 Task 안에서 작성 (별도 Task로 빼면 혼자 검증할 수 없음) |
| 나누는 방향 | **A. 계층별 · 계약 먼저** — API 계약 정의 → DB 조회 · 인덱스 → API 구현 → UI(계약 기반 Mock으로 검증) → 연결 확인. 계층 하나로 끝나는 아주 작은 기능만 세로 단위 예외 |

**규칙 10개:**

| # | 기준 | 점검 방식 | 위반 예 → 나누는 방법 |
|---|---|---|---|
| 1 | 목적이 하나 (「동사 + 대상 하나」) | 자동 (제목의 「및 · 그리고 · / · +」) | API와 UI를 한 Task로 → 분리 |
| 2 | 주 기술 영역이 하나 | 자동 (기술 설계상 변경 영역이 둘 이상) | 테이블과 화면을 같이 변경 → 영역별 분리 |
| 3 | 크기 상한 이내 | 자동 (예상 실행 시간 · 파일 수) | 상한 초과 → 기능 단위로 더 쪼갬 |
| 4 | 혼자 검증 가능 | 자동 (AC · 체크리스트 없음 = 위반, 계획 중이면 주의) | 「화면 전체 완성 후 확인」 → 검증 단위로 분리 |
| 5 | 혼자 되돌릴 수 있음 | Planning Agent 판단 기록 | 공통 코드와 사용처를 같이 수정 → 공통 부분 선행 Task |
| 6 | 충돌 묶음이 하나 | 자동 | 두 모듈 동시 수정 → 모듈별 분리 |
| 7 | 공유 계약 변경은 따로 | Planning Agent 판단 기록 | 구현하며 API 응답 형식 변경 → 계약 변경 Task 선행 |
| 8 | 되돌리기 어려운 변경은 따로 | 자동 (DB 설계가 있는 비-DB 구현 Task) | Migration과 서비스 코드 함께 → 분리 |
| 9 | 정리와 기능 변경은 따로 | Planning Agent 판단 기록 | 기능 추가하며 구조 정리 → 정리 Task 선행 |
| 10 | 불확실하면 조사부터 | 자동 (신뢰도 하, 또는 비관/낙관 > 2.5배 · 차이 2시간 초과, 선행 분석 Task 없음) | → 짧은 분석 Task 선행 |

**점검 결과 상태:** 통과 · 의심(자동 점검이 위반 가능성 감지) · 위반 · 주의(하한 미달, 명세 작성 중) · 판단(Planning Agent 합의 기록) · 예외(사유 기록됨) · 꺼짐(설정에서 끔).

**위반 처리:**

- **아직 시작하지 않은 Task:** 「Planning Agent 분할 제안」 → 기준에 따라 나눈 **Change Proposal**(신규 Task 추가 · 선행 관계 재연결 · 원래 Task 취소)을 올리고, 자동 반영 정책이면 바로 반영 · 일정 재조정합니다. 「불확실하면 조사부터」 위반이면 분석 Task를 앞에 둡니다. 나뉜 Task는 원래 Task의 Acceptance Criteria를 나눠 갖고, 체크리스트도 함께 만들어져 혼자 검증할 수 있는 상태로 생성됩니다.
- **이미 시작된 Task:** 나누지 않습니다. **예외 사유를 기록**하거나(Codex · Claude 합의, 이력에 남음), 남은 일을 후속 Task로 제안합니다.
- **초기 WBS 승인 화면:** 「분할 점검 — 통과 · 의심 · 위반」 요약과 Task별 위반 표시. 위반은 승인 전 재분석 지시로 고치거나, 승인 후 분할 제안으로 고칩니다.
- **실행 중 신호:** Runner가 보고한 실제 바뀐 파일 수 · 실행 시간이 상한을 크게 넘거나 재작업이 반복되면, Planning Agent가 남은 일을 다시 나누도록 제안합니다.
- **버그 수정:** 완료된 큰 Task를 다시 여는 대신, 원래 Task에 연결된 **작은 수정 Task**를 새로 만듭니다.

**주의:** 작게 나눌수록 선행 관계가 늘고 동시 진행 폭이 줄 수 있습니다(일정 계산 · 동시 실행 화면에서 그대로 보임). 「혼자 검증 가능」을 지키려면 계약 기반 Mock이 필요합니다.

### 5.3 상태 모델

요구사항은 상태를 하나의 Enum으로 만들 필요가 없고, **Lifecycle · Planning Approval · Execution · Verification · Completion Gate를 개념적으로 구분**하라고 했습니다. 프로토타입은 사용자에게 보여줄 **대표 상태**를 다음과 같이 둡니다.

| 대표 상태 | 키 | 개념 | 의미 |
|---|---|---|---|
| 계획 중 | `planning` | Lifecycle | 명세 작성 중, 실행 요청 불가 |
| 승인 대기 | `approval` | Planning Approval | 승인 전에는 확정되지 않음 |
| 실행 대기 | `ready` | Execution | 선행 충족 시 실행 요청 가능 |
| 실행 중 | `running` | Execution | Runner에서 Agent 세션 실행 중 |
| 중단 · 재개 대기 | `paused` | Execution | Runner 중지 · 사용량 한도 · 오류로 끊김. 재개하면 **새 시도**로 이어감 |
| QA 진행 | `qa` | Verification | 검증 Agent QA 중 |
| 재작업 필요 | `rework` | Verification | QA FAIL |
| 검증 진행 | `verifying` | Verification | 재검증 중 |
| Gate 대기 | `gate` | Completion Gate | 검증 PASS, Gate 확인 후 완료 |
| 실패 | `failed` | Execution | 실행 실패, 원인 확인 필요 |
| 완료 | `done` | Lifecycle | Gate 통과 후 완료 처리 |
| 취소됨 | `cancelled` | Lifecycle | CP로 취소, 이력 보존 |

- **「차단」은 상태가 아니라 계산값**입니다(선행 조건 미충족). 상태와 별도로 표시합니다.
- 검증 상태(별도 속성): 미실시 · 검증 중 · PASS · FAIL · BLOCKED
- 실행 시도 상태: 실행 중 · 완료 · 실패 · 중단
- **상태는 색상만으로 구분하지 않습니다.** 항상 텍스트를 함께 표시하고, 상세 사유는 Tooltip/상세 영역에서 확인합니다.

### 5.4 의존성

- 유형: **FS**(선행 완료 → 후속 시작), **SS**(선행 시작 → 후속 시작)
- 추가 시 검증: 자기 참조(400 `DEPENDENCY_SELF`), 중복(409 `DEPENDENCY_DUPLICATE`), **순환(409 `DEPENDENCY_CYCLE` + 경로)**
- 순환 검사: 추가하려는 선행 Task에서 선행 방향으로 DFS하여 현재 Task에 도달하면 순환
- 선행 Task가 있는 Task 삭제는 거부(409 `TASK_HAS_SUCCESSORS`), 삭제는 soft delete

### 5.5 Completion Gate — 5개 조건 [확정]

| 조건 | PASS 기준 |
|---|---|
| 필수 Checklist 완료 | 체크리스트가 있고 필수 항목 모두 완료 |
| 필수 산출물 존재 | 필수 산출물이 지정되어 있고 모두 제출됨 |
| 필요한 Verification 통과 | 최근 검증 PASS (FAIL → FAIL, 그 외 → BLOCKED) |
| 미해결 차단 결함 없음 | 차단 결함 0건 |
| 필요한 승인 완료 | 팀장 승인 완료 (아니면 BLOCKED) |

- 조건마다 PASS/FAIL/BLOCKED와 **사유**를 표시하고, 하나라도 미충족이면 완료 버튼을 비활성화하고 이유를 설명합니다.
- **상태를 `done`으로 바꾸는 API를 따로 만들지 않습니다.** 완료는 서버가 Gate를 판정해 통과할 때만 처리합니다.

### 5.6 Change Proposal 변경 유형

`add`(Task 추가), `modify`(우선순위 · 제목 · 완료 조건 · 담당/검증 Agent · 범위 추가 · AC 추가), `remove`(취소), `dep-add`, `dep-remove`.

- 반영 보류 조건: 대상 Task 없음, **완료 Task 수정**, 순환 발생, 존재하지 않는 Work Package, 이미 적용된 변경 등.
- 반영하면 이력을 남기고, 영향받는 후속 Task의 차단 상태 변화를 계산하고, 일정을 재조정합니다.

## 6. 일정 모델 [확정 원칙 + Mock 수치]

### 6.1 왜 이렇게 만들었는가

실행 환경(WSL/PC)은 계속 켜져 있을 수도 있지만 **재부팅, PC를 켜지 못하는 날, 토큰 부족**이 반드시 발생합니다. 그래서 일정은 미리 가정한 근무 시간이 아니라 **관측된 가동 기록**으로 계산하고, 한 날짜 대신 **범위**로 보여주며, 변화가 생기면 **Planning Agent가 전체를 자동 재조정**합니다. 새 Task가 생기면 뒤 일정이 밀리고, Task가 삭제되면 당겨집니다.

### 6.2 입력

| 입력 | 출처 | 설명 |
|---|---|---|
| 작업량 | Planning Agent 추정 | Task별 **Agent 실행 시간**(세션이 실제 작업하는 시간)의 예상 · 낙관 · 비관, 예상 토큰, 신뢰도(상/중/하), 근거, 추정 주체 |
| 가동률 | Runner 세션 기록 | **최근 7일** Runner 세션(heartbeat 기반) 가동 비율. 기록이 72시간 미만이면 정책의 가정값(Mock 60%) 사용 |
| 동시 실행 한도 | 팀장 상한 + Runner 보고 | 상한 안에서 Runner가 조절한 현재 한도(하위 Agent 포함). 일정에는 **한도 ÷ (1 + 관측 하위 Agent 비율)**을 동시 Task 수로 사용 (7장 참고) |
| 충돌 묶음 | Planning Agent 지정 | 같은 묶음 Task는 동시에 하나만 — 일정에서도 직렬로 배치 |
| 사용량 | Agent 자체 조회 → Runner 보고 | 남은 사용량(%)과 리셋 시각. 0%면 리셋 시각 전까지 그 Agent 슬롯은 사용 불가 |
| 작업 불가일 | 팀장 등록 | 그날 용량 0 |
| 고정 시작일 | Task 속성(선택) | 그 날짜 이전에는 시작하지 않음 |

### 6.3 계산 (프로토타입 `Sel.schedule`)

1. 완료 Task는 실제 기록 사용. 진행 중 Task는 실제 시작 시각 순으로 먼저 슬롯에 배치하고, **남은 작업량 = 예상 × (1 − 진행률)**.
2. 나머지는 **List Scheduling**: 선행(FS: 선행 종료, SS: 선행 시작)과 고정 시작일을 만족하는 Task 중 가장 빨리 시작할 수 있는 것 → 우선순위 → WBS 번호 순으로 배치. 시작 시각은 **공용 동시 실행 자리 · 담당 Agent 상한 자리 · 같은 충돌 묶음의 직전 Task 종료** 중 가장 늦은 시각.
3. 배치는 "유효 작업 시간" 축에서 하고, **달력 날짜 환산** 시 `하루 24시간 × 가동률`(작업 불가일은 0)을 누적합니다.
4. 세 가지 시나리오를 함께 계산:
   - 중간값: 예상 작업량 × 관측 가동률
   - 낙관: 낙관 작업량 × 높은 가동률(관측 7일 중 상위값)
   - 비관: 비관 작업량 × 낮은 가동률(하위값)
5. 진행률 = Σ(예상 작업량 × 상태 단계 가중치) / Σ예상 작업량. 완료율은 Task 수 기준과 작업량 기준을 함께 표시.

### 6.4 기준 일정 버전과 자동 재조정

- 기준 일정은 **v1, v2, …** 버전으로 쌓입니다. v1은 초기 WBS 등록 시점 추정입니다. 이전 버전은 지우지 않습니다.
- **재조정 계기:** Task 추가 · 삭제 · 재추정, Change Proposal 반영, Runner 중단, 사용량 한도, 동시 실행 상한 · Runner 한도 변경, 작업 불가일 변경, 실행 등급 변경(작업량 재추정), 가동률 변화.
- 가동률 변화처럼 작은 변화는 **임계값**(Mock 기본 1일) 이상 벗어날 때만 새 버전을 만듭니다(`driftCheck`). 노이즈로 버전이 폭증하지 않게 하기 위함입니다.
- 재조정 기록(RP-xxx)에는 계기, 주체, 새 버전, 완료 예상 · 범위, 적용 가동률, **밀림 · 당겨짐 · 신규 편입 · 제외 Task의 전후 날짜**가 남고, 각 Task 이력에도 기록됩니다.
- 정책 「자동 재조정」을 끄면 재계산은 하되 새 기준 버전은 만들지 않습니다.

### 6.5 Runner 중단 처리

- Runner 세션이 끊기면(재부팅 · PC 꺼짐 · 오류 · heartbeat 미수신) 실행 중이던 시도는 **「중단」**, Task는 **「중단 · 재개 대기」**가 됩니다.
- 재개하면 **새 실행 시도**로 이어가고 기존 시도 기록은 보존합니다. 재개 시 등급은 직전 시도와 같게 유지합니다.

### 6.6 동시 실행 — PC 사양 기반 상한 + Runner 조절 [확정 원칙 + Mock 공식]

**왜:** 동시 실행 수를 실제로 제한하는 것은 Agent 개수가 아니라 ① PC 자원 ② 지금 병렬로 할 수 있는 일의 양(선행 관계) ③ 같은 코드를 건드리는 작업 간 충돌 ④ 사용량입니다. 고정값(예: 5개, 20개)은 이 요인들을 반영하지 못하므로, **상한은 PC 사양으로 정하고**(자동 또는 팀장 지정) 실제 수는 Runner가 조절합니다.

```
실제 동시 실행 수 = min( 상한(PC 사양 기반 자동 또는 팀장 지정), Runner 조절 한도, 병렬 가능한 Task × (1 + 하위 Agent 비율) )
                    + Agent별 상한, 충돌 묶음 직렬화, 무거운 작업 대기열
```

**실행 PC는 바뀔 수 있습니다** [확정]. 더 좋은 PC로 확장하거나 저사양 PC로 옮길 수 있으므로, 특정 PC 사양을 고정값으로 두지 않습니다. **Runner가 시작할 때마다 스스로 사양을 확인해 보고**하고, WBS가 권장 상한을 계산합니다.

| 항목 | 결정 방식 | 설명 |
|---|---|---|
| 카운트 기준 [확정] | 하위 Agent 포함 | Runner가 시작한 세션 + 그 세션이 띄운 하위 Agent(subagent) 전체 |
| 상한 결정 방식 | **자동(기본)** / 직접 지정 | 자동: PC 사양 기반 권장값을 상한으로 사용, PC가 바뀌면 재계산. 직접 지정: 팀장 값 유지, 권장값보다 크면 경고 |
| 전체 상한 | 권장 공식 | `floor((메모리 − 기본 사용 3GB − 메모리 예비) ÷ 세션당 평균 메모리)`, 2 ~ 64 |
| Agent별 상한 | 권장 공식 | `ceil(전체 × 0.75)` — 합이 전체보다 커도 됨 (한쪽에 일이 몰릴 때 여유 사용) |
| 무거운 작업 상한 | 권장 공식 | `min(전체, floor(코어 ÷ 3))` — 빌드 · 전체 테스트 · E2E · `pnpm install` 동시 실행 수, 초과분은 Runner 대기열 |

| 세션당 평균 메모리 | Runner 관측 (초기 1GB) | 실제 세션 메모리를 관측해 보정 → 권장값이 운영하면서 정확해짐 |

> 공식의 상수(기본 사용 3GB, 0.75, 코어 ÷ 3, 초기 세션당 1GB)는 [Mock 추정]입니다. 실제 운영 데이터로 보정하세요.

### 6.7 하위 Agent 관측 · 자원 확정 — hook 미사용 [확정 원칙 + 검증 결과]

**결정 [확정]: Claude Code · Codex의 hook을 쓰지 않습니다.** 하위 Agent 시작 · 종료 hook은 누락(Start 없는 Stop, 강제 종료 시 Stop 미발생 등)이 보고되어 있어, 자원 제어의 근거로 삼으면 슬롯이 새거나 실행이 멈출 위험이 큽니다. 대신 Runner가 직접 소유한 신호만 근거로 씁니다.

| 신호 | 용도 | 확정 근거 |
|---|---|---|
| CLI 출력 스트림 (Claude `stream-json`, Codex `exec --json`) | 하위 Agent 생성 · 상태 **관측**, 실시간 **추정** 수 | **아니오** — 검증된 버전에서만 보조 근거 |
| 세션 기록 파일 (transcript · 세션 로그) | 「실제 사용된 하위 Agent」 사후 확정 (8번) | 사용 내역 — 대상 버전 검증 후 |
| 프로세스 그룹 · cgroup (Runner가 세션마다 생성) | **실행 트리 종료 · 자원 해제 · 실측 CPU · 메모리** | **예** — 종료 · 자원의 유일한 확정 근거 |

**Codex `exec --json` 검증 결과 (팀장 WSL 환경, 2026-11-09)** — 결론: **「일부 관측」 등급.**

- 하위 작업 수행은 관측됨. 병렬 하위 작업이 실제로 겹쳐 실행됨(약 4.9초 겹침) — 하위 Agent를 세어야 하는 이유가 확인됨.
- ID · 상태 · 부모 연결은 **누락이 있음** → 정확한 실행 트리 · 동시 실행 수 집계 근거로 부족.
- 종료는 시험한 exec의 정상 종료만 확인. **자손 · 외부 명령 종료와 슬롯 반환은 미확인.**
- 해석 주의: `spawn_agent` 완료 = 생성 호출 완료(작업 완료 아님), `agents_states.completed` = Agent 작업 완료(프로세스 종료 아님), 부모 `turn.completed` ≠ 자손 정리 완료, 출력 없음 · 스트림 단절 ≠ 실행 수 0. 공개 저장소에 하위 Agent가 실행 중인데 `pending_init`으로 남는 보고도 있음.
- 미검증 항목(중단 · 재개 · 중첩 · 부모 강제 종료 · 스트림 단절 시 자손 상태)은 **보류**하고, 결과가 나오면 이 표를 갱신합니다.
- **검증 조건 (고정 기록):** Codex CLI **0.167.0**, 모델 **gpt-6.1-sol**(설정값), 모델 · 동시 하위 Agent 수 · 중첩 깊이 설정은 **기본값 그대로**, 실행 옵션 `exec --json --skip-git-repo-check`(Git 저장소 초기화 대신 사용). 이 조합이 바뀌면(CLI 버전, 모델, 동시 수 · 깊이 설정) 재검증 전까지 「미검증」으로 돌립니다.
- 주의: 실제 운영은 git worktree 안에서 실행하므로 `--skip-git-repo-check` 없이 돕니다. 저장소 안 실행에서 관측 결과가 달라지지 않는지 보류 항목과 함께 확인합니다.
- Claude `stream-json`도 같은 항목(1개 · 복수 · 중첩 생성의 ID 연결, 완료 · 오류 · 중단 · 재개, 부모 종료 · 스트림 단절 시 자손 상태, 실측과의 비교)으로 검증하기 전까지 같은 「미검증」 규칙을 적용합니다.

**운영 규칙 [확정]:**

1. **관측 등급**을 CLI × 버전별로 둡니다: `검증됨` / `일부 관측` / `미검증`. 현재 Codex = `일부 관측`, Claude = `미검증`(검증 전).
2. **출력 스트림만으로 슬롯을 반환하지 않습니다(fail-closed).** `검증됨`이 아닌 CLI의 세션은 실행 내내 **1 + 하위 Agent 예산 k** 슬롯을 보유한 것으로 셉니다. 관측된 수가 k를 넘으면 관측값을 씁니다.
3. 관측이 끊기거나 불완전하면 그 세션의 수를 줄이지 않고 **「미확인」으로 보유**하며, 새 세션 시작을 보류합니다.
4. **슬롯 반환은 프로세스 그룹이 비었을 때만** 합니다. 강제 중단도 그룹 단위로 해 자손이 남지 않게 합니다. 일정 시간 뒤에도 그룹이 남으면 「정리 안 된 실행」 알림을 올립니다.
5. **세션 안에서 하위 Agent 생성을 직접 막지 않습니다**(hook 미사용의 대가). 통제는 (a) Task 지시문의 동시 하위 Agent 예산 명시, (b) Runner의 새 세션 시작 조절(유일한 강제 수단), (c) 예산 초과가 반복되면 알림 · 예산 조정으로 합니다. 순간적인 초과는 상한 공식의 여유분(전체 × 0.75)과 충돌 묶음 직렬화로 흡수합니다.
6. 부하 조절은 가능하면 **cgroup 실측 CPU · 메모리**를 우선합니다. 하위 Agent 수는 참고 정보(보고서 · 통계 · 지정 vs 실제)로 씁니다. WSL2에서 Runner가 cgroup v2를 쓸 수 있는지(systemd 활성화)도 검증 대상이며, 안 되면 프로세스 그룹 + `/proc` 합산으로 대신합니다.
7. **「실제 사용된 하위 Agent」**는 세션 종료 후 기록 파일로 확정하고, 이름 → 버전은 설치 시 기록한 정의 hash로 연결합니다. 확정할 수 없으면 「일부 관측」으로 표시하고 재작업률 통계에서 제외합니다. 지정한 하위 Agent를 쓰지 않았으면 **주의 표시만** 하고 Completion Gate 조건으로는 쓰지 않습니다.
8. Runner 준비 점검에 「CLI 버전 = 관측 검증된 버전인가」를 추가합니다. 다르면 경고(실행은 계속, 관측은 참고만 · fail-closed 계산).

**화면 (프로토타입)** — 설정 → Runner · 실행 환경 → 동시 실행 카드 「하위 Agent 관측」: 실행 중 세션별 CLI 관측 등급 · 관측 수 · 보유 계산 수(`max(예산, 관측)`) · 상태, 하위 Agent 동시 예산(개발 · 재작업 / 검증 세션), CLI별 설치 버전 · 검증 버전 · 모델 · 관측 등급 · 검증 조건. 동시 실행 합계는 「세션 + 하위 Agent(관측 n · 보유 계산 m)」로 표시하고 한도 판단에는 보유 계산 값을 씁니다. 실행 기록(Task 상세 · 작업 실행)은 「지정 …」 · 「실제 … · 세션 기록 확인 / 일부 관측」 · 「지정 미사용」(주의 표시만)을 보여줍니다. Mock: Claude 2.4.1(미검증) · Codex 0.167.0(일부 관측), TASK-0007 첫 개발 시도는 지정한 `fe-implementer`를 쓰지 않은 예입니다.

## 7. Agent 실행 정책 — 모델 · Effort [확정 원칙 + Mock 규칙]

### 7.1 의사결정 분담

| 주체 | 결정하는 것 |
|---|---|
| **Planning Agent** | Task별 개발 등급 · 검증 등급(모델 · Effort)과 **근거**. Task 추정 시 함께 결정하고 Task에 저장 |
| **팀장** | ① 허용 모델 목록 ② 최상위 등급 재작업 알림 횟수 ③ 최저선 ④ 사용량 부족 · 재작업 시 조정 정책. 필요하면 특정 Task 등급을 **고정**(이력에 남음) |
| **Runner** | 실행 직전 정책 범위 안에서 최종 등급 결정(재작업 상향, 사용량 절약 하향, 재개 시 유지). **실제 사용한 모델 · Effort와 조정 사유를 시도마다 보고** |

> 목적은 항상 최상위 모델 · Effort를 쓰는 것이 아니라, **작업 유형에 맞는 등급을 쓰는 것**입니다. 품질을 우선하고, 개발 시간은 충분히 가질 수 있는 환경입니다.

### 7.2 등급 표현

- WBS에는 **모델 ID와 Effort 키**를 저장하되, Effort는 CLI마다 단계 이름 · 개수가 달라 **공통 단계(1 낮음 · 2 보통 · 3 높음 · 4 매우 높음 · 5 최대)**로 비교합니다. Runner가 각 CLI 값으로 변환합니다.
- 사용 가능한 모델 · Effort 단계는 **Runner가 조회해 보고**합니다. 새 모델은 「신규 보고 — 미허용」으로 등록되고 팀장이 허용해야 쓰입니다.
- 허용을 해제하면 그 모델을 쓰던 Task는 다른 허용 모델로 다시 판단됩니다(고정 Task 포함, 이력 남김). Agent마다 허용 모델은 최소 1개.

### 7.3 정책 (설정 화면)

| 정책 | 선택지 | 기본 |
|---|---|---|
| 사용량 부족 시 | **리셋까지 대기** / 낮춰서 진행(남은 사용량 10 · 20 · 30% 미만에서 Effort 한 단계 하향) | 리셋까지 대기 |
| 재작업 시 | 같은 등급 유지 / **한 단계 상향** / 최상위로 상향 | 한 단계 상향 |
| 최상위 등급 재작업 알림 | 1회째 / **2회째** / 3회째 / 알리지 않음 | 2회째 |
| 최저선 | 「검증 Effort ≥ 개발 Effort」, 「DB · Migration 작업 Effort 높음 이상」 각각 적용/해제 | 둘 다 적용 |

규칙:

- **한 단계 상향:** 직전 개발 시도 기준 Effort +1, Effort가 최상위면 허용 모델 중 한 단계 위 모델. 더 올릴 등급이 없으면 같은 등급으로 재시도하고 알림 횟수를 셉니다.
- **낮춰서 진행:** 최저선 아래로, 팀장 고정 Task는, 재작업 상향이 적용되는 시도는 낮추지 않습니다. 남은 사용량 0%면 항상 대기합니다.
- **중단 후 재개는 항상 같은 등급 유지.**
- 등급이 바뀌면(팀장 고정 · 해제, 허용 모델 변경) 개발 작업량을 **재추정**하고 일정을 재조정합니다.
- 대시보드 「실행 등급별 결과」(시도 · 판정 · FAIL · 재작업률 · 상향 · 토큰)는 **Planning Agent가 이후 판단을 보정하는 근거**입니다. 팀장은 표를 관리하지 않고 결과만 봅니다.

### 7.4 하위 Agent (subagent) [확정 원칙 + Mock 정의]

**왜 우리 정의인가:** 외부 하위 Agent 모음(Claude 약 154개 · Codex 약 175개)은 대부분 「역할 · 일하는 습관」을 담은 범용 지시문이고, 저장소가 직접 「보안 · 정확성은 검증하지 않음」이라고 밝힙니다. 이 시스템에서 품질을 좌우하는 것은 Task 명세 · 제외 범위 · Acceptance Criteria · Completion Gate · 실행 정책이며, 범용 지시문은 오히려 명세 · 스택(React · Mantine / Fastify · Drizzle / pnpm) · 모델 정책과 충돌할 수 있습니다. 그래서 **우리 Workflow에 맞춘 정의를 10개 안팎으로 직접 두고**, 외부 모음에서는 쓸 만한 점검 목록만 골라 옮겨 옵니다.

**정의 (Mock 10개):** Claude — `fe-implementer` · `be-implementer` · `db-migrator` · `api-contract-reviewer` · `code-reviewer` · `doc-writer` / Codex — `qa-verifier` · `test-writer` · `security-reviewer` · `planner-estimator`(Planning 전용, 미허용). 각 정의: 역할, Agent, 도구, 권한(worktree 쓰기 / 읽기 전용 등), 지시문, 버전 · 해시, 참고한 외부 정의. **모델 · Effort는 정의에 적지 않습니다** — Runner가 설치할 때 Agent 실행 정책의 등급으로 채웁니다.

**자동화 (설치를 잊을 수 없게):**

1. 정의는 **Agent WBS가 보관**합니다(작업 저장소가 아님 — Agent 브랜치마다 버전이 섞이거나, 초기화로 저장소를 되돌릴 때 함께 사라지는 문제를 피함).
2. **Planning Agent가 Task를 추정할 때 개발 · 검증 각각 쓸 하위 Agent를 지정**하고 근거를 남깁니다(예: TASK-0005 → 개발 `be-implementer`, 검증 `qa-verifier` · `security-reviewer`). 쓸 필요가 없으면 지정하지 않고 기본 Agent로 실행합니다 — 반드시 쓰는 것이 아닙니다.
3. **Runner가 시도를 시작할 때마다** 지정된 정의(허용 버전)만 받아 해당 worktree의 `.claude/agents/` · `.codex/agents/`에 설치합니다. 사용자 전체 폴더(`~/.claude/agents` 등)에는 설치하지 않습니다.
4. **설치에 실패하면 그 시도는 시작하지 않습니다** (`SUBAGENT_INSTALL_FAILED` — 다시 시도). 모르는 사이에 하위 Agent 없이 진행되지 않습니다.
5. Codex도 하위 Agent를 스스로 띄울 수 있습니다(`spawn_agent` — 검증에서 병렬 실행 확인). Runner는 지시문에 사용할 하위 Agent · 맡길 일 · **동시 예산**을 명시합니다.
6. 설치한 하위 Agent와 버전, **실제 사용된 하위 Agent(6.7 — 사후 확정, 확정 불가 시 「일부 관측」)**를 시도마다 기록합니다.
7. 팀장 설정: 「하위 Agent 사용」 전체 켜기/끄기, 정의별 허용/해제(해제하면 진행 전 Task 지정을 Planning Agent가 다시 판단). 새 정의 추가는 Planning Agent 제안 → 정책에 따라 반영.

**화면:** 설정 → 하위 Agent(정의 · 역할 · Agent · 도구 · 권한 · 버전 · 지정 Task 수 · 마지막 사용 · 재작업률 · 허용, 지시문 보기, 참고 자료), Task 상세 → 실행 등급 → 하위 Agent(개발 · 검증 지정과 근거), 실행 기록(설치된 하위 Agent · 버전). 하위 Agent별 재작업률로 효과를 판단합니다.

**Runner 준비 상태 (같은 이유 — 잊어버린 설치 방지):** Runner가 시작할 때와 매일 한 번 Claude Code · Codex CLI(설치 · 로그인), git · Node.js · pnpm 버전, PostgreSQL 연결, 작업 저장소 접근, worktree 디스크 여유, 하위 Agent 정의 동기화를 점검해 보고합니다. 「문제」 항목이 있으면 해당 Agent 실행을 멈추고(실행 불가 사유 표시) 대시보드에 알림을 띄우며, 항목마다 조치 방법(예: `codex login` 실행)을 보여줍니다.

실제 사용 확인 · 동시 수 제한 방법은 **6.7로 결정**되었습니다(hook 미사용, 출력 스트림은 관측만, 종료 · 자원은 프로세스 그룹 기준).

## 9. 실제 구현 시 주의할 점

### 9.1 데이터 · 정합성

1. **참조는 항상 Task ID.** WBS 번호는 저장하지 말고 조회 시 계산하거나, 저장한다면 트리 변경 시 일괄 재계산합니다.
2. **판정은 서버가 합니다.** 차단 여부, 순환, Gate, CP 시뮬레이션, 일정, 등급 유효성은 서버 Service에서 계산하고 클라이언트는 결과를 표시합니다. Runner가 API로 직접 상태를 바꿀 수 있으므로 클라이언트 검증만으로는 부족합니다.
3. **이력은 추가 전용(append-only).** 변경 전/후 값, 주체(팀장 · Planning Agent · Runner · Codex · Claude · 시스템), 시각을 남깁니다. 실행 시도 · 검증 결과 · 기준 일정 버전도 덮어쓰지 않습니다.
4. **CP 미리보기와 반영은 같은 함수**로 계산합니다. 반영은 트랜잭션 안에서 다시 시뮬레이션하고, 결과에 문제가 있으면 반영을 보류합니다(미리보기 이후 데이터가 바뀌었을 수 있음).
5. **동시성:** Runner 여러 세션(PC에 따라 수십 개, 하위 Agent 포함)과 팀장 UI가 동시에 같은 Task를 바꿀 수 있습니다. 낙관적 잠금(`updatedAt`/version)과 상태 전이 검증(허용된 전이만)을 서버에서 강제합니다.
6. **멱등성:** Runner는 네트워크 단절 후 같은 보고를 재전송할 수 있습니다. 상태 · 결과 · 중단 보고에 멱등 키(시도 ID + 이벤트 시각 등)를 둡니다.
7. **상태 전이 규칙을 문서화된 표로 고정**하세요(예: `qa` → `rework` | `gate`, `paused` → `running` | `qa` | `verifying`). 프로토타입은 화면 흐름으로만 표현했습니다.

### 9.2 일정

1. 일정은 **이벤트가 생길 때마다 서버에서 재계산**하고, 새 기준 버전 생성 여부는 임계값으로 판단합니다. 모든 이벤트마다 버전을 만들면 3개월 · 200 Task 규모에서 이력이 폭증합니다.
2. **시간대:** 가동 기록 · 리셋 시각 · 작업 불가일은 모두 시간대가 있습니다. 저장은 UTC, 표시는 팀장 시간대(Asia/Seoul)로 하고, "하루"의 경계를 어느 시간대로 자를지 명시하세요. 프로토타입은 로컬 시간 문자열로 단순화했습니다.
3. 가동률은 **heartbeat 누락을 세션 종료로 해석**합니다. heartbeat 주기 · 누락 허용 횟수를 설정값으로 두세요.
4. 진행 중 Task의 남은 작업량은 상태 단계 가중치로 근사했습니다. 실제로는 Runner가 보고하는 진행 정보(또는 Agent 자가 추정)로 바꾸는 것을 검토하세요.
5. 200 Task 기준 List Scheduling은 서버에서 충분히 빠르지만, Gantt · Tree Table 렌더링은 **가상 스크롤**이 필요합니다(프로토타입 미구현).

### 9.3 Agent 실행 정책

1. 모델 ID를 코드에 하드코딩하지 않습니다. Runner 보고 → `agent_models` 테이블 → 팀장 허용의 흐름으로만 씁니다.
2. Effort 공통 단계 매핑은 Agent(CLI)별 설정으로 둡니다.
3. Runner의 자율 조정(상향 · 하향 · 유지)은 **정책을 WBS에서 받아 실행하고 결과를 보고**하는 구조여야 합니다. Runner가 자체 규칙을 따로 갖지 않게 하세요(`run-grade` API가 단일 출처).

### 9.4 메시지

1. 전달 상태(Draft~Cancelled)와 Agent 응답 · 작업 완료는 **별도 필드**입니다.
2. 실행 중 전달 미지원이면 `pendingNext` 상태로 두고 **다음 실행 시작 시 Runner가 가져가 ack**합니다.
3. 메시지로 공식 명세를 바꾸는 경로를 만들지 않습니다. 반드시 CP를 거칩니다.

### 9.5 프로젝트 등록 · 초기화

1. 초기화는 **트랜잭션 하나로** Agent WBS 데이터를 삭제하고 초기화 번호를 올립니다. 일부만 지워진 상태가 남지 않게 합니다. Evidence · 보고서 PDF 같은 파일 저장소도 같은 작업에서 지우고, 실패하면 재시도 대상으로 기록합니다.
2. Runner의 저장소 정리는 **기준 커밋이 기록되어 있을 때만** 실행합니다. GitHub의 Agent 브랜치 삭제 · 열린 PR 닫기 · main 되돌림 커밋(강제 push 금지)을 정리 항목에 포함합니다.
3. 입력 자료는 Runner 전용 작업 폴더에 **읽기 전용으로 checkout**하고 초기화 시 그 폴더만 지웁니다. 안의 스크립트 · 설치 명령은 실행하지 않고, 하위 모듈(submodule)은 따라가지 않습니다. Git LFS 파일이 있으면 Runner에 git-lfs가 필요합니다(없으면 checkout 실패로 표시).
4. **보호 경로:** Agent PR이 `prototype/` · `.agentwbs/` 를 바꾸거나 빌드 결과물(`.gitignore` 대상)을 커밋하면 Task 검사 첫 단계에서 거부합니다(4.13). GitHub에도 CODEOWNERS · 보호 규칙을 같이 걸어 이중으로 막습니다.
4-1. **GitHub 인증:** gh 로그인 또는 저장소 한정 fine-grained 토큰(Contents 읽기 · 쓰기, Pull requests 쓰기, Commit statuses 쓰기, Metadata 읽기). 토큰은 서버에 암호화 저장, 화면 · 로그 · API 응답 · **Agent 세션 환경 변수에 넣지 않음**(Agent는 로컬 worktree에서만 일하고 push · PR은 Runner가 함). 만료 7일 전 알림.
5. 프로젝트 등록 · 초기화 API는 팀장 세션에서만 호출할 수 있게 하고, Runner 토큰으로는 호출할 수 없게 합니다.

### 9.6 보고서

1. 스냅샷은 **불변**입니다. 수정 API를 만들지 않습니다. 잘못 생성되었으면 새로 생성하고 이전 것은 남깁니다.
2. 정기 보고서 생성 시각 · 기간 경계는 팀장 시간대(Asia/Seoul) 기준입니다. 서버를 UTC로 돌리면 하루 경계가 9시간 어긋납니다.
3. 누락분 보충은 한 번에 너무 많이 만들지 않도록 상한(예: 31일)을 둡니다.
4. 보고용 문장은 숫자와 같은 스냅샷에서 만들고, 템플릿 문장으로 생성합니다(Agent에게 자유 작성을 맡기면 숫자와 문장이 어긋날 수 있음).
5. **메일 HTML은 화면 HTML을 그대로 쓰지 않습니다.** 메일 앱(Outlook · Gmail 등)은 외부 CSS · `<style>` · flex/grid · 웹 폰트 · 스크립트를 무시하거나 제거합니다. **표(`<table>`) 레이아웃 + 인라인 스타일 + 폭 640px**, 외부 이미지 없이 만들고, 글꼴은 `'Pretendard GOV', 'Apple SD Gothic Neo', 'Malgun Gothic', sans-serif` 순서로 지정합니다(Pretendard GOV는 설치된 PC에서만 적용 — 메일에서는 예외적으로 대체 글꼴 허용). 텍스트 대체본(`text/plain`)도 함께 보냅니다(multipart/alternative). 프로토타입 `Sel.mailHtml`이 기준 구조입니다.
6. 발송은 보고서 생성 트랜잭션과 분리된 **발송 큐(작업 테이블)**로 처리합니다. 메일 서버 오류가 보고서 생성을 실패시키면 안 됩니다. 멱등 키: 보고서 ID + 수신자 ID + 시도 번호 — 서버 재시작 시 같은 메일이 두 번 나가지 않게 합니다.
7. SMTP 비밀번호는 암호화해 저장(OS 키체인 또는 서버 비밀 키)하고 API 응답 · 로그 · 내보내기에 포함하지 않습니다. 수신자 주소는 개인정보이므로 로그에는 남기되 외부로 보내는 데이터(보고서 링크 등)에 넣지 않습니다.
8. 「전체 보고서 보기」 링크는 Agent WBS가 같은 PC(`localhost`)에서 돌기 때문에 **같은 PC · 같은 네트워크에서만 열립니다.** 상급자처럼 외부에서 받는 사람에게는 PDF 첨부를 기본으로 권장합니다(프로토타입 Mock 수신자 RC-2가 그 예).

### 9.6-1 설계 원장
1. 기준은 계약 파일 하나입니다. Agent WBS DB의 설계 데이터는 **커밋 기준 캐시**(어느 커밋에서 읽었는지 기록)이며 직접 수정하지 않습니다. 결정(기술 결정)만 Agent WBS가 원본입니다.
2. 같은 항목의 키를 고정합니다: REST `METHOD path`, 테이블 `store:name`, 토픽 · 채널 이름, Redis 키 패턴. Task ↔ 항목 연결 · 불일치 · 충돌 묶음이 모두 이 키를 씁니다.
3. 호환 판정은 형식별 규칙으로 기계적으로 합니다(필드 삭제 · 타입 변경 · 필수화 = 호환 깨짐). Agent 판단에 맡기지 않습니다.
4. 실제 코드에서 명세를 추출하는 방법은 형식별로 다릅니다(OpenAPI는 라우트 스키마에서 생성, DB는 개발 DB 조회, Neo4j는 `SHOW CONSTRAINTS` 등). 추출이 불가능한 형식은 「대조 안 함」으로 표시하고 불일치 0건으로 보이지 않게 합니다.
5. 대규모(테이블 50개 이상)에서는 ERD 전체 그림 대신 도메인별 · 선택 항목 중심 그림을 씁니다(프로토타입은 목록 + 상세만).

### 9.6-2 빌드 · 통합 · GitHub
1. 실행 명령 · 결과 기록은 Runner가 하고 서버는 저장 · 표시만 합니다. 실행 로그 원문은 크므로 파일 저장소에 두고 DB에는 요약 · 위치만.
2. 실행 · 병합 대기열 · 배포 확인은 **무거운 작업 상한**을 Agent 세션과 공유합니다. 빌드가 몰리면 새 Agent 세션 시작을 늦춥니다.
3. 통합 확인 실패 시 「병합 안 함」이 기본입니다. main을 되돌리는 동작은 없습니다(병합 전에 막으므로).
4. 마이그레이션 번호 충돌(두 Task가 같은 번호)은 통합 확인의 「빈 DB부터 마이그레이션」에서 잡히도록 합니다. 번호 대신 시각 기반 이름을 권장합니다.
5. 빌드는 `src/` 만 대상으로 합니다. 빌드 결과물은 저장소에 커밋하지 않습니다(`.gitignore`). 배포 확인의 Docker 이미지에는 `prototype/` · `contracts/` 를 넣지 않습니다.
6. GitHub API 호출(PR · status)은 Runner가 하고, 실패하면 재시도 대기열에 넣습니다. GitHub 장애가 로컬 검사 결과를 잃게 하면 안 됩니다.

### 9.6-3 알림 — Telegram
1. 토큰은 **쓰기 전용** 필드로 다룹니다 — GET 응답 · 서버 로그 · 오류 메시지 · 이력에 넣지 않습니다. 요청 로그에서 `botToken` · `bot<token>/` URL 경로를 마스킹하세요(Telegram API URL에 토큰이 들어갑니다).
2. 발송은 대기열 + 워커로 합니다. `429`는 응답의 `retry_after`만큼 기다려 재시도, 통신 실패는 지수 백오프(최대 횟수 후 「실패」). `400 chat not found` · `401` · `403`은 재시도하지 않고 연결 상태를 오류로 바꿉니다. 한 대화에 초당 1건, 그룹은 분당 20건 수준을 넘지 않게 합니다.
3. `getUpdates`는 Webhook이 설정된 봇에서 동작하지 않습니다. **Webhook을 자동으로 지우지 않습니다**(다른 서비스가 쓰는 봇일 수 있음). 수신 대상 찾기는 「조회한 후보를 보여 주기만」 하고, 이 과정에서 받은 업데이트를 다른 용도로 쓰지 않습니다.
4. 그룹이 슈퍼그룹으로 바뀌면 Chat ID가 바뀝니다(`migrate_to_chat_id`). 오류 응답에 새 ID가 오면 자동 교체하지 말고 「수신 대상 변경 필요」로 알리고 팀장이 테스트 후 저장하게 합니다.
5. 상태 전이 비교는 **서버의 저장 트랜잭션 안**에서 하고, 알림 생성(outbox insert)도 같은 트랜잭션에 넣습니다 — 상태는 바뀌었는데 알림이 빠지거나, 롤백됐는데 알림이 나가는 일을 막습니다.
6. 메시지는 일반 텍스트로 보냅니다(Markdown · HTML 파싱 오류 방지). Task 제목 등 사용자 입력은 그대로 넣되 길이를 자릅니다.
7. 알림 기능 오류(설정 없음 · 발송 실패 · 워커 정지)가 Task 상태 변경 · Runner 보고 저장을 실패시키면 안 됩니다.

### 9.7 UI

0. **목록 + 상세 전환** [확정]: 원래 목록이 있는 화면(WBS, 검증 → 결과)은 「처음엔 전체 목록 → 항목 클릭 시 목록이 260px 레일로 줄고 상세 표시 → 레일 맨 위 「펼치기」로 원래 목록 복귀」 방식을 씁니다. 레일 40px 접기는 쓰지 않습니다. 작업 실행 · 변경 제안 · Planning · 보고서는 항상 「좁은 목록(260~320px) + 상세」 구조이며 접기 버튼이 없습니다.

1. **Pretendard GOV를 모든 텍스트에 사용**합니다(코드 · 숫자 · 입력창 · placeholder 포함). 한글이 없는 고정폭 폰트를 섞으면 대체 폰트가 끼어 글꼴이 섞여 보입니다. 숫자 정렬은 `font-variant-numeric: tabular-nums`로 합니다. 웹 폰트는 `pretendard-gov` npm 패키지(1.3.9)의 Variable woff2를 번들에 포함하거나 jsDelivr에서 불러옵니다.
2. 상태는 색 + 텍스트, 필수/선택 입력 구분, 위험한 변경은 확인 대화상자, 검증 실패는 구체적인 원인과 조치 안내.
3. 「실제로 구현하지 않은 동작은 완료된 기능처럼 표현하지 않는다」는 원칙을 실제 서비스에도 적용합니다(예: Runner가 실행 중 전달을 지원하지 않으면 그렇게 표시).

## 12. 프로토타입으로 확인할 시나리오

구현 결과가 프로토타입과 같은 동작을 하는지 확인하는 기준으로 사용합니다.

1. Task 생성 Wizard → 상세 명세 작성 → 읽기/편집 전환
2. DB Task(TASK-0004)의 테이블 · 컬럼 설계 입력
3. 선행 Task 지정 → 실행 차단 표시, 순환 추가 시 경로와 함께 저장 차단
4. 체크리스트 완료 → 진행률 · Gate 갱신
5. Planning 분석 비교 → 이견 조정 → Change Proposal → 자동 반영 → 일정 재조정 이력 확인
6. Claude 개발 결과 등록 → Codex QA FAIL → 재작업(**등급 자동 상향** 확인) → 재검증 PASS → Gate → 완료
7. 실행 중 추가 지시 → 다음 실행 대기 → 다음 실행 시 전달 · ack → 응답
8. Runner 연결 끊김 → 메시지 전달 실패 → 재연결 → 재전송
9. 설정에서 Runner 「재부팅」 → 실행 중 시도 「중단」 → 재연결 → 재개(같은 등급, 새 시도)
10. 사용량 한도 도달 → 그 Agent Task가 리셋 이후로 밀림 → 리셋
11. 작업 불가일 추가 · 동시 실행 상한 변경 → 완료 예상 · 범위 변화, Gantt 빗금
11-1. 설정에서 Runner 「메모리 압박」 → 한도 감소 · 조절 기록 · 일정 재계산, 「안정 10분 유지」 → 한도 증가(상한까지). 같은 충돌 묶음 Task(TASK-0008 · 0009)는 TASK-0005 실행 중 시작 불가

12. 허용 모델 변경(Fable 5.1 허용) → 아직 시작하지 않은 Task 등급 재판단
13. Task 상세에서 등급 고정(최저선 미달 경고) → 작업량 재추정 · 일정 재조정 → 고정 해제

## 13. 디자인 기준

- Modern Enterprise, 절제된 스타일, 높은 정보 밀도와 충분한 가독성, 일관된 상태 색상, 불필요한 장식 최소화.
- 레이아웃: Header 64px, 왼쪽 메뉴 **180px**(접기 56px), Page padding 24px, Card padding 16px, Modal 1024~1280px, 1920px 데스크톱 우선 + 반응형.
- 본문 12~14px 이상. 너무 작은 글자, 과도한 Badge · 카드 중첩, 약어 · 아이콘 위주 Navigation을 피합니다.
- 피해야 할 것: Kanban만으로 WBS 표현, 제목 · 설명 · 상태만 있는 Task 상세, 명세를 하나의 긴 텍스트에 몰아넣기, 좁은 컬럼으로 정보 잘림, Label과 입력값이 지나치게 멀어지는 전폭 레이아웃, 모든 Task에 같은 설계 항목 강제.

> **핵심 원칙:** 사용자가 화면의 의미를 다시 해석하지 않아도 무엇을 확인하고 어떤 작업을 해야 하는지 즉시 이해할 수 있어야 합니다.
